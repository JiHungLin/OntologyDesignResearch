Domain 設計心法

把連續的現實，切成一個個意思唯一、說得清楚、經得起檢驗的單位個體，而且這些單位個體的意思，在變成資料表、API、畫面、AI 回答的過程中不會走樣。

這頁講「為什麼這樣做」。每一步要交的文件與完成標準，見《團隊開發流程》（Domain 設計規範）；那些產出都是為了達成這裡的目的而存在。產出可以調整，目的不能丟。

看每一步的交付物與完成標準：六步開發流程 → 一頁版：心法精華 →

主線：把連續的現實，切成系統能使用的單位個體

現實是連續的：一個人每天上班、請假、換店支援、離職又回來，沒有明確的格子。數位世界是離散的：系統只能記下一筆一筆的資料、一個一個的狀態。系統要能運作，就必須用一個個單位個體來描述現實。單位個體指的是系統裡可以被指認、可以被單獨記錄的一個東西：一個人、一段僱傭關係、一筆請假申請、一個班別。它不是度量用的「單位」（公斤、小時），而是有身分的個體，會被產生、改變、結束，也會和其他單位個體互動。Sean 說「一手為陰、一手為陽」：設計者負責把現實搬進數位世界。

轉換最常出的錯，不是程式寫錯，而是單位個體切錯了：

員工

兩個單位個體被合成一個：有時指一個人，有時指一段僱傭關係。人離職再回來，系統就亂了。

核准

一連串變化被壓成一個：主管核准了，系統就當作請假已經發生。但員工後來根本沒請。

完成

同一個字指不同的單位個體：業務說簽約就完成，財務說收到錢才完成。系統只有一個 status = done。

程式完全照規格執行，結果卻是錯的，因為規格切出來的單位個體本身就對不上現實。六個階段，就是這件轉換的六個環節：

連續的現實
① 蒐集現實資訊：把要處理的現實帶進來

Ontology：現實在數位世界的單位個體系統

它不是新東西

Ontology 是軟體與知識工程裡既有的概念：描述一個領域有哪些概念、彼此什麼關係、有哪些約束。概念模型、領域模型、DDD 的通用語言都在做相近的事。我們整理 entity、relation、event、state，本來就是在做它。用主線來說，Ontology 就是 ②③④ 切出來的那套單位個體系統。

這次要改變的是什麼

以前這套單位個體系統隱含在 ERD、程式和資深同事腦中。現在把它明確導入設計過程，成為一份獨立、有版本、跨 domain 共用、人和 AI 都能檢查的東西。

一份凍結、有版本的單位個體定義集：有哪些單位個體（以及邊界）、單位個體怎麼變化（以及生命週期）、單位個體之間什麼關係、依據什麼規則、什麼永遠要成立。它本身不執行任何東西。

輸入① 蒐集的現實資訊：範圍與邊界、規範來源、真實情境、例外與反例
輸出詞彙表與 Entity 卡、關係清單、事件與狀態、規則表（需要對帳處含守恆式），存放在共用的 core/
不產出資料表、API、畫面、程式碼。它們是 ⑤ 放進技術載體的結果，每一個都要能指回它承載的單位個體

三個作用：大家說同一種話、每個產出都追得回來、為 AI 劃界。

貫穿全程的四個信念

規範沒寫到的情況，回到這四條判斷。

一

意思先於形式

先問「這是什麼單位個體」，再問怎麼存、怎麼顯示、怎麼呼叫。先想資料表，就會讓「好存」決定單位個體怎麼切。

二

判斷要寫下來，才能被檢查

資深的人心裡都有的切法，沒寫下來，新人、AI、下一個專案都不知道。寫下來是為了讓判斷可以被別人挑戰。

三

經得起推翻的，才值得相信

刻意用例外、跨店兼職、事後補單、法規修改去戳。設計者自己說沒問題不算數，要由別人、真實案例、實際執行的結果來證明。

四

AI 負責發散，人負責判斷

AI 擅長「相似」，企業需要「明確」：Manager、Approval、Permission、Authority 在 AI 眼裡很接近，在公司裡是四個單位個體。信任來自可以檢查的結果，不是來自放手。

六個階段：目的與判斷方式

每個階段分兩層：目的明確但抽象，不規定做法；怎麼判斷做到了是比較具體的方法層。不是瀑布，後面發現前面漏了，回頭補是正常的。

① 蒐集現實資訊

目的把要處理的那部分現實，盡可能完整地帶進來，包括例外。

Ontology　準備 Ontology 的輸入

為什麼需要

單位個體是從資訊裡切出來的。資訊缺了，後面切出來的單位個體一定也缺；而現實沒有邊界，不先劃定範圍，資訊永遠收不完。所以這一步同時決定：這次帶進來的現實有多大，以及做完後系統要能回答哪些問題。

怎麼判斷做到了

要問自己
  • 範圍從哪裡開始、到哪裡結束？哪些明確不做？
  • 真實發生過哪些情況，尤其是不照正常流程走的？
  • 做完以後，系統要能回答哪些問題？答不出來就算沒做完
做好的感覺

任何人都能說出「這個情況在範圍內嗎」；你知道該怎麼判斷成敗。

常見陷阱
  • 用功能選單劃範圍（「請假功能」），而不是一條真實情境
  • 只寫正常流程；系統會壞的地方都在例外
  • 資訊全由 AI 整理，盲點一路傳到最後
產出為什麼存在

範圍、草稿 User Story、驗收問題，分別回答「帶進來的現實有多大」「現實裡真實發生什麼」「怎樣算成功」。

AI補充沒想到的例外；把訪談整理成情境

人決定做與不做；從現場與 Domain 專家取得真實情況

② 找出獨立單位個體

目的從連續的現實中，切出一個個有自己身分、能被指認、系統能使用的個體。

Ontology　產生 Ontology 的單位個體與邊界，這是它最核心的部分

為什麼需要

系統只能處理離散的東西，必須先決定「一個」是什麼。後面的混亂，幾乎都源自這裡把兩個單位個體當成一個（人和僱傭關係、請假申請和請假事實、角色和權限），或把算出來的數字當成單位個體。一個單位個體的意思，取決於它和其他單位個體的邊界。

名稱與單位個體

名稱只是形式。單位個體用英文識別名稱，讓程式與 AI 穩定指到同一個單位個體；各語言名稱是映射出去的標籤。換語言，標籤會變，單位個體不能變；不同國家的同名概念（台灣特休、日本年次有給休暇）是不同的單位個體。

怎麼判斷做到了

要問自己
  • 它有自己的開始和結束嗎？還是只是屬性或分類？
  • 刪掉它，能從別的資料算回來嗎？算得回來的是推導值，不是單位個體
  • 兩個很像的東西，結束的時間會不會不一樣？會，就是兩個單位個體
  • 它不是什麼？
做好的感覺

每個單位個體都能一句話說清楚，並說出它和最像的那個單位個體差在哪；換專案、換人看也不會誤解。

常見陷阱
  • 為了資料庫好設計而合併單位個體；看到 is_xxx 旗標通常是兩個單位個體被壓成一個
  • 把算出來的數字（餘額、總計）當單位個體管理
  • 同一單位個體在不同 domain 各自重新定義
產出為什麼存在

詞彙表、Entity 卡、「不是 Entity」清單，把「是什麼、不是什麼、跟誰不能合併」固定下來，讓人能挑戰、讓下個專案能沿用。

AI列出候選單位個體，換成懷疑者攻擊自己的結果

人判斷邊界切得對不對；把邊界問題翻成業務語言問專家

③ 描述單位個體的變化

目的描述單位個體會因為什麼而產生、改變、結束，以及每次變化之後處在什麼狀態。

Ontology　產生 Ontology 的變化與生命週期：有哪些變化、由什麼觸發、改變什麼狀態、由人推動時誰有權做

為什麼需要

現實是連續的過程，系統只能記下離散的變化點。變化點切得太粗就會失真：請假只有一個「已核准」，就分不出「核准了」和「真的請了」。這一步仍然是在紙上描述現實，還沒有寫程式。

變化從哪來
  • 人的動作：員工提出請假、主管核准
  • 其他單位個體的變化：員工離職，連帶觸發未休特休結算
  • 外部系統或訊息：銀行回報退匯、政府回覆投保生效
  • 時間或條件到達：年資滿一年取得特休；特休到期失效
兩個重點
  • 可能停在半路的地方要分開記。請假：提出申請 → 系統建議 → 主管核准（或駁回）→ 實際請假（或取消）→ 當月扣薪。每個箭頭都可能停下
  • 建議和決定是不同的變化。系統或 AI 依證據提出建議（「這週人力吃緊，建議改到下週」），由有權的人決定

怎麼判斷做到了

要問自己
  • 這個單位個體從產生到結束經過哪些變化？每次變化後是什麼狀態？
  • 每次變化由什麼觸發？人、其他單位個體、外部系統，還是時間或條件？
  • 哪一步可能停下、沒有下一步？那一步要單獨記
  • 由人推動的變化，誰有權做？需要什麼證據？
  • 做錯了，業務上發生什麼？誰發現、誰核准更正？
做好的感覺

① 的每個情境（含例外）都能在這些變化上從頭走到尾；每次變化都說得出由什麼觸發、改變了什麼、何時；由人推動的說得出是誰、憑什麼。

常見陷阱
  • 一個 status 承載好幾次變化
  • 只描述正常流程，沒有取消、駁回、更正
  • 只描述人的操作，漏了時間、外部系統或其他單位個體觸發的變化（特休到期、銀行退匯）
  • 只把申請程序做對，沒有幫人做決定（9/30：「程序 OK、整體不 OK」）
產出為什麼存在

事件與狀態目錄記下變化、狀態與權責；決策流程記下建議怎麼產生、誰決定；正式 Use Case 回頭驗證每個草稿情境都走得通。

AI推演各種路徑與例外

人拿正式 Use Case 對照現實：真的是這樣走嗎？

④ 描述單位個體的限制

目的描述單位個體與變化必須遵守的條件：什麼情況下允許、數值怎麼算、得出什麼結論、什麼關係永遠要成立。

Ontology　產生 Ontology 的規則與約束；到這裡 Ontology 定義完成，可以凍結

為什麼需要

現實裡有很多隱含的規矩，人會自然遵守，系統不會。這些規矩必須明確寫出來，系統才能一致地執行；寫成獨立、可閱讀的清單，而不是散在程式的 if/else 裡，人才能審查。

四種限制（依管什麼）
  • 前提條件：年滿 18 歲才能建立資料；額度足夠才能核准請假
  • 計算：加班費依時薪與倍率計算
  • 判定：補假被駁回的缺勤列為曠職；某次缺勤是否屬於職災
  • 永遠成立的關係：假的取得與使用要能對帳

另外標出系統能不能自己判斷：可自動判斷、看條件、需要解釋，或交給人判斷（例：是否屬於職災）；交給人判斷的，系統只能建議。

每條要說得出

套用在哪裡（哪個單位個體或變化）、從哪來（法規、政策、業務需求）、違反時怎麼辦（擋下、提醒、交給人）。版本只在需要時才加：會隨時間改變、且舊結果要依當時規則解釋的（例：法定費率），才記版本與生效日。

怎麼判斷做到了

要問自己
  • 哪些事需要先滿足條件？哪些數值要計算？哪些關係必須永遠成立？
  • 違反時要擋下、提醒，還是交給人判斷？
  • 會不會隨時間改變？改變後舊結果照舊還是重算？
  • 判斷需要的資料，② 的單位個體存得下嗎？（判斷 18 歲就要有出生日期）
做好的感覺

每條限制都說得出套用在哪裡、從哪來、違反時會怎樣、誰來判斷；需要的資料都存得下；會變的已標出版本與生效日。

常見陷阱
  • 規則散在程式各處，沒人說得出全貌
  • 有解釋空間的問題被包裝成確定公式
  • 相信 AI 給的條號與數字；一律對照原文
  • 每條規則都加版本管理，徒增負擔
產出為什麼存在

規則表讓所有限制集中一處、說得出依據、能被審查；需要對帳的地方，守恆式是檢查系統有沒有算錯的尺。

AI從法規、政策、訪談整理出可能的限制

人確認來源與適用範圍；法規逐條對照原文；專家決定哪些需要人判斷

⑤ 放進技術載體

目的用資料表、API 等技術形式承載這些單位個體、變化與限制，而且意思不跑掉。

Ontology　把 Ontology 投影到技術載體；對照表是投影的契約，不屬於 Ontology

為什麼需要

單位個體系統要有載體才能運作。但載體有自己的形狀（表、欄位、外鍵、API），很容易反過來扭曲單位個體，例如為了少一張表把兩個單位個體合成一個。所以要寫下「哪個單位個體落在哪裡」的對照，日後才查得出意思有沒有跑掉。

只對照業務意思

一個單位個體不一定對到一張表。主鍵、建立時間、樂觀鎖版本等技術欄位，或 outbox、稽核紀錄等平台表，不代表業務單位個體，標成「技術」並依《平台架構約定》處理即可。

怎麼判斷做到了

要問自己
  • 每個單位個體落在哪幾張表、哪幾支 API？
  • 每張業務表、每個業務欄位承載哪個單位個體？說不出來又不是技術用途的，就是多出來的
  • 推導值怎麼存？每次變化、每條限制由誰把關？
  • 每個 Use Case 都能用一組 API 完成嗎？
做好的感覺

任意指一個業務欄位，說得出它承載哪個單位個體；任意指一個單位個體，找得到它落在哪裡；其餘都標明是技術用途。

常見陷阱
  • 讓載體的方便回頭改寫單位個體；單位個體真的切錯了就回前面正式修改
  • 每個 domain 各自決定歷史怎麼存、API 怎麼設計（見《平台架構約定》）
  • 要求每個技術欄位都對應業務單位個體，徒增負擔
產出為什麼存在

概念對照表記下每個單位個體落在哪裡，是之後檢查「意思沒有走樣」的依據。

AI依對照表與平台約定產生 schema 和 API

人檢查對照表，確認每個單位個體都有落點

⑥ 回到現實驗證

目的拿現實去對照離散的系統，確認切出來的單位個體與描述沒有失真。

Ontology　證明放進載體後，單位個體的意思仍和 Ontology 一致，而 Ontology 也仍對得上現實

為什麼需要

單位個體怎麼切、變化怎麼描述，都是人和 AI 的判斷，有可能切錯。唯一可靠的檢驗是回到現實：用真實的案例、① 寫下的問題、懂現實的人來對照系統。AI 說「測試全過」不算數，設計者自己說「應該沒問題」也不算數。

怎麼判斷做到了

要問自己
  • ① 寫的驗收問題，系統真的答得出來嗎？
  • 用獨立於系統的方式算出的答案（人手算、試算表、專家提供），和系統一樣嗎？
  • ④ 的限制：該擋下的有擋下嗎？有守恆式的地方都成立嗎？
  • ③ 的例外路徑（取消、駁回、更正）都試過了嗎？
  • 沒跑過的項目，有沒有被當成「通過」？
做好的感覺

把證據攤在桌上給一個懷疑的人看，他找不到理由不相信。

常見陷阱
  • 同一個 AI 自己出題、自己作答、自己改考卷
  • 用測試數量代替測試的有效性
  • 只測正常流程
  • 把「未執行」寫成「通過」
產出為什麼存在

黃金案例、驗收問題回答表、實際執行結果，是「切出來的單位個體對得上現實」的證明，也是下一個人能信任這份設計的依據。

AI產生大量合成資料，測量大、情況多時會不會壞

人用獨立於系統的方式算出黃金案例的答案；專家確認「這就是我要的」；執行與簽核分開

節奏

先規劃，再一條一條做

六個階段是每條切片都要走的。第一條之前，先為整個 domain 做一次粗略的 ①②：先蒐集現實資料（找不到的由 AI 去公開來源找，再找不到的寫成推想、由人接受為假設），再切出切片地圖，最後列出全局名詞草圖。有新資料就回頭更新。

來回，而不是一次走完

後面發現前面漏了就回頭補。這是設計本來的樣子，重點是補的時候說得出原因。

一次做一條小切片

單位個體系統可以想得周全，落地一次只走一條從頭到尾的情境。Sean 說「沒有 over design」，同時要求「從小範圍開始」。

凍結是改動要留紀錄

定案後就凍結；要改，說得出是哪個驗收問題或反例逼你改的。「覺得比較好」不構成理由。

共用的東西只有一份

人、組織、僱傭關係只定義一次，所有 domain 共用。換專案不必重想 entity。

和 Sean 三層方法論的關係

Sean 的三層對應階段真正在守的事
Define Meaning① ② ③ ④單位個體被切清楚、說清楚
Preserve Meaning⑤，以及每個階段的凍結單位個體的意思在轉換中不走樣
Prove Meaning⑥單位個體對得上現實

一頁記住

階段目的怎麼判斷做到了
① 蒐集現實資訊把要處理的那部分現實帶進來，包括例外有人問「這在範圍內嗎」，你答得出來
② 找出獨立單位個體從連續的現實中，切出有身分、能被指認的個體每個單位個體都說得出它「不是什麼」
③ 描述單位個體的變化單位個體因為什麼而產生、改變、結束，變化後處在什麼狀態每次變化都說得出由什麼觸發、改變了什麼
④ 描述單位個體的限制什麼情況允許、數值怎麼算、得出什麼結論、什麼必須成立每條限制都說得出套用在哪裡、從哪來、違反時怎麼辦
⑤ 放進技術載體用資料表、API 承載單位個體，意思不跑掉任何業務欄位都追得回它承載的單位個體
⑥ 回到現實驗證確認切出來的單位個體與描述沒有失真懷疑的人看完證據也找不到理由不信
