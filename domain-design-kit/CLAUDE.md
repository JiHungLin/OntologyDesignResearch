# Domain 設計工作規則

這個 repo 用來把一個 domain 從現實轉成數位系統的設計。你（AI）負責**產出**交付物；人負責**審查與決定**。每一步產出後停下來，等人審查並下達凍結，才進入下一步。

你沒有之前對話的記憶。**每次開始工作，先執行 `/domain-status`**，從檔案重建目前狀態，不要猜。

## 三個名詞（使用者不一定熟悉，需要時用這個說法解釋）

| 名詞 | 意思 | 例子 |
|---|---|---|
| 共用核心（`core/`） | 所有已定義的概念，大家共用一份——**成果** | Person、Employment、LeaveEntitlement |
| 領域 | 一個業務主題範圍，用來分類——**範圍** | 人資／請假、人資／薪資 |
| 切片 | 一個情境從起點走到可驗證的結果——**工作單位** | 急診沒去 → 事後補單 → 餘額與扣薪正確 |

設計與驗證分兩個循環：一條切片做到第 ⑤ 步凍結就是一個設計版本（設計完成，待驗證），接著換下一條；第 ⑥ 步在有系統時再做。切片之間會互相影響，需要改別條切片已凍結的內容時，先向使用者說明、經同意才回頭改並記雙方的 CHANGELOG。

不先設計整個領域，而是一條一條切片做；切片怎麼切，先用 `/domain-plan` 和使用者一起討論出切片地圖（`slices/PLAN.md`）。使用者不需要事先知道切片的名稱和範圍。

規劃也要從現實出發：先盤點現實資料，再切情境、列名詞；地圖與草圖的每一列都標依據（哪份資料，或「推想」）。

名詞則要先看全局：規劃時同時產出全局名詞草圖（`slices/ENTITY_SKETCH.md`），列出所有切片會用到的名詞、預計由哪條切片正式定義；每條切片的第 ② 步對照它，確保共用的名詞撐得起後面的切片。

## 目錄

- `inputs/`：原始輸入。依據分三級：現場資料（`inputs/shared/`、`inputs/<切片>/`）、公開來源（`inputs/research/`，只放實際讀過的頁面，附網址與原文摘錄）、推想（`inputs/drafts/`，你依一般知識寫的參考資料，要經使用者同意）。已存在的檔案不修改（推想草稿的狀態欄除外）；使用者在對話中貼上的資料，新增為 `inputs/` 下的新檔案，檔頭註明「使用者於對話中提供，<日期>」。
- `templates/`、`docs/`、`tools/`：唯讀，不修改。
- `core/`：共用核心（Ontology）。只在 `/domain-freeze` 時寫入。
- `slices/PLAN.md`：切片地圖。
- `slices/ENTITY_SKETCH.md`：全局名詞草圖（規劃用參考，不是 Ontology；正式定義只在 `core/`）。
- `slices/<切片代號>/`：每條切片的交付物。
- `.build/`：工具用 YAML，由你從 Markdown 轉出，不手改、不提交。

## 必須遵守

1. **格式**：交付物一律照 `templates/` 與 `docs/02` 的格式。欄位值只用 `docs/02` 列出的選項，標記只用 `docs/02` 第三節的寫法。
2. **停下來**：每一步產出後，把狀態改為「待檢查」，向人報告後停止。不要自己進入下一步。
3. **不代替人**：
   - 不填「審查者確認」欄，不寫「結論：通過」，不把狀態寫成「已凍結」（只有 `/domain-freeze` 可以）。
   - 不計算、不填寫黃金案例的「預期結果」「計算過程」「計算者」。
   - 不簽核第 ⑥ 步。
   - 不把自己想出來的驗收問題標成「Domain 專家」或「客戶端使用者」來源；那是 `AI`。
4. **來源**：你提供的法規條號與數字，一律標 `[未核對]`。沒有實際讀過的頁面，不能當成公開來源，也不能編造網址。公開來源一個主題一份檔案，分類寫在欄位與 `inputs/research/INDEX.md`，不依國家或年份分資料夾；法規改了就新增一筆、舊的標「已過時」，不刪除；只憑記憶的內容寫成推想草稿。推想草稿只能由使用者接受，你不能自己標「已接受為假設」；接受只代表先當假設用，不代表內容已確認。research 條目的原文核對、規則的解讀核對，都只能由人填寫，你只能寫 `[未核對]`。
5. **留紀錄**：修改狀態為「待檢查」或「已凍結」的檔案時，同時在該切片的 `CHANGELOG.md` 最上面新增一筆。不刪改 `CHANGELOG.md` 的舊紀錄。
6. **語意層不談實作**：第 ①～④ 步的交付物不出現資料表名、欄位名、API 路徑。模型元素用英文識別名稱，第一次出現附中文。
7. **共用核心只有一份**：先查 `core/`，有就引用，不重新定義；要改已驗證的項目，走變更提案。
8. **不確定就問**：範圍、取捨、要不要回頭，提出選項與你的建議，讓人決定。需要專家回答的，寫進 `questions.md`（EQ 編號），相關項目標 `[待專家確認: EQ-nnn]`，繼續往下做。
9. **git**：只有 `/domain-freeze` 會 commit 與打 tag。其他時候不 commit、不 push。
10. **只改流程需要改的**：使用者只是要看內容或問問題時，不修改檔案。編號（D、P、X、EQ…）依新增順序遞增，不重排、不重用既有編號。

## 使用者用一般的話說，你來對應流程

使用者不需要記指令，也不需要知道「切片」「凍結」這些詞。依他說的話判斷該走哪個流程，**開始前用一句話說明你要做什麼**（例：「我先整理一份切片地圖，列出可以分幾條情境來做」），再照對應的 skill 執行。

| 使用者大概會這樣說 | 對應流程（skill） |
|---|---|
| 「現在做到哪？」「接下來要做什麼？」、每次新 session 開始 | `domain-status` |
| 「我們要做請假系統」「想做 POS」、貼上需求或訪談、「這條要拆開」「多加一個情境」 | `domain-plan` |
| 「開始做第一條」「做下一條」「先做急診補請假那個」 | `domain-new-slice` |
| 「繼續」「下一步」「開始寫規則」「這部分重做」 | `domain-step` |
| 「審查好了」「我打勾了」「這步過了」 | `domain-freeze` |
| 「專家回覆了」「人資說其實是…」「客戶覺得…」 | `domain-expert-reply` |
| 「上線後發現一個特例」「這裡設計錯了」「客戶多了一個需求」 | `domain-change`（新需求先判斷擴充現有切片還是開新切片） |
| 「檢查一下有沒有漏」「有沒有衝突」 | `domain-check` |

- 判斷不出來時，先執行 `domain-status`，依目前狀態提出一兩個選項讓使用者選。
- 使用者的話同時涉及多個流程（例：貼上專家意見，又說「然後繼續」），依序處理，每個流程結束時照它的規定停下來。
- `/domain-plan` 這類斜線指令是給熟悉的人用的捷徑，效果相同。

## 指令一覽（捷徑）

| 指令 | 用途 |
|---|---|
| `/domain-status [切片]` | 從檔案重建目前狀態：各步驟狀態、tag、待回覆的專家問題、下一步 |
| `/domain-plan [粗略的範圍或新資訊]` | 建立或更新切片地圖：一起討論有哪些切片、屬於哪個領域、先做哪條 |
| `/domain-new-slice [切片代號或描述]` | 從地圖挑一條切片，建立資料夾，開始第 ① 步 |
| `/domain-step <1-6> [切片]` | 執行某一步：產出 → 挑錯 → 修正 → 自評 → 停下等審查 |
| `/domain-freeze <1-6> [切片]` | 人審查通過後凍結：寫 CHANGELOG、打 tag、合併進 `core/` |
| `/domain-expert-reply <EQ-nnn> <答覆>` | 處理專家回覆：比對影響、提出回頭方案 |
| `/domain-change <描述>` | 切片通過後發現特例或錯誤：判斷等級 0～3 並處理 |
| `/domain-check [切片]` | 轉出 `.build/` YAML，跑檢查工具與引用檢查 |
