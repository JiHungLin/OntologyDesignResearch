## 一、和其他文件的關係

```
Domain 交付物（規劃、①～④；只寫業務事實）
    │ 提供訊號（本指南第五節寫出每一項讀哪個欄位）
    ↓
《平台架構約定》P1～P13：任何選擇都要守住的約束
    │ 限制選項
    ↓
本指南 → 各 domain repo 的 architecture/DECISIONS.md 架構決定紀錄（ADR）
    │ 產生
    ↓
⑤ 對照表、schema、API → 實作 → ⑥
```

- **依賴的方向**（精簡版原則 1）：本指南讀 ①～④ 與切片地圖，不要求 ①～④ 寫技術措施。判斷時發現缺的是**業務事實**（例：上游改了、下游晚一點才重算，業務上能不能接受），照 0.9 回到該步補，補的仍是業務事實；不能為了技術方便要求改寫業務事實（例：為了少一次跨集合檢查合併兩個 Entity）。
- **和《平台架構約定》**：約定是約束與選項，本指南是在約束內選擇的方法。P2 的 A／B／C（和 S5 相關）、P3 物化與否（S4）、P6 落實位置（S1、S2）本身就是選型，約定保留原則與選項，「選了哪個」寫在架構決定紀錄。
- **和 Sean 的方法**：Sean 的設計到「與實作無關的契約」為止，刻意不做選型——D09 的元件是邏輯責任邊界、不是微服務或部署決定，D15 對照規則最後一條說實體 schema 與 API 協定刻意不凍結（`Sean:SeanHRSystemWay/D09_Component_Architecture_Prototype/D09_Prototype_Report_v1.0.txt`、`D15_Canonical_API_DB_Mapping_Prototype/D15_Mapping_Rules.md`）。具體選型是我們自己補的一層，不和 Sean 衝突。Sean 的報告提到的「Architecture Review Gate」（D05、D15 報告的狀態列寫還沒執行，D01、D09 報告的結論列為之後的步驟）是檢查 P01～P05 原型有沒有守住意思，對應我們 ⑤ 的對照表與 P8，**不是**本指南的架構決策關卡。

## 二、原則

1. **預設選最簡單的**；只有交付物讀得到訊號時才升級。
2. **訊號要寫出處**：ADR 的背景寫交付物的檔名與編號（例：`04_rules.md` R31），或寫「沒有訊號，用預設」。「這個方法很主流」「AI 說比較好」不是訊號（0.10「來源本身不是理由」）。
3. **偏好可以是理由，但要寫出來並列代價**：團隊熟悉度、使用者偏好是正當的理由，ADR 寫明「理由：偏好」，並和訊號指向的選項比較代價。HR 的資料庫只寫了「使用者選擇」，代價在 ⑤ 挑錯與實作時才一個一個出現（`HR:inputs/shared/範圍釐清_平台約定_第五步.md` 第 1 列；`he 05_mapping.md` D-15；`HR:impl/README.md`）。
4. **每個決定寫代價與重新評估的觸發**：觸發是之後哪個交付物出現什麼，就要重判（例：第一次出現跨部署單元的下游）。**代價寫它犧牲哪個品質屬性**：每一點開頭寫第六節 K11 九個名稱之一（例：「效能：同一雇主的公司規定改版要排隊重新判定」「可維護性：引用完整性要在 service 自己檢查」）；「沒採用的做法」的理由也寫那個做法犧牲了什麼（例：「PostgreSQL：可維護性，團隊不熟；理由：偏好」）。這樣同一個品質屬性被哪幾條 ADR 犧牲，關卡時查得到（第四節 4.1）。
5. **判斷有先後**：S7 和其他都不衝突、成本最低，可以最早定；S1 先於 S2（交易邊界影響資料庫的要求）；S6 和 S3 互相牽動（部署分開才需要非同步）；S5 幾乎一定帶出 S4。
6. **取捨對照品質屬性情境**（K11）：一條 ADR 讓某條情境做得到、卻讓另一條做不到（例：S3 選同一交易，連鎖的正確性有保障，送出的回應變慢），就是取捨點：寫進那條 ADR 的代價、引用兩條情境的編號，由架構負責人決定改 ADR 或接受。情境的目標值是 `未定` 時，取捨照寫、不量化，等 P13 有數字時重判。

### 4.1 用情境走 ADR（關卡的最後一步；K15 的輕量評估）

關卡判斷完 S1～S7 之後，用架構決定紀錄的「品質屬性情境」逐條檢查這組 ADR 撐不撐得住。取自 SEI ATAM 的做法（情境、敏感點、取捨點、風險），但不開工作坊、不建效用樹、不投票：AI 走一遍、寫進紀錄，有風險或取捨的才一題問架構負責人。

1. **列出影響每條情境的 ADR**：讀每條 ADR 的「決定」與「代價」，提到這條情境的品質屬性、或決定了這條情境走的路徑的都算（常見：正確性 → S1、S3；回應時間 → S3 同一交易或之後做、S4；排程或背景工作的時限 → S3、K10、S2 的交易限制；地端斷線、可攜 → S6、S7；故障後不遺失 → S3 outbox、S2、P1）。
2. **每一對標一種**，寫進情境的「走過的 ADR」：`ADR-nnn 支持`（照這條 ADR 做，情境做得到）；`ADR-nnn 風險：<一句>`（照這條 ADR 做，情境做不到或要額外的做法；例：交易有大小上限，一個雇主上千段僱傭關係要分批）。
3. **取捨點**：同一條 ADR 對一條情境支持、對另一條是風險 → 照原則 6 寫進那條 ADR 的代價，引用兩條情境的編號。
4. **處理風險**：每個風險一題問架構負責人——改 ADR（照複查第 3 點新增、舊的已取代）／加一條判斷 `K11` 的 ADR 補做法（例：分開工作佇列）／接受（那條 ADR 的代價寫「接受：QS-nn，<理由>」）。目標值 `未定` 的風險一樣寫，選「接受」時在 ADR 的重新評估觸發加「QS-nn 的目標值決定時」。
5. **沒有任何 ADR 走到的情境**：寫「沒有 ADR 處理」，同樣一題（常見是可用性、備份與還原：屬平台團隊 K13，寫「交給平台團隊，T18」也是一種答案）。

完成的樣子：每條情境的「走過的 ADR」有值；每個風險都有改、補或接受；取捨點都在 ADR 的代價裡。訊號複查新增情境時，只走那一條。

**試用安排**（分析 6.3 第 6 點，2026-11-03）：碳管理 `electricity-emission` 的 ⑤ 在關卡備好前已開始，當對照組（⑤ 自己決定平台的第二個樣本）；關卡在下一條先開始 ⑤ 的切片第一次試用。那之前要完成 T05、T06、T10（S1、S2、S7），S3～S6 可以用「暫定」過關。

### S1　Aggregate 與交易邊界（K04）

- **要判斷什麼**：哪些實例要一起檢查、一起改，兩個動作同時送出時要互斥（Aggregate，一致性邊界），每個 Aggregate 用什麼當鍵；一個動作碰到好幾個 Aggregate 時怎麼辦；跨 Aggregate、不寫入的判定與計算放哪裡（Domain Service）。Aggregate 是一個 Context（一個 domain repo，K03）內的邊界；切片不是邊界。
- **讀哪裡**
  - `04_rules.md` 規則表：「違反時」為 `擋下` 的規則；「規則」文字裡的範圍——「同一 X 的…」「任何一天最多一筆」「不重疊」「不重複」「合計不超過」「每一期…不能小於 0」，以及用到的 `` `Entity.attribute` `` 跨幾個 Entity；「套用對象」的每個事件都是要互斥的動作（不只建立，也包括更正、撤銷註銷，以及系統的背景工作、每日排程、連鎖觸發的動作——它們常和人的動作同時寫同一個 Aggregate，例：`ee 05_mapping.md` X-33、`alg 05_mapping.md` X-11）。
  - `04_rules.md` 守恆式：「套用對象」是檢查哪一筆，**不一定是範圍**；等號兩邊的項指到其他筆時（例：遞延進來的那一筆、分到這一期的帳單調整），範圍要包含它們。
  - `03_flows.md` 事件表：一個事件連帶改了什麼（重新判定、重算、轉 Superseded）；「觸發來源」是其他事件、而且一次影響很多筆的（例：公司規定改版 → 每段僱傭關係重新判定）。
  - `02_entities.md`：Entity 卡「身分」裡的唯一性（例：同一家企業內電號不重複）；關係表的「幾對幾」。「不能跟誰合併」只說明是兩個 Entity，不決定是不是同一個 Aggregate。
- **值得用的訊號**（每條 `擋下` 規則與守恆式各問一次）

  | 規則的樣子 | 判讀 |
  |---|---|
  | 只看單一實例（例：迄日不早於起日） | 不影響邊界；可以用 db constraint |
  | 同一範圍內多筆之間的關係（不重疊、最多一筆、合計、要平） | 這個範圍是一個 Aggregate，範圍內的寫入要互斥 |
  | 在很大的集合裡不重複（例：同一雇主在職者的員工編號） | 唯一性約束，不把整個集合放進一個 Aggregate；資料庫做不到唯一索引時，才鎖集合的鍵 |
  | 引用另一個 Aggregate 很少改的屬性（例：組織單位所屬的雇主） | 在交易裡讀來檢查，不用鎖 |
  | 違反時為 `提醒` | 交易之後再檢查也可以，不放進邊界 |
  | 判定、計算（違反時 `—`），讀好幾個 Aggregate、不寫入 | Domain Service |
  | 業務上要「整批一起」、而且「基準變了就過時」（例：採用改算建議要整個企業年度，基準計算變了就不能採用） | 範圍很大時不鎖整批：採用時確認每一筆基準都沒變（樂觀檢查），變了照 ④ 判過時（K06） |
  | 一個動作連帶改好幾個 Aggregate（例：更正到職日 → 重新判定特休；公司規定改版 → 每段僱傭關係重新判定） | 看「上游改了、下游晚一點才改」業務上能不能接受（S3）：不能接受、筆數少 → 同一交易一起鎖；筆數多 → 分批，並讓之後寫入那一筆的交易先補做；發起分批的交易也要更新每個受影響 Aggregate 的鎖——只寫待辦清單或佇列不算互斥，快照隔離下同時進行的排程仍會讀到舊資料（`alg 05_mapping.md` X-11） |

- **代價**：邊界大，同時寫入互相等待、重試；邊界小，跨 Aggregate 的 `擋下` 規則要另外互斥，或接受最終一致；範圍沒有對應的 Entity 時（例：同一人＋同一雇主），鍵是組出來的，⑤ 與程式都要寫清楚，否則新增的動作會忘了拿。
- **預設**
  - 以「`擋下` 規則與守恆式一起檢查的範圍」劃邊界，每個 Aggregate 寫出鍵。範圍沒有對應的 Entity 時，用範圍本身的鍵，**不為了技術在 ② 新增或合併 Entity**（原則 1）。
  - 同一個資料庫裡，一個動作碰到好幾個 Aggregate 時，可以在同一交易一起鎖（照固定順序拿）；跨部署單元（S6）或筆數多到一個交易做不完時，才分批或非同步（S3、K06）。
  - 跨 Aggregate、不寫入的判定與計算寫成 Domain Service：輸入是讀出來的事實與規則版本，可以單獨測試。
  - ADR 的「決定」逐一寫 Aggregate：名稱、鍵（根）、包含的 Entity、依據的規則與守恆式；「背景與訊號」依切片分段寫 `<切片>/04_rules.md Rnn、Cnn`，段與段用「；」分開。⑤ 第三區對到這些規則的列，「說明」寫靠哪個 ADR 防同時送出（《Domain設計輸入輸出規範》⑤，`lint.py` 檢查）。
- **K04 其他項目在哪裡**（不另外判斷）

  | DDD 的名詞 | 我們的對應 |
  |---|---|
  | Entity／Value Object | ② 六問：第 1 問「不需要分別認出 → 屬性」的屬性（例：地址、期間）與分類值，就是 Value Object 的候選 |
  | Domain Event | ③ 事件（K03） |
  | Repository | 每個 Aggregate 一個，整個取出、整個存回；是程式結構，不進 ⑤ 對照表；不預設成獨立的一層，見 S7；轉換規則見 T13 |
  | Domain Service | 見上；⑤ 第三區的落實位置寫 `service` |
  | Factory | ③ 建立 Aggregate 的事件與它的前提條件；不另外判斷 |
  | Specification | ④ 判定類規則與決策表；要不要做成可重用的規則物件或規則引擎，見第六節 K10 |

- **重新評估的觸發**：新增一條 `擋下` 規則或守恆式，範圍跨兩個既有的 Aggregate；某條規則從 `提醒` 改成 `擋下`；一個動作連帶改的 Aggregate 變多（例：雇主層級的設定影響每一位員工）；S6 把同一交易裡的 Aggregate 拆到不同部署單元；實作或 `signoff.md` 出現寫入衝突、鎖等待、寫入偏斜。

### S2　資料庫類型（K05）

- **要判斷什麼**：主資料庫用哪一類（關聯式、文件、圖、時序）；要不要另配一種當**附加的讀模型**（圖、時序、全文搜尋）。產品（例：PostgreSQL、MongoDB）寫在同一條 ADR 的「決定」，理由可以是偏好或維運條件（原則 3）。S1 先做：Aggregate 與「一個動作碰幾個 Aggregate」決定資料庫要提供什麼交易能力。
- **讀哪裡**
  - 初判（切片地圖同意後，還沒有 ①～④）：切片地圖「整體目標」的部署形態（地端時客戶那邊要能安裝、備份這種資料庫）、規模與尖峰；使用者或團隊對資料庫的偏好（問一題，有的話寫「理由：偏好」）。只寫候選、標 `暫定`。
  - 關卡（④ 凍結後）：
    - `04_rules.md` 規則表：「違反時」為 `擋下`、規則文字的 `` `Entity.attribute` `` 跨兩個以上 Entity 的規則（列編號）；S1 判讀裡「同一範圍內多筆之間的關係」與「引用另一個 Aggregate 的屬性」兩類。
    - `02_entities.md`「關係」表：幾對幾、有無期間；兩邊都是多的關係，以及經過一個有自己屬性的 Entity 連起來的（例：引用）。Entity 卡裡只屬於它、不被別處指到的屬性（帶期間的屬性、清單）。
    - `01_scope.md` 驗收問題的查詢形狀：期間切分、重疊、某個時點（範圍查詢）；跨很多筆的彙總（某年、某家全部）；更正前後；**長度不固定**的關係路徑（「A 經過幾層影響到 Z」）；依內容找資料（全文搜尋）。
    - `03_flows.md` 狀態機的「歷史需求」（`需要重建當時` → P2 A 版本化保存）。
    - S1 的 ADR：Aggregate 的大小、一個動作碰幾個 Aggregate、要不要分批。
- **值得用的訊號**

  | 讀到的樣子 | 判讀 |
  |---|---|
  | 跨 Entity 的 `擋下` 規則多（引用的東西要存在、兩邊的雇主要相同、日期要落在另一筆的期間內） | 偏關聯式：外鍵、複合外鍵、CHECK 能在資料庫擋一部分；文件型全部要在 service 寫 |
  | 驗收問題要期間切分、重疊、某個時點、跨很多筆彙總 | 偏關聯式（範圍索引、join、彙總）；文件型也做得到，跨集合時要多次查詢或聚合管線 |
  | 同一範圍內多筆之間的 `擋下`（不重疊、最多一筆、合計） | 不決定類型：兩類都要照 S1 防同時送出。關聯式多了資料庫層的選項（排除約束、可序列化隔離），文件型只能靠 S1 的鎖 |
  | 只屬於一個 Entity、不被別處指到的屬性多（帶期間的屬性、清單），讀寫都跟著主體 | 文件型的好處（嵌入，一次讀寫）；關聯式用子表或 JSON 欄位 |
  | 狀態機多為 `需要重建當時` | 不決定類型：版本表與版本文件都做得到（P2 A）。只新增要由資料庫擋時（P1、P2 A），關聯式可以用 trigger 與權限，文件型只能靠 service 與權限 |
  | 驗收問題問長度不固定的路徑 | 圖，當附加讀模型 |
  | 固定兩三層的關聯（例：用量 → 引用 → 佐證檔案） | **不是**圖的訊號：join 就夠 |
  | 依時間累積的高頻量測（每幾分鐘一筆、筆數以百萬計） | 時序，當附加讀模型 |
  | 依內容找資料、模糊搜尋 | 全文搜尋，當附加讀模型 |

- **代價**（ADR 照抄適用的幾條；選文件型時逐條判斷）
  - 文件型：
    1. 資料庫不檢查引用的東西存不存在：每個引用都由 service 檢查（同一個租戶也是）。
    2. 沒有跨文件的唯一或排除約束，也沒有可序列化隔離：同一範圍內多筆之間的 `擋下` 規則都要照 S1 另外鎖。快照隔離下，兩個交易各自讀到「沒有重疊」、各自新增不同文件，不會衝突（寫入偏斜）。
    3. 多文件交易是另外的能力：要特定的部署方式（例：MongoDB 要 replica set），而且有時間與大小上限；一個動作影響很多筆時要分批（S1 最後一列），比關聯式更早碰到。
    4. 沒有 trigger、索引條件有限制：只新增（P1、P2 A）只能靠 service 與權限；部分索引寫不出的條件要加快取欄位。
    5. ⑤ 的交付物 `schema.sql` 要改成別的格式（偏離《輸入輸出規範》的檔名），轉換規則要另寫一份。
  - 關聯式：模型改了要寫遷移（P12；文件型也要處理舊文件，只是資料庫不強迫）；帶期間的屬性與清單要拆子表、多 join；預設隔離等級下寫入偏斜一樣會發生，仍要照 S1 鎖，或改用排除約束、可序列化隔離。
  - 圖、時序、全文搜尋：通常另配、不當主資料庫——多一份資料要同步、會落後（S4 的代價），多一種資料庫要維運與備份（地端部署時在客戶那邊）。
- **預設**
  - 關聯式，一個主資料庫（P1 事件改狀態、P2 A 只新增、P5 規則版本、P6 落實位置，都可以在資料庫層再擋一道）。
  - 其他類型只在某一類驗收問題有明確訊號時加，當**附加的讀模型**：主資料庫是唯一的事實來源，附加的可以整個重建；落後的時間窗業務上可以接受（業務事實，由 ①③ 回答，S3）；寫明由誰同步。條件與做法照 S4。
  - 偏好文件型時照原則 3：「背景與訊號」寫「理由：偏好」，「沒採用的做法」寫訊號指向的類型，「代價」照上面文件型逐條寫適用的。
- **K05 其他項目在哪裡**（不另外判斷）

  | 項目 | 我們的對應 |
  |---|---|
  | temporal／bitemporal | 業務上的有效期間（② 帶期間的屬性）＋系統登錄的時間（P2 A 的版本、`as_of` 查詢，例：`alg 05_mapping.md` D-16）就是兩條時間軸；③ 的歷史需求決定要不要，不需要另一類資料庫 |
  | KV、快取 | 沒有 Domain 訊號；效能有證據時看 K11（T22），快取的身分照 P3 |
  | 全文搜尋 | 上表；附加讀模型 |
  | 分區 | 規模與尖峰有數字時（K11、T22） |
  | 保存與封存 | ④ 的保存期限規則與 P7；做法在資安線與 K13 |
  | polyglot persistence | 就是「附加讀模型」；兩個主資料庫不預設 |
  | ACID／BASE、CAP／PACELC | 由 S1（交易邊界）與 S6（部署單元）決定要什麼；單一部署、一個主資料庫時不另外判斷 |
  | schema 演進 | P12 |
  | 團隊熟悉度、維運成本 | 原則 3（偏好）；初判讀部署形態 |

- **重新評估的觸發**：驗收問題第一次出現長度不固定的路徑、全文搜尋或高頻量測（加附加讀模型，主資料庫不換）；選了文件型之後，跨集合的 `擋下` 規則或另外的鎖持續增加；實作出現交易超過時間或大小上限、要分批的動作變多；規模與尖峰有了數字；部署形態改變（例：多了地端）。

### S3　事件驅動與同步或非同步（K07）

- **要判斷什麼**：一個事件之後要做的處理（本切片內的連帶處理、其他切片掛在它上面的處理、送給外部系統），和事件**同一交易**做，還是**之後**做；之後做的用什麼機制（交易後的工作佇列、給其他切片或系統的訊息）、送達與重送怎麼保證；外部系統的資料怎麼進來。S3 不決定「晚一點才改，業務上能不能接受」——那是業務事實，由 ③④ 回答。
- **讀哪裡**
  - `03_flows.md`「事件」表：「觸發來源」為 `其他單位個體的變化`（連帶處理）、`外部系統或訊息`（外部資料進來）、`時間或條件到達`（排程）；「改變什麼」寫了一次改很多筆的（例：每段僱傭關係、每家企業）。「自動計算的範圍」這類說明寫的連帶範圍。
  - 業務上的時間窗：③ 的說明、④ 的規則有沒有寫「上游改了、下游晚一點才改」能不能接受（例：排程用舊到職日做年度終結不能接受；係數修正後背景重算期間舊計算仍是 Current 可以接受）。**交付物沒寫時照 0.9 回到 ③ 補**，補的是業務事實；不由架構或 ⑤ 審查頁代答。
  - `core/flows.md`「連鎖」、⑤ 的「其他切片事件的連鎖」（上一條切片已寫的）：哪些切片掛在哪個事件上、時機是 `同一交易` 或 `之後`。
  - `01_scope.md`「範圍外但會用到」、切片地圖「明確不做」：之後的切片或外部系統要接收或提供的東西（例：轉換交給薪資、碳權在外部交易平台完成）。
  - S1 的 ADR（連帶改的 Aggregate、筆數多要分批的）；S6 的 ADR（上下游在不在同一個部署單元）。
- **值得用的訊號**

  | 讀到的樣子 | 判讀 |
  |---|---|
  | 連帶處理在同一個部署單元，業務上**不能**接受晚一點才改（例：更正到職日 → 特休重新判定，否則排程可能用舊到職日做年度終結） | **同一交易**；跨切片時用掛勾：上游的動作呼叫，下游註冊（S6 的依賴方向），任一個失敗整個動作失敗 |
  | 連帶處理在同一個部署單元，筆數多到一個交易做不完（例：雇主層級的改變 → 每段僱傭關係重新判定；政府係數修正 → 每家企業重算） | **交易後的工作佇列**：發起的交易寫佇列並更新每個受影響 Aggregate 的鎖（S1 最後一列），之後每個 Aggregate 一個交易；業務上要接受這段時間窗，舊結果在處理完之前仍有效 |
  | 下游在之後的切片或另一個部署單元，可以延後，下游失敗不該擋住上游（例：特休轉換交給薪資） | **給其他切片或系統的訊息**（outbox）：和事件同一交易寫入，之後送出 |
  | 送給外部系統（政府申報、銀行、通知） | outbox；外部回應逾時是「結果不明」，不當成功也不當失敗，進對帳；外部失敗不回滾已成立的業務事實 |
  | ③ 觸發來源為 `外部系統或訊息`；之後要匯入外部資料（例：台電用電資料、外部交易平台的紀錄） | 外部資料**經本系統的登錄動作**（③ 的事件）才成為事實：見下方「外部資料進來」 |
  | 只是提醒或建議（建議層事件），不改事實 | 同一交易或之後都可以；要在回應裡馬上看到的同一交易 |
  | 一個事件掛的下游越來越多、上游交易變慢 | 把不需要同一交易的下游改成之後；仍要同一交易的，看能不能縮小範圍 |

- **之後做的兩種機制**（兩個試跑都各用了一次，名字不同）
  - **交易後的工作佇列**：本系統自己之後要做的工作（例：`alg` 的 `leave_reassessment_queue`、`ee` ⑤ 草稿的 `outbox_messages`）。一列一件工作，記觸發的事件、處理到哪裡、嘗試次數與最後的錯誤；寫入同一個 Aggregate 的交易先把它的佇列清掉（S1）。
  - **給其他切片或系統的訊息**（outbox）：別人要知道的事（例：`alg` 的 `LeaveConversionDetermined`）。只有下游確實存在或已規劃時才寫；「每個事件都寫一筆、沒有人讀」不預設。
- **送達的預設**（之後做的都適用；應用架構約定的候選，關卡寫在 S3 的 ADR，第一次有人讀時提升，T12）
  1. 和業務事實同一交易寫入；送不出去不回滾業務事實，留在佇列可以查（嘗試次數、最後的錯誤）。
  2. 至少送一次：會重送，所以**接收端要冪等**——以「來源事件編號＋處理種類」（或對象，例：每家企業）當鍵，處理過的跳過（例：`ee` ⑤ 草稿 X-39 的 `outbox_message_organizations` 與改算建議的唯一索引）。
  3. 重送不產生新的業務事件；接收端處理的結果才是新的事件。
  4. 順序只保證同一個 Aggregate（S1 的鍵）內；跨 Aggregate 不假設順序。要依賴順序的，回到 S1 看是不是邊界畫錯了。
  5. 訊息只帶編號、種類與下游需要的數量，不帶個資明文（P7；`he 05_mapping.md` 第五節 `outbox`）。
- **外部資料進來**（S7 的 adapter 只負責轉換）
  - 外部的紀錄、回應、編號不等於本系統的事實：經本系統的登錄動作（③ 觸發來源 `外部系統或訊息` 的事件，或人登錄的事件）才改狀態；不直接寫資料庫、不由 webhook 改狀態（P1）。
  - 原始資料保留當證據（例：佐證檔案）；外部編號存成對照，不當本系統的身分（P11）。
  - 外部重送用冪等鍵擋，不產生第二筆登錄；同一個冪等鍵帶不同內容的擋下。
  - 對不上（外部改了、內部沒改）用對帳找出，由擁有資料的領域決定要不要更正（P2 的更正動作），不自動覆寫。
  - 匯入和人工登錄走同一個事件：③ 不用為匯入另立事件，只在證據與「誰」寫來源。
  - 既有系統（客戶原本用的系統）的資料搬進來、或並行期間同步，也照這幾點：既有系統是 S6 附表一的外部系統，關係寫 K03（ACL 或 Conformist），逐步取代見 K14（T18）；系統開始管理前的業務事實怎麼補登由 ①～④ 決定（例：`he 03_use_cases.md` UC-11）。
- **代價**：之後做就有時間窗，業務上要說得出能接受；重送、冪等、順序、除錯都變難；佇列要有人看（卡住的工作、失敗的訊息）。同一交易：上游交易變大、變慢，下游的錯誤會讓上游的動作失敗；拆成不同部署單元（S6）時同一交易就不成立，要改 saga 或補償（K06）。
- **預設**
  - 同一個部署單元內，連帶處理**同一交易**；跨切片用掛勾，下游註冊。
  - 筆數多到一個交易做不完的，用交易後的工作佇列，照 S1 分批。
  - 跨部署單元、之後的切片要接收的、外部系統，用 outbox，照「送達的預設」。
  - ADR 的「決定」寫：同一交易的掛勾、工作佇列、outbox 各用在哪裡（列連鎖或事件），送達的預設與這個平台的例外；「背景與訊號」寫每個「之後」的時間窗依據（③④ 的編號）。

### S4　CQRS／讀模型（K08）

- **要判斷什麼**：查詢由寫入用的資料直接回答（推導值查詢時現算），還是另建一份給查詢用的資料（讀模型：物化的推導值、彙總表、另一個資料庫或索引）；建了的話，它的身分（P3 快取）、由誰在什麼時候更新（同一交易或之後）、怎麼重建。也要分清楚兩種不是讀模型的東西：**凍結快照**（P3：產生時寫一次的結果，例：已判定的轉換、一次排放量計算）是事實，屬 S5 與 ⑤ 第四區；**狀態欄位**由事件推出時是快取，但和事件同一交易寫入、不落後。S4 不決定推導值要不要有——那是 ② 的 `[推導]`；判斷是否物化仍照 P3「願不願意隨時把它砍掉重建」。
- **讀哪裡**
  - 初判（切片地圖同意後）：「整體目標」的規模與尖峰、部署形態；P13 目標值（架構決定紀錄第一區）。多數是「未定」，用預設。
  - 關卡（④ 凍結後）：
    - `01_scope.md` 驗收問題的查詢形狀：只看一個實例或一個 Aggregate 內的幾筆（例：一位員工某天有哪幾筆特休）；跨很多實例的彙總或清單（某家企業全部、某年度、跨企業）；報表或清冊；某個時點系統知道的（`as_of`，這一類屬 S5）。
    - `02_entities.md` 標 `[推導]` 的屬性：輸入在幾個 Aggregate、幾筆；是不是會被 `擋下` 規則拿來判斷（例：剩餘不能小於 0）。
    - `04_rules.md` 計算規則與守恆式：推導值怎麼算、改版時要不要重算。
    - `01_scope.md`「範圍外但會用到」與切片地圖：之後的切片會讀這裡的結果做彙總或報表（例：年度清冊）。
    - S1（推導值的輸入跨不跨 Aggregate）、S2（附加讀模型）、S6（輸入在不在同一個部署單元）的 ADR。
  - 訊號複查（之後每條切片 ⑤ 前）：上一條切片 ⑤ 第二區的查詢 API 與第四區推導值的身分，這條切片有沒有第一次跨很多實例的查詢。
- **值得用的訊號**

  | 讀到的樣子 | 判讀 |
  |---|---|
  | 推導值只讀一個 Aggregate 內的幾筆（例：一段僱傭關係的特休剩餘、一個電號一年的漏登） | 查詢時現算，不物化 |
  | 推導的結果要被引用、交給別的切片或外部，或要照當時的規則定案（例：已判定的轉換交給薪資、計算被年度清冊採用） | **凍結快照**（P3），是事實、不是讀模型；記當時的輸入版本與規則版本（P5、S5） |
  | 推導值被 `擋下` 規則拿來判斷 | 在同一交易現算（照 S1 鎖）；物化的快取不能當擋下的依據，除非它和寫入同一交易更新 |
  | 驗收問題跨很多實例或很多 Aggregate 彙總（某年、某家企業全部、跨企業） | 先在同一資料庫現算（彙總查詢、索引）；規模有數字、或實作量到超過 P13 目標時，才加物化的彙總表（P3 快取） |
  | 驗收問題問某個時點系統知道的推導值（`as_of`） | **不是**讀模型的訊號：從版本與規則版本現算（S5）；物化了也要能依版本重算 |
  | 推導值的輸入在另一個部署單元（S6） | 讀模型，由對方的事件或訊息更新（S3「送達的預設」），寫明落後的時間窗；同一個部署單元內讀對方模組的查詢入口就好 |
  | 讀寫量差很多、尖峰集中在查詢（例：年底盤查報表），而且有數字 | 讀模型；沒有數字不加 |
  | 驗收問題要全文搜尋、長度不固定的路徑、高頻量測 | S2 的附加讀模型 |
  | 法定或給外部的報表（申報檔、清冊） | 報表本身是凍結快照；產生時從哪裡讀見下方「報表與分析」 |

- **代價**
  - 加讀模型：多一份資料要同步，之後更新的會落後（時間窗要業務上能接受，S3）；更正、註銷、重新判定、規則改版時要一起更新——漏一處就和來源對不上（HR 不存剩餘的理由，`alg 05_mapping.md` D-06）；要有重建程式與 P9「快取砍掉重算，結果一致」的測試；身分照 P3 快取管理（只有重算程式寫、對不上以來源為準）。跨部署單元的讀模型另有重送、順序、冪等（S3）。
  - 不分、現算：跨很多實例的查詢會慢、寫起來複雜（彙總、`as_of` 要掃版本）；規則改版後每次查詢都照新的算——要照當時規則的結果，要做成凍結快照，不是讀模型。好處是判定與查詢共用同一段推導程式（S7 的 Domain Service），不會有兩份算法。
  - 完整的 CQRS（命令與查詢各一套模型、各一個資料庫）：上面兩點之外，再加 S6 的維運、最終一致、兩套 schema 的演進（P12）。
- **預設**
  - 不分；推導值查詢時現算（P3：推導值不存）；判定與查詢共用同一段推導程式。
  - 結果要被引用、交給別人、或要照當時規則定案的，做成凍結快照（事實），不算讀模型，寫在 ⑤ 第四區。
  - 加讀模型要三個條件都有：一、查詢形狀或規模有訊號（規模與尖峰、P13 有數字，或某個查詢實作量到超過 P13）；二、可以整個砍掉重建（P3 快取）；三、之後更新的話，落後的時間窗業務上能接受（①③ 回答，S3）。先用同一資料庫裡的物化表，不先分資料庫。
  - 狀態欄位由事件推出（例：`he` D-12 的 `status`）時，和事件同一交易寫入，仍要有重建程式與 P9 測試；做不到就把它寫成「事實，由動作寫入」，不寫成快取。
  - ADR 的「決定」寫：現算的範圍（列跨很多實例的查詢，寫「現算」）、凍結快照有哪些（指到 ⑤ 第四區）、讀模型（有的話：名稱、來源、同一交易或之後、重建方式、時間窗的依據）。
- **報表與分析**（2026-11-04 補，T21）
  - **要判斷什麼**：報表、清冊、統計這類跨很多實例的查詢用什麼回答——主資料庫直接查（彙總查詢加索引）；同一資料庫的物化彙總表；唯讀副本或報表資料庫（同一份 schema 複製出去分擔讀取）；分析資料庫或資料倉儲（OLAP：照分析的需要另建模型，由主資料庫單向送入）。先分清楚**報表的內容**和**查詢方式**：交出去、會被查驗或引用的報表（清冊、申報檔、盤查報告書）內容是業務上定案的結果，身分是凍結快照（P3）；它是不是 Entity、有哪些狀態、來源更正後要不要重交，由那條切片的 ②③④ 決定。這裡只決定產生它與日常查詢時從哪裡讀。
  - **查詢的種類**

    | 驗收問題問的 | 例子 | 用什麼回答 |

### S5　Event Sourcing 與歷史的保存（K09）

- **要判斷什麼**：每一類資料的歷史怎麼保存，才回答得出 ③ 的歷史需求與 ① 的時點、更正前後問題——版本化狀態（P2 A）、覆寫加變更紀錄（P2 B，變更紀錄記不記前後值）、直接覆寫（P2 C），或完整的 Event Sourcing（事件是唯一的事實，狀態都由重放事件得出）；狀態、版本、事件紀錄（P1）三者之間，**哪一份是「某個時點」的還原來源**；事件帶什麼內容。S5 寫平台的做法與 A／B／C 的分法，每個項目用哪個寫在 ⑤ 第四區（P2）。
- **讀哪裡**
  - 初判：不做（還沒有 ③）。團隊有 Event Sourcing 的經驗或偏好時，記在 S5 ADR 的背景，關卡再判斷。
  - 關卡（④ 凍結後）：
    - `03_flows.md` 每個狀態機的歷史需求（`只需現況`／`需要軌跡`／`需要重建當時`）與依據的 Q；「更正方式」表（同一筆、前一版保留／新的一筆指向舊的／註銷）；觸發來源為 `時間或條件到達` 的事件（依據的日期被更正時要重新推導）。
    - `01_scope.md` 驗收問題問的是哪一種歷史（下表「查詢的種類」）。
    - `02_entities.md` 的 `[推導]` 與它的輸入：推導的結果要回答某個時點時，**輸入也要能還原那個時點**。
    - `04_rules.md`：需要版本的規則（P5）、規則改版後要重算過去的（改算建議、重新判定）、法定的保存與刪除期限（P7）；② 可識別個人的屬性（P11 的資料性質）。
    - S2（資料庫能不能擋只新增）、S4（讀取要不要經投影）的 ADR。
- **查詢的種類**（`as_of`＝系統登錄的時間，`on`＝業務上的日子；Sean 的 TR0-03 把歷史查詢分成五種，對照見 K09 表）

  | 驗收問題問的 | 要保存什麼 | 用什麼回答 |
  |---|---|---|
  | 現在是什麼 | 現況 | C 就夠 |
  | 誰、何時、為什麼改的 | 每次改變的事件（誰、何時、理由、依據） | 事件紀錄（P1）；B 的變更紀錄只記改了哪些欄位就夠 |
  | 某一天（業務上）是什麼 | 帶期間的屬性 | ② 的期間，和保存方式無關 |
  | 某個時點系統知道的、更正前是什麼（`as_of`） | 每一版的內容與登錄時間 | A 的版本；或 B 的變更紀錄**記前後值**再倒推 |
  | 當時依哪一版規則 | 結果記規則版本 | P5 |
  | 用新規則或新數字重算過去、前後各多少 | 當時輸入的版本＋規則版本，重算的結果另存一份、舊的保留 | A 的輸入版本＋凍結快照（S4）；不需要重放事件。Sean TR0-11 的 replay 指的也是這件事：用當時的規則版本重新推出結果、和舊結果比差額，不是重放事件得出狀態 |
  | 狀態要依事件重新推出，而且推出的方式會改（事件本身是法定或業務上的紀錄，例：帳務的分錄） | 完整的事件序列 | 只有這一種是 Event Sourcing 的訊號 |

- **值得用的訊號**

  | 讀到的樣子 | 判讀 |
  |---|---|
  | 狀態機 `需要重建當時`，驗收問題問更正前後、某個時點 | A（版本化狀態）；**不是** Event Sourcing 的訊號 |
  | 狀態機 `需要軌跡` | B；變更紀錄記誰、何時、改了哪些欄位、哪個事件 |
  | `需要軌跡` 的資料被 `需要重建當時` 的推導或 `as_of` 查詢讀到（例：已休的固定資料 → 請假權利的 `as_of`；人的國籍 → 判定的 `as_of`） | 那份資料改用 A，或 B 的變更紀錄記前後值；只記欄位名稱回答不了（`alg 06_evidence/signoff.md` #11、`he 05_mapping.md` X-13） |
  | `需要軌跡`，但驗收問題也問某個時點的內容（例：`ee` 的佐證 Q04、Q09） | B 記前後值倒推，或改用 A |
  | 用新規則或新係數重算過去（例：`ee` Q07、Q08；HR 公司規定改版、天數表改版） | **不是** Event Sourcing 的訊號：輸入的版本（A）＋規則版本（P5），重算的結果是新的一筆或新版本，舊的保留 |
  | 註銷、撤銷註銷後要依其餘事件重算（`he` D-11、`alg` D-17），或狀態欄位是由事件推出的快取（`he` D-12） | 局部的重放：事件要帶得出重算需要的值，要有重建程式與 P9 測試（S4）；這是 Event Sourcing 代價的一部分，寫進 ADR |
  | 時間觸發的事件在依據的日期更正後要重新推導（`he` D-12 `derived`） | 推導的事件標 `derived`、可以失效；不是 Event Sourcing |
  | 大多數 Aggregate 的狀態只能從事件序列得出，業務上要依事件重新解讀 | Event Sourcing 的候選（上表最後一列） |
  | 可識別個人的屬性多、法定要能遮蔽（P7） | 反對事件或只新增的紀錄帶個資明文：事件與變更紀錄只帶參照，個資放在遮蔽得到的地方 |
  | 狀態機 `只需現況` | C |

- **代價**
  - 完整的 Event Sourcing（四項，ADR 照抄適用的）：
    1. **事件格式的演進**（P12）：事件是永久的事實，模型改了之後，每一個讀事件的投影都要能讀每一版的舊事件（版本化的事件格式、讀取時轉換）；P12 的「新屬性在舊資料上是未知」「拆、合概念用遷移事件」在事件上都要做。版本化狀態只要處理目前的 schema 與既有版本。
    2. **讀取都經投影**（S4）：查詢與 `擋下` 規則要的狀態都由事件投影出來；投影是 P3 的快取，要有重建程式與 P9「砍掉重算一致」的測試，非同步投影還有落後的時間窗（S3）。所以 S5 選 Event Sourcing 時，S4 一定要重判。
    3. **只新增和個資刪除衝突**（P7）：事件不能改，遮蔽就要另開路徑——事件只帶參照、個資放在可遮蔽處；或每個人一把金鑰、刪金鑰讓事件裡的個資讀不出來（crypto-shredding，資安線 T26、T28）。
    4. **學習成本**（團隊條件）：除錯、測試、資料修正、遷移都換一套做法；地端部署時客戶的維運人員也要懂；試跑由 AI 寫實作，產生的程式也要照同一套。ADR 的背景寫團隊數與經驗（S6 的團隊數那一題一起問）。
  - 版本化狀態＋事件紀錄（預設）：
    - 狀態、版本、事件**兩三份紀錄要對得上**；還原的來源沒寫清楚時，各切片各自從不同的紀錄拼湊，各自不完整（`alg` signoff #11：change_log 不記值，改從事件還原）。
    - A：版本多、查目前要條件索引或快取欄位（S2）；遮蔽要改每一份版本（P7）。
    - B 只記欄位：只回答「誰、何時、改了哪些」，回答不了某個時點的內容。B 記前後值：前後值裡可能有個資（`ee 05_mapping.md` D-29），倒推的查詢比 A 複雜。
    - 只新增由資料庫擋（S2 關聯式的 trigger）時，P7 的遮蔽要另開一條有權限、留紀錄的路徑。
- **預設**
  - **不採完整的 Event Sourcing**。照 ③ 的歷史需求分（P2 建議）：`需要重建當時` → A（每一版帶登錄時間與事件編號）；`需要軌跡` → B；`只需現況` → C。事件紀錄（P1）只新增，記誰、何時、理由、依據；狀態與版本是事實的來源，事件是軌跡。
  - **每個要回答某個時點的項目，只有一份還原的來源**：A 的版本，或記前後值的 B。ADR 寫明這個平台的 B 記不記前後值；不記的話，要回答時點的一律用 A，不從事件拼湊。
  - 推導的結果要重建當時時，沿 `[推導]` 的輸入逐一確認輸入也是 A 或記值的 B。
  - 事件帶編號、改了什麼的參照、數量、理由，不帶個資明文（P7）。要依其餘事件重算的（註銷）事件，要帶得出重算需要的值；這一點寫進 ADR 的代價，同一平台只用一種註銷的做法（應用架構約定，T12）。
  - 狀態欄位寫成「由事件推出的快取」時，照 S4 要有重建程式與 P9 測試。
  - 用新規則重算過去：輸入版本＋規則版本，結果做成凍結快照或新版本（S4），舊的保留。
  - ADR 的「決定」寫：A／B／C 的分法、B 的變更紀錄記什麼（欄位、前後值、個資怎麼處理）、時點由哪份紀錄回答、事件帶什麼、註銷的做法、只新增怎麼擋、P7 遮蔽的路徑。

### S6　部署單元與模組（K01）

- **要判斷什麼**：系統分成幾個部署單元（一起部署、一起升版的一套程式；monolith、modular monolith、microservices）；同一個部署單元裡程式模組怎麼分、每個集合或表由哪個模組寫入、模組之間誰可以依賴誰；多租戶模式（客戶的資料放在同一個資料庫加租戶欄，還是分開）。結果用 C4 的 Context、Container 兩層與一張模組表寫在 ADR 的附表（下方「附表的格式」）。S6 不決定交易邊界（S1）與同步或非同步（S3），但部署單元分開時，兩者都要重判。
- **讀哪裡**
  - 初判（切片地圖同意後）：
    - 切片地圖「整體目標」：要做的系統與對象（產品形態、客戶是誰）、明確不做（由外部或另一個系統完成的事 → Context 圖的外部系統）、**部署形態**（地端、雲端、混合；哪些資料要留在客戶端）、規模與尖峰。部署形態是 2026-11-03 加的欄（T03）；之前的地圖寫在「要做的系統與對象」或「決定與理由」（例：HR 的整體目標與 D-07）。
    - 切片地圖「領域」表（領域數 → 模組的候選）、「切片」表的依賴（哪些領域之間有上下游）。
    - 《平台架構約定》P11 識別範圍（切片地圖「決定與理由」或 ② D-01 的寫法）：哪些資料每家客戶各一份、哪些全平台共用（→ 多租戶模式）。
    - 團隊數：不在交付物；不知道就以「一個團隊」寫在 ADR 的背景，問 S6 那一題時一起確認。
  - 關卡（④ 凍結後；第一條切片只有一個領域時多半只是確認）：
    - `core/entities.md` 每個 Entity 的「出處」（哪條切片定義）與「層」；切片地圖「切片」表該切片的「主要領域」→ 擁有的模組。
    - `core/flows.md`「連鎖」與 ③ 事件「觸發來源」為 `其他單位個體的變化` 的：哪些領域之間有連鎖、要不要同一交易（S3 讀同一處）。
    - `01_scope.md` 驗收問題：有沒有跨客戶的查詢或彙總（多租戶模式）。
    - `01_scope.md`「範圍外但會用到」、③ 觸發來源 `外部系統或訊息`：Context 圖的外部系統（K03）。
- **值得用的訊號**

  | 讀到的樣子 | 判讀 |
  |---|---|
  | 部署形態有一部分在客戶地端、一部分在雲端（例：人事資料留在客戶端，雲端管授權） | **至少兩個部署單元**，界線就是部署形態寫的那條線；先看雲端那一部分是不是本平台的領域——「明確不做」或寫「屬平台」的，是另一個系統（Context 圖的外部系統），不在這個 domain repo 裡拆 |
  | 部署形態「可地端、也可雲端」（同一套給不同客戶） | 不是拆的訊號：同一個部署單元要能裝在兩處。代價是地端時資料庫、檔案存放、排程都在客戶那邊（S2「地端要客戶能維運」、S7 存放的 adapter） |
  | 兩個領域之間有 core 事件的連鎖，而且業務上不能接受「上游改了、下游晚一點才改」（例：更正到職日要和特休重新判定一起成立） | **反對**把這兩個領域拆成不同部署單元：拆了就要分散式交易或補償（K06），不能同一交易 |
  | 某個領域的規模、尖峰或可用性目標和其他領域差很多（規模與尖峰、P13 有數字） | 可以把那個領域拆成獨立部署單元；沒有數字不拆 |
  | 第二個團隊加入，要各自決定升版時間 | 可以依領域拆；一個團隊不拆（Conway 定律：拆的界線跟著團隊） |
  | 多個領域、切片很多 | **不是**拆的訊號：用模組分，不用部署單元分 |
  | P11 每家客戶各一份、另有全平台共用的參考資料（例：司法管轄區、政府公告的係數） | 多租戶用**共用資料庫加租戶欄**：共用的參考資料只有一份，不用每家各複製 |
  | 驗收問題或背景工作要跨客戶（例：新係數公告後列出各企業受影響的計算） | 同上，而且反對每家一個資料庫：跨客戶要逐一連線 |
  | 客戶要求資料實體分開（合約、法規、地端安裝） | 地端：每家一套部署，程式仍帶租戶欄（同一套程式也能在雲端用）；雲端要分開的：每家一個 schema 或資料庫，寫明是哪個客戶的要求 |

- **代價**
  - 拆成多個部署單元：原本同一交易的連鎖要改成非同步或 saga（S3、K06），業務上要能接受時間窗；跨單元的查詢要經 API 或讀模型（S4）；維運、監控、升版要協調、API 要相容（K13、K14）。依領域拆時，一個 Context 變成多個：`core/` 的 core、shared 層要決定是 Shared Kernel 還是某一邊的上游，原本 Context 內的連鎖變成 Customer–Supplier（K03）。
  - modular monolith：模組界線沒有部署擋著，靠約定與檢查守住——寫入別的模組的集合、上游模組 import 下游模組，在同一份程式裡都做得到，要有人看（HR 判讀例子有兩處）。整個系統一起升版、一起停機。
  - 共用資料庫加租戶欄：每個查詢、每個引用都要帶租戶並比對（S2 文件型第 1 點；關聯式可用含租戶的複合外鍵在資料庫擋）；漏一處就跨客戶讀到資料（資安線）；單一客戶的還原、搬遷要按租戶篩。每家一個 schema 或資料庫：共用的參考資料要複製或另放一處、遷移要跑 N 次、跨客戶的查詢與背景工作要逐一連線。
- **預設**
  - **一個部署單元（modular monolith）**；部署形態要求分開的，界線照部署形態。拆的界線依部署形態或領域，**不依切片**（K03：切片是工作單位，一條切片常碰到多個領域）。這裡的模組是同一份模型內的程式分組；精簡版 0.3 不採用的「分模組」是各模組各自定義名詞，兩者不同。
  - **模組**：每個領域一個模組，加一個**平台元件**模組。平台元件放 P1～P13 落實的共用機制（事件紀錄、outbox、變更紀錄、規則版本、多語名稱、「今天」的入口、排程紀錄、稽核、個資處理紀錄）、租戶與帳號、P11 寫明全平台共用的參考資料。
  - **每個集合或表只有一個擁有的模組**，只有它寫入：Entity 屬於定義它的切片（`core/entities.md`「出處」）的主要領域；技術表屬於落實它的模組。其他模組可以讀 core、shared 層的 Entity（同一交易內），domain 層的只由自己的模組讀，別的模組要用時經它的查詢入口。別的模組要改它擁有的資料，經它的動作，或由它聽 core 事件。`[靜態替代]` 照 S7 換法一換成真功能時，擁有者換成取代它的切片的模組（寫在附表）。
  - **依賴方向**：下游領域的模組可以依賴上游（切片地圖「依賴」），上游不 import 下游；下游掛在上游的動作上時經 core 事件連鎖（掛勾），由下游註冊。所有模組都可以依賴平台元件，平台元件不依賴領域模組。這和 `core/` 的 core／shared／domain 依賴方向是同一個方向。
  - **多租戶**：共用資料庫加租戶欄；地端時每家一套部署，程式不變。
  - Context、Container 兩層一定寫；Component 層就是模組表，不另畫圖。拆成多個部署單元時，每個單元畫一張 Component 圖（哪些模組在哪個單元、單元之間經什麼 API 或事件）。

- **重新評估的觸發**：部署形態改變（例：第一個地端客戶、雲端多了一部分）；第二個團隊加入；某個領域的規模或可用性目標和其他領域差很多；第一次出現「上游改了、下游晚一點才改」業務上可以接受、而且上下游要分開部署的連鎖；P11 的識別範圍改變（例：人改成全平台一份）或客戶要求資料實體分開；另一個領域的切片要寫入既有模組擁有的資料（換擁有者，或改經它的動作）；實作出現寫入別的模組的集合、上游 import 下游。

### S7　分層（K02）

- **要判斷什麼**：④ 的規則與判定要不要和資料庫、框架隔開；靜態替代與外部來源之後換成真的東西時，程式改哪裡（Hexagonal／ports and adapters、Onion、Clean）。這是原則 6（概念先存在、實作可以先用替代品）在程式層的對應：② 讓「引用它的地方不用改」，S7 讓「讀它的程式不用改」。
- **讀哪裡**
  - `01_scope.md`「範圍外但會用到」：「本切片怎麼處理」為 `[靜態替代]` 的列，與「歸屬的切片」（之後由誰取代）。
  - `02_entities.md`、`core/entities.md`：標 `[靜態替代]` 的 Entity 與屬性；屬性同時標 `[推導]` 的（之後改由別的事實推出）。
  - `03_flows.md`：事件「觸發來源」為 `外部系統或訊息` 的事件；「其他說明」寫外部來源這版怎麼處理。
  - `04_rules.md`：判定與計算（「違反時」為 `—`）的數量；`P5` 規則版本與參數依管轄區或客戶不同的。
  - 切片地圖「整體目標」：最後要套用的範圍（例：其他國家）、部署形態、「明確不做」中由外部完成的事；P11 資料存放。
  - 初判就能讀（地圖）；關卡時用 ①～④ 確認。
- **值得用的訊號**

  | 讀到的樣子 | 判讀 |
  |---|---|
  | `[靜態替代]` 是別的切片之後會建立的主檔或參數（例：雇主、組織單位、工資給付日） | **換法一**：替代品是先載入同一份資料（同一個集合或表，形狀照 ⑤），之後換寫入的一方；讀的程式不改 |
  | `[靜態替代]` 之後要改由別的事實推出（屬性同時標 `[推導]`；例：已休天數之後由請假事實推出） | **換法二**：替代品是固定資料＋**一個讀取入口**；之後只改這個入口，停用固定資料的寫入；其他程式不直接讀固定資料 |
  | `[靜態替代]` 是別的切片之後會發出的事件（例：一般離職的結束日） | **換法三**：固定資料用一個事件載入，下游聽 core 事件的種類（`core/flows.md`「連鎖」），不聽固定資料事件的名稱；之後上游改發真的事件 |
  | ③ 觸發來源有 `外部系統或訊息`；地圖「明確不做」由外部完成、系統只記錄 | 外部來源經 port：外部資料經本系統的登錄動作（③ 事件）才成為事實，adapter 只負責轉換（外部資料進入的原則見 S3「外部資料進來」） |

  | ④ 判定與計算多；目標要套用其他國家，規則版本與參數依管轄區 | 判定寫成 Domain Service（S1）：輸入是讀出來的事實與規則版本，不在判定裡查資料庫，沒有資料庫也能用黃金案例與守恆式測（P9） |
  | 只有人工登錄、沒有靜態替代、沒有外部來源 | 不另外設 port；只做「判定不碰資料庫」 |

- **代價**：介面與轉換變多，簡單的資料維護也要經過好幾層；判定前要先把事實讀齊，容易一次讀太多或漏讀（讀的範圍要和 S1 的 Aggregate 一致）；對小型 CRUD 過度。換法一的前提是真的切片沿用同一份資料的形狀，要改形狀時就是跨切片修改（精簡版 0.9）。
- **預設**：輕量的 ports and adapters——
  - ④ 的判定與計算不依賴資料庫與框架：先讀出事實與規則版本，再交給判定（Domain Service，S1）。
  - 每個 `[靜態替代]` 照上表三種換法之一；固定資料的讀取不散在各處。
  - 外部來源與檔案、存放經 port；這版沒有外部來源的不先建。
  - Repository 不預設成獨立的一層：讀寫資料庫的程式依 Aggregate 集中（S1）；有第二種存放方式的訊號才抽成介面。Onion、Clean 的完整分層不預設。
  - ADR 的「決定」寫上面幾點與這個平台的例外；每個 `[靜態替代]` 用哪種換法，在判讀時寫進 ADR 的附表（標題 `#### ADR-nnn 附表一　靜態替代的換法`，欄位：`[靜態替代]`｜誰取代｜換法｜換的時候改哪裡，同下方 HR 判讀表的前四欄；⑤ 不另外寫，2026-11-03 使用者選擇題）。

## 六、判斷表之外的類別

第三節去處為「指南只列選項」的類別寫在這裡：不設關卡，寫對照或選項、讀哪裡、值得用的訊號、代價、預設、重新評估的觸發與判讀例子，給第五節的判斷與 ADR 引用。有外部關係或決定要記時，ADR 的「判斷」寫該類別的 K 編號。目前有 K03、K10、K11；K06、K14 由 T19、T18 補。去處為「平台團隊」的類別不展開做法，只寫和 Domain 交付物、α 的步驟接在哪裡：目前有 K13 的環境部分。

### K03　DDD 戰略層：切片、領域、`core/` 對應什麼

- **要判斷什麼**：系統有幾個 Bounded Context（一份模型、一套詞彙適用的範圍），和外部系統或其他平台是哪種關係（Context Map）。用途是讓 S6、S7 與應用架構約定（T12）用對名詞：不把一條切片當成一個 Context，不把 `core/` 當成幾個服務共用的資料庫。
- **對照**

  | DDD 的名詞 | 我們的對應 | 對得上嗎 | 我們文件的位置 |
  |---|---|---|---|
  | Bounded Context | 一個 domain repo（一個平台）：一份 `core/`、一份詞彙對照表 | 對得上。「同一個概念只能有一份定義」「Person 在不同領域只是投影」是同一個 Context 內的規則；HR 與碳管理各自定義 Person／Organization、各一份紀錄，是兩個 Context | 精簡版 0.3「共用核心內部再分三層」、0.5「平台」；`core/glossary.md` |
  | Subdomain（問題範圍的劃分） | 切片地圖「領域」（例：人資／請假） | 對得上 | 精簡版 0.3 名詞表；`slices/PLAN.md`「領域」 |
  | Module（同一個 Context 內的程式分組） | 領域，加上 core／shared／domain 的依賴方向 | 部分：「領域」在設計上只用來分類，不各自定義名詞；程式依領域分模組是 S6 的預設 | 精簡版 0.3；本指南 S6 |
  | （沒有） | 切片 | **不對**：切片是交付的工作單位，沒有自己的模型，一條切片常碰到多個領域（`slices/PLAN.md`「會碰到的領域」）。不依切片拆 Context、模組或服務 | 精簡版 0.3「一條切片多大」 |
  | Shared Kernel（兩個 Context 共有、一起修改的一小塊模型） | 目前沒有 | **不對**：`core/` 的 core、shared 層在同一個 Context 裡，表示依賴方向，不是兩個 Context 共有。只有拆成兩個 Context 時才會出現（S6 依領域拆部署單元，或兩個平台決定共用某些名詞） | 精簡版 0.3 三層表；分析 6.3 第 1 點 |
  | Core／Supporting／Generic Subdomain（依業務價值分） | 沒有對應 | **不對，而且撞名**：我們的「core 層」是每種系統都會碰到的概念（Person、Organization），依業務價值反而多屬 Generic | 精簡版 0.3 三層表 |
  | Ubiquitous Language | 詞彙對照表與英文識別名稱 | 對得上，一個 Context 一份 | `core/glossary.md`；《平台架構約定》P10 |
  | Domain Event | ③ 事件 | 對得上（Context 內；交易邊界屬 S1） | `03_flows.md`「事件」；`core/flows.md` |
  | Context 之間的上下游（Customer–Supplier） | 切片之間的連鎖與其他切片要求修改 | **不對**：同一份模型內的上下游，靠同一份 `core/` 與審查處理，不需要轉換。依領域拆成不同部署單元後才變成 Customer–Supplier | 精簡版 ⑤「其他切片事件的連鎖」、0.9「其他切片要求修改」；`core/flows.md`「連鎖」 |
  | Conformist、Anti-Corruption Layer、Open Host Service／Published Language | 本平台和外部系統、其他平台之間的關係 | 對得上，但沒有集中寫的地方：散在切片地圖「明確不做」與「決定與理由」、① 範圍外但會用到、③ 觸發來源 `外部系統或訊息` | 下方「讀哪裡」；有關係要記時寫 ADR（判斷 `K03`） |
  | Anti-Corruption Layer 的實作 | S7 的 adapter | 部分：ACL 是 adapter 中要翻譯外部模型的那一種。`[靜態替代]` 的對象是本平台之後的切片時，換成真功能只換 adapter，不是 ACL | 本指南 S7 |

  **Sean 的用法不同**：D01 原型把 143 個 canonical entity 分在 15 個 bounded context，同時檢查整份沒有重複的 canonical ID（`Sean:SeanHRSystemWay/D01_HR_Canonical_Domain_Class_Diagram_Prototype_v1.0/D01_Prototype_Report_v1.0.txt`）——那是同一份模型內的分組，對到我們的「領域」，不是各自有模型的 Context。讀 Sean 的材料時，把那裡的 bounded context 讀成「領域」。9/18 會議的開放問題提到實作層仍要有邊界管理（`Sean:Sean會議記錄/20260918/sean_ontology_20260918_會議總結.md` 開放問題第 4 點），由 S6 的程式模組回答。
- **讀哪裡**
  - 切片地圖「整體目標」：「明確不做」中由外部或平台完成的事、「部署形態」；「決定與理由」中處理外部系統的決定。
  - `01_scope.md`「範圍外但會用到」：歸屬不是本平台切片的列。
  - `03_flows.md`「事件」：觸發來源為 `外部系統或訊息` 的事件。
  - `02_entities.md`：定義或身分取自外部的 Entity（法規、公告、其他系統的編號）；「不能跟誰合併」的討論中，同一個詞在兩個領域要兩種意思的情況。
- **值得用的訊號**
  - 有外部系統或其他平台提供或接收資料 → 寫出關係：外部的定義照用、對方不會為我們改（政府公告、法定格式、交易平台的編碼）→ Conformist，經 port（S7）；外部的模型和我們的不同而且會變 → ACL；對方是我們能要求修改的團隊 → Customer–Supplier；我們提供給多個外部使用 → Open Host Service／Published Language（⑤ `api.yaml`）。
  - 同一個詞在兩個領域要兩種意思，照 0.3 的投影也併不起來 → 可能是兩個 Context。不在 `core/` 裡硬併，回到 S6 判斷。
- **代價**：多一個 Context，就多一份模型與詞彙、多一層轉換與同步；Shared Kernel 要兩邊一起改；Conformist 讓外部改版直接改到我們的模型；ACL 多一層要維護的轉換。反過來，一個 Context 太大，同一個詞被迫只有一種意思、模組之間耦合高。
- **預設**：一個 domain repo 一個 Context；領域是子領域，也是程式模組的分法（S6）；切片不是 Context。和外部的關係：照用外部定義的寫 Conformist、經 port；要翻譯的寫 ACL。不另畫 Context Map，有外部關係要決定時寫一條 ADR（判斷 `K03`）。
- **重新評估的觸發**：S6 改成依領域拆部署單元；兩個平台決定共用某些名詞（分析 6.3 第 1 點改變）；同一個詞在兩個領域併不起來；第一次設計外部系統的匯入或輸出；第二個團隊加入。
- **判讀例子**

- **代價**
  - **函式**：規則的條件改了要改程式、部署；④ 的決策表和程式各一份，可能不一致（靠黃金案例與每一列的測試）；版本要自己傳進函式（忘了傳就會取到最新版）。
  - **決策表執行器**：④ 的表要轉成執行器的格式（運算式語言），表裡的「資料不足」「不可能」「[待專家確認]」與跨規則的引用（例：碳 R17 用 R18 選出的年度）轉換時容易改掉意思（同 ⑤「型別不改變意思」）；版本要和 P5 的規則版本綁在一起；多一個依賴與一種語言。
  - **規則引擎**：推理順序不透明，測試與除錯難；結果的解釋要另外做；P5 的版本、P3 的凍結快照、P1 的事件都要自己接；團隊要學。
  - **工作流引擎**：流程的狀態存在引擎裡，和 ③ 的狀態機是兩份；流程改版時進行中的實例怎麼遷移（P12）；地端每家一套要安裝、升版、監看。
  - **排程框架**：多一個元件；地端每家一套。
- **預設**
  - ④ 的判定與計算寫成函式（Domain Service，S1、S7）：輸入是事實、規則版本與參數（依 P5 選出、由呼叫的一方讀好傳入），輸出是結果代碼與依據（用到的版本與輸入、缺什麼）；函式裡不查資料庫、不取現行版本。
  - 每張決策表一個函式，條件與結果照 ④ 的表（可以寫成表格資料再查表，列的順序照 ④）；程式註明對應的 ④ 決策表標題；測試每一列一個案例（含資料不足；「不可能」的列測它被前面的規則擋下）。逐列測試與程式指回決策表是 P9 必須自動的檢查。
  - 參數照 P5 與 ⑤「參數放在哪裡」；值改不改程式。
  - 人工步驟用 ③ 的狀態與事件；不用工作流引擎。
  - 排程：平台的排程器每天呼叫一支程式，同一時間只排一份；做法照應用架構約定的排程條目；觸發、警示與監看照 K13。
  - 照預設時不寫 ADR；要導入決策表執行器、規則引擎、工作流引擎或排程框架時，寫一條 ADR（判斷 `K10`），背景寫上表的哪一個訊號、出處。

### K11　品質屬性：情境、模式與取捨

- **要判斷什麼**：這個平台要守住哪些品質屬性、守到什麼程度（寫成**品質屬性情境**），以及要不要為了某條情境加 timeout、retry、circuit breaker、限流（rate limit）、分開資源（bulkhead）、快取這類模式。情境也是第二節原則 4、6 與第四節 4.1 的對照：沒有情境時，S4、S6 的觸發只能寫「規模有數字」「量到超過 P13」，沒有人知道什麼時候算到了。
- **已經決定、不在這裡重判的**

  | 項目 | 我們的對應 | 位置 |
  |---|---|---|
  | 目標值（回應時間、可用性、併發與尖峰、備份與還原） | 平台負責人決定，寫在架構決定紀錄「P13 目標值」；什麼時候必須填照 P13 | 《平台架構約定》P13；精簡版 0.5 |
  | 規模與尖峰、部署形態 | 切片地圖「整體目標」，產品的事實，規劃時必問、不知道寫「未定」 | 精簡版 0.3；P13 |
  | 同時送出、重跑、失敗時規則仍成立 | 鎖（S1）；同一交易、工作佇列、outbox、冪等（S3、K06）；排程的做法（應用架構約定的排程條目） | S1、S3 |
  | 快取、讀模型 | P3 快取；S4 讀模型三個條件 | S4 |
  | 環境、備份、監控、部署的做法 | 平台團隊；介面見 K13 | K13 |
  | 資安 | ADR「資安影響」；《資安設計指南》 | γ |
  | 算得對不對（功能適合性） | ① 驗收問題、⑥ 黃金案例與驗收 | α，不在本指南 |

- **品質屬性的名稱**：情境與 ADR 的代價（原則 4）都只用這九個。

  | 名稱 | 意思 | ISO/IEC 25010 |
  |---|---|---|
  | 正確性 | 同時送出、重跑、失敗、延後處理時，④ 的規則與守恆式仍成立 | 功能正確性；可靠性 |
  | 效能 | 一個動作或查詢的回應時間、一段時間內處理完的量 | 效能效率 |
  | 可擴展 | 客戶、資料或尖峰變大時，不改架構撐得住多少 | 效能效率（容量） |
  | 可用性 | 要用的時候能用；計畫停機、故障、斷線時還能做什麼 | 可靠性（可用性） |
  | 可靠性 | 故障或中斷後不遺失、不重複，能恢復（含備份與還原） | 可靠性（容錯、可恢復性） |
  | 可維護性 | 規則或模型改了要改幾處、測不測得到、下一條切片接不接得上 | 可維護性 |
  | 可攜性 | 地端、雲端、混合都能裝；換存放方式或外部系統 | 可攜性 |
  | 資安 | 見 γ；ADR 的「資安影響」 | 資訊安全 |
  | 成本 | 建置、維運、授權、每多一家客戶多出的成本 | 不在 25010（Richards、Ford 的 architecture characteristics 有） |

- **情境的寫法**：一條一列，寫在架構決定紀錄第一區的「品質屬性情境」表（格式見《Domain設計輸入輸出規範》「架構決定紀錄」）。

  | 欄位 | 寫什麼 | 從哪裡來 |
  |---|---|---|
  | 編號 | `QS-nn`，依新增順序遞增，不重排、不重用 | — |
  | 品質屬性 | 上表的名稱，一到兩個 | — |
  | 當…（發生什麼） | 業務上發生的事：誰、做了什麼、多少（例：曆年制的雇主在 1 月 1 日全體員工同時取得特休）。數量讀地圖的規模，沒有寫「規模未定」 | 切片地圖、①～④（業務事實） |
  | 在…時（環境） | 平常、尖峰（地圖寫的尖峰時段，或 research 的法定期限）、故障、規則改版或升版、地端斷線 | 同上 |
  | 系統要… | 完成什麼、不能發生什麼（例：每段僱傭關係各給予一次，失敗的不擋其他人） | ①～④、ADR |
  | 在…內 | 時間、比例或次數；沒決定寫 `未定`。正確性的情境寫次數（例：0 次違反 C01），量測靠 P9 的守恆式檢查（全部測試資料） | 平台負責人（P13） |
  | 依據 | 地圖、交付物的檔名與編號、research | — |
  | 走過的 ADR | 關卡時填（第四節 4.1）：`ADR-nnn 支持`、`ADR-nnn 風險：<一句>`、`沒有 ADR 處理` | 架構負責人 |
  | 狀態 | `草稿`（AI 提出）／`確認`（平台負責人同意）／`已取代: QS-nn` | — |

  - 「當…」「在…時」是業務事實，讀不到的寫 `未定`，不由 AI 推想數字（和地圖「規模與尖峰」同一條規矩）；推想的尖峰（例：自願盤查也集中在法定期限前）寫「推想」並一起問。「在…內」是平台的目標，不回寫到 ①～④（單向依賴）。
  - 一個平台 3～6 條，至少涵蓋：尖峰時的效能或可擴展、會碰到鎖或連鎖的正確性、時間觸發或背景工作在時限內做完、故障後不遺失與恢復；地圖有部署形態的加可攜或斷線，有規則版本的加改版。只寫會影響選型的，畫面多快打開這類不寫。
  - P13 四列的「目標」寫 `見 QS-nn`（回應時間、併發與尖峰對到效能、可擴展的情境；可用性、備份與還原對到可用性、可靠性的情境）；沒有對應情境的那一列照 P13 直接寫目標或 `未定`。

- **讀哪裡**：切片地圖「整體目標」（要做的系統與對象、部署形態、規模與尖峰）與「決定與理由」中的產品決定；`01_scope.md` 驗收問題中跨很多實例或有期限的；`03_flows.md` 事件觸發來源 `時間或條件到達` 與決策流程；`04_rules.md` 有期限或時間窗的規則、版本欄、參數表；已做過 ⑤ 的，第二區時間觸發事件與背景工作、「決定與理由」中的分批與鎖；research 的法定期限；`signoff.md` 中和量、時間、交易大小有關的設計問題。
- **值得用的訊號**（模式）

  | 讀到的樣子 | 判讀 |
  |---|---|
  | 情境的「在…內」有數字，實作量到達不到 | 回到那條情境「走過的 ADR」，照那條 ADR 的重新評估觸發重判（例：S4 先加物化彙總表、S6 把那個領域拆出去）——S4、S6 寫的「量到超過 P13」指的就是這個 |
  | 呼叫外部系統（③ 觸發來源 `外部系統或訊息`、S7 的 adapter），對方慢或停了不能拖住日常動作 | 每個外部呼叫設 timeout；只重試冪等的（S3）；對方常停、而且有可用性的情境時才加 circuit breaker |
  | 排程或背景工作要在某個時間前做完 | 每個對象一個交易、失敗的不擋其他（應用架構約定的排程條目、S3）；量有數字時才平行或分批（例：`alg` D-18）；和日常動作搶資源而且有數字時，排程與背景工作用分開的佇列與連線（bulkhead） |
  | 共用資料庫加租戶欄（S6），一家大客戶的量會拖慢其他客戶 | 規模有數字、客戶大小差很多時才依租戶限流或分開佇列；沒有數字不做 |
  | 上傳檔案、大量匯出 | 大小與筆數上限（也是 γ 攻擊者第 5、6 題）；超過的改成背景工作 |
  | 同一份資料一直被讀、算起來很貴 | 快取照 S4 三個條件（P3 快取、可重建、時間窗業務上可接受）；不當判定與擋下的來源 |
  | 資料庫的交易有大小或時間上限 | S2 的代價；影響很多筆的動作分批（例：`alg` D-18） |
  | 可用性的目標高於一台資料庫給得到的 | 複本與自動切換屬平台團隊（K13）；選型上只看 S2 選的資料庫支不支援 |
  | 地端每家一套、和雲端平台斷線 | 地端的日常動作不依賴雲端（S6 的部署界線）；斷線多久仍能用是產品決定，寫成可攜或可用性的情境 |

- **代價**：情境要有規模與尖峰才量化得了，沒有數字時只能當檢查清單；寫太多，關卡逐條走就沒人看。每加一個模式（circuit breaker、限流、分開資源、快取）就多一個元件與一種失敗方式，而且要測。
- **預設**
  - 規劃後初判時，AI 依切片地圖與已有的交付物寫 3～6 條情境，狀態 `草稿`，「在…內」除非平台負責人已給數字都寫 `未定`；一題問平台負責人整組確認或修改，同意的改 `確認`。AI 不補數字。
  - 模式：每個外部呼叫與資料庫呼叫設 timeout；只重試冪等的；排程與背景工作每個對象一個交易、失敗的不擋其他；上傳與匯出有上限。不加 circuit breaker、限流、快取、唯讀副本，直到某條情境有數字而且量到達不到。
  - 照預設不寫 ADR；為了某條情境導入模式或元件時，寫一條 ADR（判斷 `K11`），背景寫情境編號與量到的結果。

    | QS-05 平台發布新的規則版本（參數值改），不改程式就生效，已有計算照 R19 沿用當時的版本（`ee 04_rules.md` 參數表、R19、`05_mapping.md` D-25） | 可維護性、正確性 | K10 預設（函式接收規則版本）→ 支持；實作 `calc.ruleset()` 取最新版 → 風險（T20 比對發現） |
    | QS-06 資料庫或物件儲存要還原，佐證檔案和紀錄一起還原、`file_sha256` 對得上（`ee` R36、`05_mapping.md` Evidence.file） | 可靠性 | S2（關聯式＋物件儲存）→ 取捨點：兩處要一起備份與還原，寫進 S2 的代價；RPO、RTO → 沒有 ADR 處理（K13、T18） |
  - 兩個試跑的共同觀察：走一遍找到的風險，多數已經在 ⑤ 挑錯或實作時出現過（`alg` D-18 分批、碳 R25、`calc.ruleset()`）——情境能在關卡就把它們排在同一張表上；沒有任何 ADR 處理的都是「斷線多久」「備份與還原」，前者是產品決定、後者屬平台團隊。
- **延伸閱讀**：ISO/IEC 25010；SEI 的 Quality Attribute Scenarios 與 ATAM（Bass、Clements、Kazman《Software Architecture in Practice》）；Richards、Ford《Fundamentals of Software Architecture》（architecture characteristics）；Nygard《Release It!》（timeout、circuit breaker、bulkhead）。

### K13　營運環境：分級、隔離，和 ⑥ 驗證環境的關係（只寫環境；K13 其他項目待 T18）

- **範圍**：這一節只寫 K13 中的「環境」：每個平台有哪幾級環境、各級怎麼隔開、可以放哪種資料、誰能在裡面做什麼，以及和 α ⑥ 驗證環境的關係。工具的選擇（容器編排、IaC、雲端服務）、CI/CD、部署策略、備份與災難復原、可觀測性屬平台團隊的文件；《平台架構約定》P12 補環境、P13 的觸發條件由 T18 做，安全的最低要求（機密管理、相依與機密掃描、環境的存取權限）由資安線 T29 做。來源：使用者 2026-11-04「iml時，甚至是最終系統建立時的運行環境，需要有辦法獨立、管控，應該就是類似沙盒環境的方式」；⑥ 的部分已做（精簡版 ⑥「驗證環境」）。
- **要判斷什麼**：分幾級；每一級和其他級隔開到什麼程度（網路、密鑰、存取權限、主機）；每一級能放哪種資料；誰（人、AI、CI）能在裡面執行指令、部署新版、修改環境定義；環境定義放在哪裡、改了由誰核准。
- **對照**

  | | ⑥ 驗證環境（α，已定） | 開發 | 測試 | 試點 | 正式 |
  |---|---|---|---|---|---|
  | 用途 | 一條切片的實作能不能得出設計的結果（黃金案例、P0 驗收） | 寫程式、本機試跑 | 多條切片一起跑；P9 的自動化檢查（併入主幹前跑，P9 最低要求） | 第一批真實使用者 | 所有客戶 |
  | 誰定義 | 實作附 `compose.yaml`，由人核准 | 平台團隊，從 ⑥ 的定義衍生 | 同左 | 平台團隊 | 平台團隊；地端時另見下方訊號 |
  | 資料 | 只放測試資料（黃金案例、合成資料），用完 `docker compose down -v` | 測試資料、合成資料 | 同左；P12 要用既有資料試遷移時，去識別後才放（資安線） | 真資料 | 真資料 |
  | 誰能執行 | AI 執行、人逐條核准（核准的人是執行者，不能是簽核者） | 開發者、AI | CI | 只經部署流程，執行與核准分開 | 同左 |
  | 生命週期 | 用完可丟 | 可丟 | 每次可重建 | 長期，要備份 | 長期，要備份與還原目標（P13） |
  | 檢查 | `tools/check_env.py`，結果與環境指紋寫進 log | — | P9 | T18、T29 | T18、T29 |

  - **⑥ 的定義是開發與測試環境的起點**：`compose.yaml` 已經固定 image（`@sha256:`）、套件鎖定檔、schema 的載入方式，也和主機隔開。平台團隊建開發、測試環境時從它衍生（同一份 digest 與鎖定檔，再加多條切片、CI 需要的服務），不另外寫一份。
  - **不能直接當試點與正式**：試點、正式要的東西 ⑥ 都沒有，也不該有：真資料（P7、P11 資料性質）、機密管理、存取控制與稽核紀錄（T28）、備份與還原（P13）、監控、部署新版前確認既有資料（P12）。這些由平台團隊照 T18、T29 補，不回寫到 ⑥。
  - **依賴的方向**：⑥ 不依賴平台的環境——沒有平台環境，一條切片也能驗證（原則 1 的延伸：α 不等 β、γ）。平台有測試環境之後，⑥ 的 image 與資料庫版本要和測試環境相同；不同時 ⑥ 跟著改，改了照 ⑥ 的規定重跑簽核用的測試（log 的環境指紋會變）。
  - **延續 ⑥ 的兩個做法**：環境定義放版本控制、修改由人核准（⑥ 的環境定義第一次與每次修改都由人核准）；執行與核准分開（⑥ 的執行者不能是簽核者）。
- **讀哪裡**：切片地圖「部署形態」（地端、雲端、混合）、「規模與尖峰」；P7、P11（有沒有個資、資料性質的分類）；P12（既有資料）；P13；⑥ 的 `compose.yaml`、`check_env.py` 結果與 `signoff.md` 的執行者。
- **值得用的訊號**（什麼時候一定要決定）
  - 第一次要放真資料（試點前）→ 試點環境要決定，而且和開發、測試隔開（不同網路、密鑰、存取權限）。
  - 處理個資（P7；P11 資料性質）→ 試點、正式以外不放真資料；資料性質還沒分類的（T26），先分類再決定哪一級能放什麼。
  - 地端部署 → 每家客戶一套正式環境（S6 的預設），要決定客戶端的環境由誰管控、新版怎麼送到客戶端、P12 的既有資料確認在每家客戶各做一次。
  - 第二條切片開始實作或多人同時實作 → 要有共用的測試環境與自動執行（P9 最低要求），各切片 ⑥ 的定義合成同一份。
- **代價**：分級越多、隔得越嚴，維護與準備資料的成本越高；從 ⑥ 衍生就要維持兩邊版本一致；地端每家一套，升版與既有資料確認要做很多次。
- **預設**（先試用，T18、T29 補完）：四級——開發、測試、試點、正式；開發與測試從 ⑥ 的定義衍生；試點與正式由平台團隊定義，和開發、測試分開網路、密鑰與權限；真資料只在試點與正式；環境定義放版本控制、修改由人核准；部署到試點、正式只經部署流程，執行與核准分開；AI 只在 ⑥ 驗證環境、開發、測試執行，試點與正式要不要給 AI 任何權限由 T29 決定。
- **重新評估的觸發**：第一次試點；第一家地端客戶；P13 目標值填了；⑥ 的定義和測試環境版本不一致；T29 決定機密與掃描的最低要求。
- **判讀例子**
  - HR：部署形態「地端、雲端或混合，人事資料可留在客戶本地，雲端至少管理設備與授權」（`HR:slices/PLAN.md` 整體目標、D-07）→ 正式環境至少兩種：每家客戶地端的人資（S6 的人資部署單元）與我們雲端的授權與設備；D-31 這一階段只做地端、屬性不標資料性質 → 試點前要先補 P11 分類（T26），才決定非正式環境能放什麼。實作目前直接連本機的 MongoDB（`HR:impl/app/config.py` `HR_MONGO_URI`，預設 `localhost:27017`、replica set），有 `impl/uv.lock`，沒有 compose 定義；下一條切片 ⑥ 照「驗證環境」補上後，就是 HR 開發、測試環境的起點。
  - 碳管理：⑥ 驗證環境的來源——AI 直接在主機起資料庫（port 對所有網卡開放、image 沒固定，見《團隊開發流程_對抗性審查》2026-11-04「⑥ 的驗證環境用沙盒」）。切片地圖沒有「部署形態」（T03 加欄位前寫的），S6 判讀用預設（一個部署單元＋關聯式資料庫＋物件儲存）；試點前要補部署形態，物件儲存的佐證檔案（`ee` 夾帶個資，《20261103資安範圍與合規盤點》）決定哪一級能放真檔案。
