# 舊專案相容

這份只給**在 2026-11-07 工具包整理之前就開始的設計 repo**（例：HR、碳管理的試跑）。新的 repo 從範本開始，用不到這裡的任何一條；遇不到下面的「怎麼認出來」，就不用讀。

修改經過見研究資料夾的《團隊開發流程_對抗性審查》。

## 一、舊格式的檢查紀錄

**怎麼認出來**：交付物的完成標準表是「完成標準｜AI 自評｜審查者確認」，沒有「類」欄、沒有「- 審查頁：」行；或 `signoff.md` 有「審查者確認」欄（2026-11-04 前已送審的 ⑥）；或檔案內有「審查重點（人）」表（2026-10-27 前送審）。

**已經送審、要凍結的**（`/domain-freeze`）：
- 舊格式（完成標準表有「審查者確認」欄，含 2026-11-04 前已送審的 ⑥）：每一列的「審查者確認」都已打勾（✓），或寫了人同意的偏離理由；「審查者」已填且不是 AI，「結論」是「通過」。2026-10-27 前送審、檔案內有「審查重點（人）」表的，照那張表確認。

**之後要回頭修改的**（`/domain-step`、`/domain-expert-reply`、`/domain-change`；或還沒簽核的 ⑥ 重做）：送審前先換成新格式。
已凍結的步驟回頭修改（或還沒簽核的 ⑥ 重做）時，檢查紀錄如果還是舊格式（完成標準表是「完成標準｜AI 自評｜審查者確認」，沒有「類」欄、沒有「審查頁」行），送審前先照現在的範本換成新格式，再照第 3～6 點自評、產生審查頁；工具和網頁只讀新格式（`lint.py` 送審中是舊格式會亮紅燈）。換法：
   - 用範本 `templates/slice/<檔名>` 的 `CHECKLIST` 區整段取代舊表：完成標準的條目、順序、類別都照範本。
   - 範本的每一條重新自評。舊表文字對得上的那一條，舊的 AI 自評保留在前面，有審查者確認的接著寫「（原審查者確認：<原文>）」，這次重評的加日期註記（例：「〔2026-11-06 重評〕✓ …」）。
   - 舊表有、範本沒有的列，寫在表下方一行「換格式前的其他列：<完成標準>：<AI 自評>（原審查者確認：…）；…」，不刪掉。
   - 照範本補「- 審查頁：reviews/<檔名>」行。換格式是整理性修改，不另記 CHANGELOG，在這輪的那一筆寫一句「檢查紀錄換成新格式」。
   - 已經凍結、沒有要回頭修改的步驟不用換。

- 已經凍結、沒有要回頭修改的步驟不用換。工具與網頁只讀新格式；送審中（「待檢查」）還是舊格式的，`lint.py` 亮紅燈。

## 二、規劃文件裡的變更紀錄

**怎麼認出來**：`slices/PLAN.md` 或 `slices/ENTITY_SKETCH.md` 還有「## 變更紀錄」區、但沒有 `slices/CHANGELOG.md`。

開始前先檢查。`slices/PLAN.md` 或 `slices/ENTITY_SKETCH.md` 還有「## 變更紀錄」區、但 `slices/CHANGELOG.md` 還不存在時，先向使用者說明：規範已改成把兩份的紀錄集中在 `slices/CHANGELOG.md`，地圖與草圖只放目前的內容。提出搬移：把兩份的舊紀錄依日期合併（同一天的保留原本的先後），原文照搬到 `slices/CHANGELOG.md`，每筆標題加上來源（PLAN 或 SKETCH），內容一字不改，再刪掉原本的「## 變更紀錄」區。**經使用者同意才搬**；搬完逐筆核對筆數一致，並在 `slices/CHANGELOG.md` 記一筆「PLAN、SKETCH　變更紀錄搬移」（搬了幾筆、從哪兩份）。使用者不同意時，照舊在原檔記，並在回報中提醒。

## 三、以日期分界的檢查

`lint.py` 有幾項只檢查某個日期之後的審查頁（例：問題的「例子」2026-10-28 起、黃金案例的「要得出」2026-11-04 起、抽查的寫法 2026-11-05 起；⑤ 已凍結過的不補「事後才到的輸入」表），舊的審查頁不回頭補。新 repo 的審查頁都在這些日期之後，全部會檢查。
