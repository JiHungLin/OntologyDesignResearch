# 平台架構約定

> 用途：記錄**整個平台決定一次**的架構規範。每個 domain 做設計時不必重新討論，直接依循。
> 與《團隊開發流程_精簡版.md》（Domain 設計規範）的分工：
> - **Domain 設計規範**：把一個 domain 從現實轉成 digital 的設計工作，也就是要交哪些文件、怎樣算完成。
> - **本文件**：事件、歷史、資料種類、API 形式、自動化檢查這類平台層級的決定。Domain 設計的第 ⑤ 步（投影到實作）依本文件與架構決定紀錄（見下方）產生 schema 與 API。
>
> **依賴的方向**：本文件讀 Domain 設計的第 ①～④ 步，不反過來要求 ①～④ 寫技術措施（精簡版原則 1）。各條「Domain 設計要寫出…」要求的，在第 ①～④ 步都是業務事實（例：P3 的推導值、P4 依哪個地點的日期、P11 的資料性質、P12 資料未知時的結果），其餘在第 ⑤ 步之後。新增或修改約定時照這個方向寫。
>
> **平台**：共用同一套平台決定的一個產品；目前每個 domain repo 各是一個平台（例：HR 與碳管理各自決定）。
>
> **本文件只放約束與選項；現況與選擇寫在各 domain repo 的架構決定紀錄**（`architecture/DECISIONS.md`，工具包範本 `templates/architecture/DECISIONS.md`）：P1～P13 每條的現況（已採用，或不同做法與理由）、P2／P3／P6 這類本身是選擇的「選了哪個」、P13 的目標值，以及選型（《架構決策指南》）。工具包裡的本文件是唯讀副本，不在這裡填。
>
> **誰決定**：P1～P12 由**架構負責人**、P13 的目標值由**平台負責人**決定（兩個角色見精簡版 0.5，可以是同一人）。
>
> **契約的兩半**：每條約定是「平台決定什麼」（各節內文）與「需要 Domain 提供什麼」（下方總表最後一欄）。Domain 這一半的正本在這張表；精簡版各步只指回條號。
>
> **修改約定時**：在文末「修改紀錄」寫日期、改了哪一條，以及受影響、而且已經有實作的切片；每個受影響的切片在 `06_evidence/signoff.md`「實作時發現的設計問題」加一列，處理寫「待處理」，改好才能簽核通過（精簡版 0.9「其他切片要求修改」）。

## P1　狀態只能由事件改變

- 核心業務狀態（例：請假申請的狀態、薪資批次的狀態）不提供直接改欄位的通用介面；每次變更都是一個有名字的動作（例：提出請假、核准請假），產生一筆事件紀錄，再由事件決定新的狀態。
- 動作執行前檢查 ③ 定義的「誰可以做」與「前提條件」。
- 單純的資料欄位（例：員工電話）不受此限，可以直接更新。

**判斷**：這個欄位改變時，業務上需不需要知道「誰、何時、為什麼改」？需要 → 走動作與事件；不需要 → 可直接更新。

## P2　歷史與更正的保存方式

Domain 設計只規定「更正」是一個業務動作（Domain 設計規範原則 4）；資料實際怎麼保存，由平台決定一次。

| 選項 | 做法 | 適用 |
|---|---|---|
| A 只新增 | 原紀錄不修改，更正產生新紀錄與兩者的關聯 | 會影響錢、法規、需要舉證的資料（薪資、請假扣薪、核准紀錄） |
| B 覆寫＋變更紀錄 | 直接更新，但另存不可刪除的變更紀錄 | 一般業務資料 |
| C 直接覆寫 | 只保留目前值 | 不需要追溯的資料 |

**建議**：平台依 ③ 標出的歷史需求與資料風險決定選項，而不是全部採 A。例：需要重建當時、且影響錢或法規 → A；需要軌跡 → B；只需現況 → C。Domain 設計在第 ⑤ 步的對照表（儲存區）寫下每個項目採用哪個選項。

## P3　資料的三種身分

| 身分 | 誰可以寫 | 對不上時以誰為準 | 例子 |
|---|---|---|---|
| 事實 | 業務動作新增 | 它就是真相 | 請假紀錄、核准紀錄 |
| 快取 | 只有重算程式 | 來源為準，它重算 | 餘額欄位、月結表 |
| 凍結快照 | 產生時寫一次，之後唯讀，記錄當時的規則版本與用到的輸入 | 它就是真相 | 離職結算單、已鎖定的薪資 |

Domain 設計在 ② 標出哪些是推導值；本條決定推導值存不存、怎麼存。判斷是否物化只看一件事：**願不願意隨時把它砍掉重建**。

凍結快照記用到的輸入：保存方式 A 的項目記版本編號，B、C 的項目記當時的值；不用時間去對版本（同一時間的更正與計算會對錯）。

## P4　時間欄位與時區

Domain 設計在 ③ 標出哪些時間有業務意義。平台提供三種時間欄位的標準命名與型別：

| 時間 | 意義 | 建議欄位名 |
|---|---|---|
| 發生時間 | 現實中何時發生 | `occurred_at` |
| 得知時間 | 系統何時知道 | `recorded_at` |
| 生效時間 | 規則或決定何時生效 | `effective_from`／`effective_to` |

不是每筆紀錄都需要三種；依 ③ 的標註決定。

**時區**：

| 項目 | 做法 |
|---|---|
| 時間點 | 一律存 UTC。光有 UTC 還原不出「當地幾點」，所以現實中在某個地點發生的時間（例：打卡），另存發生地的時區（IANA 名稱，例：`Asia/Taipei`） |
| 只有日期的值 | 生日、到職日、取得日這類本來就是日期的，存日期，不轉成時間點 |
| 「今天」與業務日期 | 依某個地點的當地日期判斷。用哪個地點（例：雇主所在地、工作地點、班次所在地、出差地點）是 Domain 的決定，平台不預設；程式取得「今天」一律經過同一個入口，傳入地點，不直接讀伺服器時鐘 |
| 地點 → 時區 | 由平台維護對照（參考資料，例：台灣 → `Asia/Taipei`）。一個管轄區可能跨多個時區（例：美國），對照可以掛在比管轄區更細的地點上 |

- Domain 設計要寫出：以日期判斷的規則或排程，依哪個地點的當地日期。規則本身因地點而不同時寫在 ④ 的規則；其餘寫在 ⑤ 對照表（排程寫在第二區，規則寫在第三區的說明）。
- 同一個人在不同地點發生的事（例：出差時打卡），算哪一天、工時怎麼認定，是該切片 ③④ 的決定（例：照所屬班次的日期，還是照當地日曆），不在平台決定。

## P5　規則版本與參考資料

### 規則版本可被引用

- 規則（④ 的規則表）以資料形式存在，有編號，不寫死在程式常數裡。
- ④ 標出需要版本的規則（會隨時間改變、舊結果要依當時規則解釋），保存版本與生效日；依它算出的結果，記錄當時引用的版本。
- 不需要版本的規則（例：年齡門檻）只需要編號與來源。
- 選版本依 ④ 寫的日子（例：取得日、計算日），不預設取最新；重新判定時照 ④ 寫的沿用原本的版本或依新的日子重選。帶期間的值（參數、設定、約定）同樣照 ④ 寫的日子查。④ 沒寫依哪一天的，回 ④ 補（業務事實，精簡版原則 1），不在 ⑤ 自己解讀。
- 結果記錄用到的每一條有版本的規則各自的版本，不只記有參數的。

### 規則資料與參考資料的維運

平台要載入、維護的資料有三種：

| 種類 | 是什麼 | 例子 |
|---|---|---|
| 規則資料 | ④ 有版本的規則的值與參數（大表在 ④ 只寫來源條目） | 最低工資、投保分級表、法定特休天數表、電價種類對應表 |
| 參考資料 | 全平台共用、由法規或平台決定的清單，名詞與規則會指到 | 管轄區、保險制度與施行日、假別、政府公告的係數、地點 → 時區（P4）、分類值的多語名稱（P10） |
| 固定資料 | `[靜態替代]` 的值，由平台代為載入，之後由取代它的切片接手（精簡版原則 6） | 還沒有組織切片時的雇主資料、還沒有薪資切片時的工資給付日 |

客戶自己訂的規則資料（例：公司規定的版本、企業可調的參數），以及由使用者經 API 登錄的固定資料，是業務動作，照 ③ 的事件，不在本節。

| 項目 | 做法 |
|---|---|
| 誰載入 | **平台維運**（由平台負責人兼任，精簡版 0.5）。只執行載入，不決定內容：內容來自設計（④ 規則表與參數表的「來源」、②④ 的分類值）與它們引用的 `inputs/` 條目。系統裡誰能執行載入，用一份有期間的平台維護人員名單表示，名單的增減同樣寫事件。AI 不能核對、不能發布版本 |
| 怎麼核對 | 每一筆記來源條目編號與核對狀態；值由程式從來源檔或 ④ 參數表讀出，不在程式裡另外抄數字。開發、測試與 ⑥ 驗證可以載入 `[未核對]` 的（⑥ 受影響的案例照樣不算通過）；**試點與正式只載入原文（research 條目）與解讀（④ 規則）都已核對的版本**。來源查不到生效日的，照 ④ 的寫法表示（例：沒有下限），同樣算未核對 |
| 值改了，還是規則改了 | 只有值改了（例：新一年的分級表、新的最低工資）：research 新增一筆（舊的標已過時），核對後載入新版本，不必改 ④。規則的條件、算法或參數的種類改了：先照精簡版 0.2 改 ④（回頭修改或變更提案），再載入 |
| 怎麼載入 | 每次載入、改版、修訂、停用都是一個平台的動作，寫一筆事件（誰、何時、理由、來源條目、版本）。只新增：改版新增版本，登錄錯誤新增同一版本的修訂，不原地改、不刪除（P2 A）。不以重建資料庫或直接寫資料表載入（P1；P12 的遷移也是事件）；重建資料庫只用在開發與測試 |
| 改版時通知切片 | 新版本或修訂進來時，已有的結果怎麼處理（不影響、補足、重新判定、產生建議）是業務事實，寫在 ④ 的「版本／生效日」。載入的動作是上游事件：用到這條規則的切片在 ⑤「其他切片事件的連鎖」掛上，凍結時寫進 `core/flows.md`；同一交易或之後，照架構決定紀錄（《架構決策指南》S3） |
| 未來的生效日 | 可以載入生效日在未來的版本；到那一天的處理由排程依「到今天應生效、還沒處理」補上（各平台應用架構約定的排程條目），不在載入時處理，也不依載入的時間判斷 |

## P6　規則的落實位置

| 規則性質 | 建議落實位置 |
|---|---|
| 單表、靜態的限制（例：同一班次不能重複請假） | 資料庫 constraint |
| 跨表、但不需外部資訊的一致性 | 資料庫 trigger 或 service 層檢查（平台擇一為主） |
| 需要外部資訊或人工判斷 | service 層；「需人工判斷」的規則只產生建議，不自動生效 |

## P7　個人資料的刪除與遮蔽

- 當事人依個資法要求更正、刪除或停止利用時，依法刪除或遮蔽，並留下「何時、依誰的請求、處理了哪些資料」的紀錄。
- 業務事實（例：某日請假、某月發薪）保留，只移除或遮蔽可識別個人的內容。
- 這條是 P2 選項 A 的例外。
- 哪些情況必須刪除、哪些可以遮蔽，需請懂個資法的人確認。

## P8　追溯：實作指回概念

- 每張業務表、每支 API、每個業務欄位都能指回 `core/` 中的某個概念（Entity、事件、規則）。
- 技術欄位（主鍵、建立時間、樂觀鎖版本等）與平台需要的表（outbox、稽核紀錄等）不對應業務概念，標明「技術」即可。標「技術」的不能是驗收問題、規則或 Use Case 的唯一來源；是的話它就是業務欄位，要指回概念（例：事件 payload 裡唯一記著的判定內容）。
- 指回的方式由平台統一（例：在 schema 註解、OpenAPI 擴充欄位，或獨立的對照檔）。Domain 設計 ⑤ 的 `05_mapping.md` 依此格式撰寫。

## P9　自動化檢查

以下檢查寫成自動測試，每次修改都重跑：

- 守恆式成立
- 快取砍掉重算，結果一致
- 沒有權限的人無法執行動作
- 每張表、每支 API 都指得回概念（P8）
- 黃金案例的結果與人工預期一致

Domain 設計負責提供這些檢查的內容（④ 的守恆式與決策表、⑤ 寫成快取的項目、⑥ 的黃金案例與驗收問題）；本條負責讓它們自動執行。最低要求如下，各平台的做法（在哪裡跑、例外清單）寫在架構決定紀錄的「P9 自動化檢查」一列。

### 最低要求：必須自動的檢查

對照設計的檢查（在資料庫上跑；資料庫和 ⑥ 驗證環境用同一份定義）：

| 檢查 | 怎樣算通過 | 內容來自 |
|---|---|---|
| 守恆式 | 每個守恆式在這次執行的**全部**測試資料上成立：整批測試跑完後，再對全部資料檢查一次。這也是正確性情境「0 次違反」的量測（《架構決策指南》K11） | ④ 守恆式；架構決定紀錄的品質屬性情境 |
| 快取砍掉重算 | ⑤ 寫成快取（P3）的每一項都有重建程式；刪掉後重建，結果和原本一致。寫成快取卻沒有重建程式算**失敗**，不是跳過；做不到就把它改寫成「事實，由動作寫入」 | ② 推導值；⑤ 的 P3 身分 |
| 決策表逐列 | ④ 每張決策表的每一列各一個測試，含資料不足；「不可能」的列測它被前面的規則擋下 | ④ 決策表；《架構決策指南》K10 |
| 黃金案例 | 系統結果和人算的預期結果一致 | ⑥ `golden_cases.md` |
| 權限 | 沒有權限的人無法執行受權限保護的動作；涵蓋範圍（每個動作、跨租戶）見下方「安全相關的檢查」 | ③「誰可以做」；⑤ 第二區「權限檢查」 |
| 追溯（P8） | 實作的每張表（集合）、每支 API 都在 ⑤ 的 schema 與 `api.yaml` 中，欄位與格式一致 | ⑤ |

讀程式的檢查（先試用，精簡版 0.10）：

| 檢查 | 怎樣算失敗 | 依據 |
|---|---|---|
| 「今天」只從一個入口取 | 業務上的「今天」（日期）不經 P4 的入口取得，例：直接呼叫 `date.today()`、在 SQL 裡把 `now()` 轉成日期。記錄 UTC 時間戳不算 | P4；HR `hire-employee` 簽核紀錄 #22 |
| 業務資料只由動作或遷移寫入 | 動作與遷移以外的程式（腳本、後台修復工具、排程的捷徑）直接寫入業務表或集合 | P1；P5 的載入；P12 |
| 程式指回決策表 | ④ 的決策表沒有對應的函式（程式註明表的標題）；或程式註明的表在 ④ 找不到 | 《架構決策指南》K10 |

- 測試準備資料、開發與測試環境的重建資料庫（P5）這類例外，列在架構決定紀錄「P9 自動化檢查」一列的例外清單；每一項寫範圍與理由，由架構負責人同意。
- 檢查程式由各平台寫在實作的測試裡（不同語言、資料庫寫法不同），工具包不提供。
- 權限的涵蓋範圍、相依套件與機密掃描、SBOM 見下一段。

### 最低要求：安全相關的檢查

對應《資安設計指南》G03（身分與存取）、G07（供應鏈與基礎設施）；對照的標準是 OWASP ASVS Level 2 的 V8 Authorization、V13 Configuration、V15 Secure Coding and Architecture（只列章名，要求照原文）。掃描工具由各平台選，寫在架構決定紀錄「P9 自動化檢查」一列。

| 檢查 | 怎樣算通過 | 什麼時候跑 | 內容來自 |
|---|---|---|---|
| 權限的涵蓋範圍 | ⑤ 第二區每個有 API 的事件（`無 API：排程` 的除外；實作沒有 HTTP 層時，是服務層的動作）至少一個測試：沒有權限的人執行，被擋下。動作讀寫屬於某個租戶（客戶、企業）的資料時，另外至少一個測試：別的租戶的使用者讀不到、改不到（一個帳號隸屬多個組織時，用它不屬於這個組織的身分測）。只有平台維運能做的動作（P5），一般使用者被擋下。沒有測試的動作算**失敗**，不是跳過 | 併入主幹前、⑥ 簽核前 | ③「誰可以做」；⑤ 第二區「權限檢查」；P11 識別範圍 |
| 機密掃描 | 版本控制裡（程式、環境定義、自動執行的設定檔）沒有真的機密（密碼、金鑰、token、連線字串裡的密碼）；⑥、開發、測試用的測試密碼（例：`test-only`）列在例外清單 | 併入主幹前；第一次設定時掃過整個歷史 | — |
| 相依套件的已知漏洞 | 有鎖定檔（每個套件固定版本）；鎖定檔裡沒有「已經有修正版」的高或嚴重等級已知漏洞。其他等級留在掃描結果，由平台負責人安排升級 | 併入主幹前；另外定期跑（例：每週），因為程式不改也會出現新的已知漏洞 | 鎖定檔 |
| SBOM（軟體元件清單） | 部署到試點、正式的每一版產生一份（CycloneDX 或 SPDX 格式），和那一版一起保存 | 每次部署到試點、正式 | 鎖定檔、image |

- 掃到真的機密：當作已經外洩，平台負責人先換掉它（改密碼、撤銷金鑰），再從程式移除；只從程式刪掉不算處理完。
- 定期掃描的紅燈沒有「提交修改的人」：由平台負責人安排升級。
- 安全檢查的例外（暫時接受一個漏洞、某個測試密碼、某個動作不測權限）由**資安負責人**同意（精簡版 0.5），記在同一份例外清單（哪一項、範圍、理由、到什麼時候）；其他檢查的例外照上一段由架構負責人同意。
- ASVS L2 其他章的對照不能全靠自動檢查，由資安負責人在第一次試點前做（《資安設計指南》第四節「試點前」），不屬本條。
- 各級環境的安全最低要求（機密放在哪裡、誰能存取、AI 能在哪幾級執行）見《資安設計指南》G07。

### 最低要求：什麼時候跑、在哪裡跑

| 時機 | 跑什麼 | 在哪裡 |
|---|---|---|
| 每次修改要併入實作的主幹之前 | 上面全部（安全相關的檢查另照該表的時機，例：定期、部署時）；紅燈不併入 | 平台的測試環境（《架構決策指南》K13；環境的分級與誰能部署由平台團隊定） |
| ⑥ 簽核前 | 該切片的測試 | ⑥ 驗證環境，用 `tools/run_evidence.py`（精簡版 ⑥）；這份 log 才是簽核依據 |

- 自動執行的定義（例：CI 的設定檔）和環境定義一樣放在版本控制，修改由人核准；照定義自動執行時不再逐次核准。
- 還沒有自動執行時，由提交修改的人在 ⑥ 驗證環境跑同一組檢查；架構決定紀錄的 P9 現況寫「不同做法：還沒自動執行」，不寫「已採用」。

### 最低要求：失敗時誰處理

| 失敗的原因 | 誰處理 | 怎麼處理 |
|---|---|---|
| 程式和設計不一致 | 提交這次修改的人（AI 寫的修改，由核准它的人負責） | 修程式；修好之前不併入 |
| 設計沒寫、寫錯或做不到 | 同上，提出給該切片 | 記在該切片 `06_evidence/signoff.md`「實作時發現的設計問題」，照精簡版 0.9 回頭修改；不在程式裡自己補，也不改測試的預期結果去配合程式 |
| 檢查本身寫錯 | 提交這次修改的人 | 修檢查，commit 訊息寫原因；預期結果來自黃金案例或 ④ 的，不在這裡改 |
| 要跳過、停用某項檢查或加例外 | 架構負責人同意（安全相關的檢查由資安負責人同意） | 記在例外清單（哪一項、範圍、理由、到什麼時候）；沒有同意就跳過的，算紅燈 |
| 環境或自動執行本身壞了（資料庫起不來、資源用完、逾時） | 平台負責人（精簡版 0.5） | 修好後重跑；這一次不算通過，也不改成跳過 |

### 和 ⑥ 的關係

- 自動執行不取代 ⑥：⑥ 的簽核依據是 `tools/run_evidence.py` 的 log（指令由人逐條核准，執行者不是簽核者，黃金案例由人算）；自動執行的輸出不當簽核依據，⑥ 的完成標準也不引用它。
- ⑥ 簽核後，該切片的測試加進自動執行；之後每次修改都重跑，紅燈照上表處理。設計問題記回那條切片的 `signoff.md`，已凍結的照 0.9 回頭修改。

## P10　識別名稱與多語標籤

- 模型元素（表、欄位、API、事件、狀態）以英文識別名稱命名，與 Domain 設計的詞彙對照表一致。
- 分類值以穩定代碼儲存（例：假別 `ANNUAL`），代碼不隨語言改變；畫面、報表、AI 回答顯示時，依使用者語言從對照表取名稱。
- 各語言名稱與代碼分開存放（例：多語標籤表或語系檔），新增語言只要新增標籤，不必改資料或程式。
- 不同管轄區的同名概念（台灣特休、日本年次有給休暇）是不同的分類值，各有代碼，不共用。

## P11　識別範圍與資料存放

各平台的情況不同，這條沒有預設答案，由團隊依產品決定一次：

| 要決定的事 | 可能的選擇（例） | 影響 Domain 設計的哪裡 |
|---|---|---|
| **識別範圍**：在什麼範圍內認「同一個」 | 每家客戶各自一份（同一個人在兩家客戶是兩筆）；整個平台一份；混合（例：人是全平台一份，員工編號只在雇主內有效） | ② 第 1 問「靠什麼認出是同一個」。個別 Entity 要用不同範圍時，才在它的 Entity 卡寫明 |
| **資料性質**：這個平台處不處理個資 | **處理個資**（有任何可識別個人的資料，包括登入帳號）→ 必須標，分類固定為下表三種，不能選「不標」或晚一點再標；**不處理個資** → 不標，寫明依據（例：只有匿名的統計資料、沒有帳號） | ② 的屬性。處理個資的平台，第 ② 步每個屬性都標（含「不含個資」） |
| **資料存放** | 全部放同一處（地端或雲端）；依資料性質分開放（例：去識別資料在雲端、可識別資料在地端） | ⑤ 的對照與 schema。② 不受影響：同一個 Entity 的資料分放兩處，仍是同一個 Entity |

**資料性質的分類**（2026-11-04 起；處理個資的平台必用，代碼照 P10）

| 分類 | 代碼 | 是什麼（依《個人資料保護法》） | 例子 |
|---|---|---|---|
| 不含個資 | `NONE` | 不能直接或間接識別特定的人 | 雇主的統一編號、假別、規則版本、政府公告的排放係數、電費單的用電度數 |
| 可識別個人 | `PERSONAL` | 第 2 條：姓名、出生日期、身分證號、聯絡方式等，能直接或間接識別特定的人的資料 | 姓名、住址、證件號碼、投保薪資、特休餘額、登入帳號 |
| 特種個資 | `SPECIAL` | 第 6 條：病歷、醫療、基因、性生活、健康檢查、犯罪前科，原則上不得蒐集，例外要有法定依據 | 傷病紀錄、病假的醫療證明、健康檢查結果 |

- **依業務上可能存到的最敏感內容標**：一個屬性可能存到個資時（例：佐證檔案裡可能夾帶身分證影本、加盟主名稱可能是自然人），標它可能存到的最高一級，不依「通常」的內容。
- **只標法規分類**：證件號碼要不要比姓名多一層遮蔽、企業的營運數字算不算機密，是 γ 的風險判斷或合約，不在 ② 標，由《資安設計指南》G02 在第 ⑤ 步讀屬性的意思決定。特種個資的**蒐集依據**（第 6 條的哪一個例外）是業務事實，寫在 ① 的範圍或 ④ 的規則。
- 決定的現況寫在架構決定紀錄第一區「P11 資料性質」一列：`已採用`（處理個資，標三種）或 `不同做法：不處理個資`（附依據）。
- 資料性質描述的是資料本身（例：身分證號可識別個人），不是它放在哪裡；同一個標註可以支援不同的存放方式，也支援 P7 的刪除與遮蔽、加密、存取權限與威脅建模（γ）。
- 分開存放時，兩處的資料怎麼對應（例：雲端只存代號，地端保存代號與真實身分的對照），由平台統一，不在各 domain 另訂。

## P12　模型演進與既有資料

Domain 設計改了名詞或屬性之後（第 0 級回頭修改、第 2 級擴充、第 3 級改變意思都算），開發、測試、試點或正式環境（下方「環境」）裡已經存在的資料怎麼處理，由平台決定一次：

| 情況 | 做法 |
|---|---|
| 新增屬性 | 既有紀錄的值是**未知**，不填預設值。未知和「否」「0」「空白」分開表示（例：欄位不存在，或明確標成未知）；程式不能把未知當成否 |
| 規則用到未知的屬性 | 判定與計算的結果是「資料不足」，列出缺的屬性，提示補登；不當成條件不成立。④ 的判定類規則要寫出這個結果 |
| 補值 | 用業務動作補（例：補登、更正），產生事件，依據寫回頭修改的 `CHANGELOG.md` 那一筆或變更提案（CR-nnn）；不直接改欄位（P1）。能從其他資料確定推出的，可以用遷移批次補，但遷移本身也是一個事件：記依據、執行者、時間、改了哪些紀錄 |
| 拆、合概念（第 3 級） | 舊紀錄保留原意，不改寫；新意思從生效日起適用。生效日以前的資料需要用新意思來看時，用遷移事件產生新紀錄並指回舊紀錄（P2 選項 A） |
| 資料庫驗證規則與 schema | 隨設計的 tag 一起改版；部署新版前，先確認既有資料都符合新的驗證規則（新屬性要允許未知；誰做見下方「部署新版前確認既有資料」） |

- Domain 設計在 ⑤ 的對照表寫出：哪些集合或表有既有資料受影響、新屬性的未知怎麼表示、由誰用哪個動作補值。變更提案的「舊資料怎麼處理」欄寫同樣的內容。
- 遷移腳本與後台修復工具是 P1 最常被違反的地方，要納入 P9 的自動化檢查（只能透過動作或遷移事件寫入；見 P9「業務資料只由動作或遷移寫入」）。

### 環境

每個平台的系統分四級環境（2026-11-05 起）。α 第 ⑥ 步的驗證環境（精簡版 ⑥「驗證環境」）只驗證一條切片，不算其中一級。

| | 開發 | 測試 | 試點 | 正式 |
|---|---|---|---|---|
| 用途 | 寫程式、本機試跑 | 多條切片一起跑；P9 的自動化檢查（併入主幹前） | 第一批真實使用者 | 所有客戶 |
| 誰定義 | 平台團隊，從 ⑥ 的環境定義衍生（同一份 image 版本與鎖定檔，再加需要的服務） | 同左 | 平台團隊 | 平台團隊；地端見下方 |
| 資料 | 測試資料、合成資料 | 同左；用既有資料試遷移時，用去識別的副本 | 真資料 | 真資料 |
| 誰能執行、部署 | 開發者、AI | 自動執行（P9） | 只經部署流程，執行與核准分開 | 同左 |
| 生命週期 | 可丟 | 每次可重建 | 長期，要備份 | 長期，備份與還原照 P13 的目標 |
| 重建資料庫 | 可以（P5） | 可以 | 不可以；資料的改變照本條上表、P5 的平台動作 | 同左 |

- **隔離**：試點、正式和開發、測試分開網路、機密與存取權限；四級不共用資料庫。各級的機密放在哪裡、誰能存取、AI 能做什麼，見《資安設計指南》G07，這裡不重寫。
- **環境定義**（例：Compose、IaC、部署設定）放在版本控制，修改由人核准；照定義自動執行時不再逐次核准（同 P9）。
- **真資料只在試點、正式**：處理個資的平台（P11 資料性質）要把資料從試點、正式拿到其他級時，先去識別。
- **和 ⑥ 的關係**：⑥ 不依賴這四級，沒有平台環境，一條切片也能驗證；平台有測試環境之後，⑥ 的 image 與資料庫版本跟上測試環境（《架構決策指南》K13）。
- **地端部署**：每家客戶一套正式環境（試點在客戶端時也一樣）。客戶端的環境由誰管控、新版怎麼送到客戶端，寫成架構決定紀錄中判斷 `K13` 的 ADR。
- 現況（建了哪幾級、各在哪裡）寫在架構決定紀錄 P12 一列；工具（容器編排、IaC、CI/CD、雲端服務）與做法屬平台團隊的文件（《架構決策指南》K13）。

**部署新版前確認既有資料**

| 步驟 | 誰 | 做什麼 |
|---|---|---|
| 寫確認程式 | 提交這次修改的人（AI 寫的修改，由核准它的人負責） | 隨實作寫：拿既有資料對新的驗證規則與 schema，列出不符合的紀錄；和遷移程式放在一起 |
| 在測試環境先跑 | 自動執行（P9） | 用合成資料或去識別的副本跑確認與遷移 |
| 在要部署的那一級跑 | 部署流程（自動） | 部署前跑確認；有不符合的就停止部署，不先部署再修 |
| 核准部署 | 平台負責人（精簡版 0.5） | 看過確認的結果再核准；執行與核准分開，AI 不在試點、正式執行（《資安設計指南》G07） |
| 處理不符合的資料 | 架構負責人決定 | 照本條上表補值（業務動作或遷移事件）；是設計的問題時記在該切片 `06_evidence/signoff.md`，照精簡版 0.9 回頭修改。不為了通過確認而放寬驗證規則或直接改資料 |

- 地端時每家客戶各跑一次；某一家沒通過，只停那一家。

**什麼時候要決定**

| 觸發 | 要決定什麼 |
|---|---|
| 第二條切片開始實作，或多人同時實作 | 共用的開發與測試環境、自動執行（P9）；各切片 ⑥ 的環境定義合成同一份 |
| 第一次試點前（第一次放真資料） | 試點環境照本節建好；部署新版前的確認可以執行；P13 的目標值（P13「什麼時候必須填」）；《資安設計指南》G07 的確認 |
| 第一家地端客戶前 | 客戶端的環境由誰管控、新版怎麼送到客戶端（判斷 `K13` 的 ADR） |
| 第一次改到試點或正式已有的資料 | 照本條上表與 ⑤ 的「既有資料」做，部署前照上方確認 |

## P13　非功能需求（效能、可用性、併發）

效能（例：回應時間）、可用性（例：每月可用時間比例）、併發量、備份與還原時間這類目標，由平台決定一次，不在各切片設計。目標值由平台負責人（精簡版 0.5）決定，寫在架構決定紀錄的「P13 目標值」。

| 項目 | 目標 | 依據 |
|---|---|---|
| 回應時間 | （寫在架構決定紀錄） | |
| 可用性 | （寫在架構決定紀錄） | |
| 併發與尖峰 | （寫在架構決定紀錄） | |
| 備份與還原 | （寫在架構決定紀錄） | |

- Domain 設計只提供決定這些目標需要的業務資料，寫在切片地圖的「整體目標」：部署形態（地端、雲端或混合）、規模（例：客戶數、每家的員工數範圍）與尖峰時段（例：月底結算薪資、年度特休給假）；規劃時必問，不知道寫「未定」。
- 個資與法規遵循（例：刪除、遮蔽、資料存放地）不屬於這一條，見 P7、P11 與 ④ 的規則。

### 什麼時候必須填

| 時間點 | 誰 | 填什麼 | 沒有時 |
|---|---|---|---|
| 規劃（切片地圖） | 使用者回答 | 部署形態、規模與尖峰（業務事實） | 寫「未定」，不由 AI 推想 |
| 規劃後初判、架構決策關卡 | 平台負責人 | 品質屬性情境（《架構決策指南》K11）；目標值可以是「未定」 | 照預設判斷；ADR 的重新評估觸發寫「QS-nn 的目標值決定時」 |
| **第一次試點前**（第一次放真資料） | 平台負責人 | 四項都有目標；備份與還原寫最多遺失多久的資料、多久恢復；可用性、備份與還原的品質屬性情境「在…內」有值 | 不進試點 |
| 之後 | 平台負責人 | 規模或尖峰改了、多一種部署形態（例：第一家地端客戶）、量到某項做不到、客戶合約有要求時重填 | 照情境走過的 ADR 重新評估（《架構決策指南》第四節） |

- 目標寫成量得到的：量什麼、在哪一級環境量、多長期間（例：正式環境每月 API 成功回應的比例）。怎麼量、怎麼警示屬平台團隊（《架構決策指南》K13 可觀測性）。
- 地端與雲端的目標可以不同，分開寫。
