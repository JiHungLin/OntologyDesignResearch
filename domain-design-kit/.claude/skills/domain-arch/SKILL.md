# 架構決定

參數：`$ARGUMENTS`（模式與切片代號）。沒有參數時依狀態判斷：沒有 `architecture/DECISIONS.md` 或沒有任何 ADR → 初判；要開始某條切片的 ⑤ → 關卡或複查（見第 3 節）；⑤ 剛通過審查要凍結 → 提升。開始前用一句話說明要做什麼（例：「開始 ⑤ 之前，先依已凍結的 ②③④ 決定資料庫、交易邊界這些技術選擇」）。

這是 β 系統架構的工作，不是六步的一步（`docs/01` 0.5、⑤）。決定由**架構負責人**同意，P13 目標值由**平台負責人**；沒有指定人時由使用者兼任。

## 1. 共同規則
- 讀 `docs/06`《架構決策指南》（第二節原則、第四節時間點、第五節該判斷的那一節）、`docs/03`《平台架構約定》、`docs/02`「架構決定紀錄」的格式。
- **只讀，不改** 切片地圖與 ①～④（`docs/01` 原則 1）。判斷時發現缺的是**業務事實**（例：上游改了、下游晚一點才重算，業務上能不能接受；法定的保存期限），停下來向人說明，照 `docs/01` 0.9 回到那一步補——補的是業務事實，不是技術措施。不能為了技術方便要求改寫業務事實（例：為了少一次跨集合檢查合併兩個 Entity）。
- **每條 ADR 照指南該節的「讀哪裡」找訊號**，在「背景與訊號」寫出處（`<切片>/<檔名> <編號>`、`slices/PLAN.md` 整體目標或 D-nn）；讀不到寫 `沒有訊號，用預設`。「這個方法很主流」「我覺得比較好」不是訊號。偏好（使用者說「我想用 X」）可以是理由：寫「理由：偏好」，並在「沒採用的做法」「代價」和訊號指向的選項比較。
- 每條 ADR 都寫：沒採用的做法（至少一個）、代價、重新評估的觸發、資安影響（要守住什麼；沒有寫「無」）。代價每一點開頭寫它犧牲的品質屬性（`docs/06` 原則 4、K11 的九個名稱，例：`效能：…`）。
- **問人**：一條 ADR 一題，照 `docs/01` 0.2「問人的方式」用選項介面（AskUserQuestion）：背景（訊號與出處）、一個具體例子（例：「同一位員工兩筆僱傭期間同時送出」）、一句問題、`A（建議）` 與其他選項，每個選項寫「做法 → 結果（含代價）」。建議的就是預設，除非讀到訊號。使用者選了之後，「提出／同意」寫 `AI／<人>（<日期>）`（使用者自己提出的寫 `<人>／<人>`）；沒問到或沒回答的維持 `AI／待確認`。
- 寫入 `architecture/DECISIONS.md` 用 `tools/table.py` 讀寫表格；改完跑 `python3 tools/lint.py <切片>`（用目前要做的那條；還沒有切片時跳過，第一條切片的 lint 會檢查），看「架構決定」沒有紅燈。
- **git**：這個技能結束時，只 commit `architecture/DECISIONS.md`（訊息 `architecture：<模式>：<一句摘要>`），不打 tag、不 push。這是 CLAUDE.md「只有 /domain-freeze 會 commit」的例外，因為 ⑤ 的「讀取的輸入」要寫這個檔案的 commit。

## 2. 初判（切片地圖同意後）
1. 沒有 `architecture/DECISIONS.md`：從 `templates/architecture/DECISIONS.md` 建立，`{{平台}}` 寫這個 repo 的產品名稱。
2. 讀 `slices/PLAN.md` 整體目標（要做的系統與對象、明確不做、**部署形態**、**規模與尖峰**）、「領域」「切片」表、「決定與理由」。部署形態或規模與尖峰空白：先問使用者（不知道就寫「未定」），經同意在地圖補上並在 `slices/CHANGELOG.md` 記一筆（PLAN）。
3. **搬既有的平台決定**：地圖「決定與理由」中屬於平台的（識別範圍、資料庫、API 風格、P1～P13 的選項；例：HR 的 D-31、D-35），列給使用者看，經同意搬進紀錄（第一區現況、或寫成 ADR，提出／同意照原本的 D-nn，背景寫 `slices/PLAN.md D-nn`），地圖那一列不刪除，「決定」欄末尾加「（已搬到 architecture/DECISIONS.md ADR-nnn）」，記 `slices/CHANGELOG.md`。已做過的 ⑤「決定與理由」不在初判搬（只有資料庫屬 S2 可以），在關卡第 1 點補寫；在這裡寫成 S1、S3～S5 的 ADR 會讓關卡被判成複查。
4. 依指南判斷 S6（部署單元與模組）、S7（分層）、S2（資料庫）的候選，各寫一條 ADR，狀態 `暫定`，「重新評估的觸發」寫「第一條切片 ④ 凍結後的架構決策關卡」。S6 的 ADR 下方寫三張附表（C4 Context、C4 Container、模組；格式見指南 S6、`docs/02`「架構決定紀錄」的附表）；還沒有切片時，模組表只寫領域與平台元件。
4a. **品質屬性情境**（先試用，`docs/06` 第六節 K11）：依切片地圖（規模與尖峰、部署形態、要做的系統與對象）與已有的交付物，在第一區「品質屬性情境」寫 3～6 條，狀態 `草稿`：至少涵蓋尖峰時的效能或可擴展、會碰到鎖或連鎖的正確性、時間觸發或背景工作在時限內做完、故障後不遺失與恢復；有部署形態的加斷線或可攜，有規則版本的加改版。「當…」「在…時」只寫讀得到的業務事實（讀不到寫 `未定`，推想的尖峰標「推想」）；「在…內」不補數字，平台負責人沒給就寫 `未定`；「走過的 ADR」留空。整組一題問平台負責人（確認、修改或補數字），同意的改 `確認`；有數字的同步寫進「P13 目標值」（`見 QS-nn`）。
5. **② 要用的兩件 P11 與資安範圍**（② 開始前要有；還沒決定的在這裡問，各一題）：
   - P11 識別範圍：產品決定，② 第 1 問要用。
   - P11 資料性質（`docs/03` P11）：平台處不處理個資（有任何可識別個人的資料，包括登入帳號，就是處理）。處理 → 第一區「P11 資料性質」寫 `已採用`，② 每個屬性標三種分類；不處理 → `不同做法：不處理個資`，依據寫為什麼沒有個資。
   - 資安範圍：一條 ADR，判斷 `K12`（`docs/07` 第四節「規劃」、G01）——適用的法規（預設個資法）、應用安全標準與等級（預設 OWASP ASVS L2）、ISO/IEC 27001、27701 只當參考、客戶的資安要求（沒有就寫「待提供」）、資料落地（讀整體目標的部署形態；例：人事資料可留在客戶本地）、一個帳號跨多個組織（有的話寫出）。背景寫 `slices/PLAN.md` 整體目標與 `inputs/` 的法規研究；同意者是**資安負責人**（沒有指定人時由使用者兼任），狀態 `暫定`，「重新評估的觸發」寫「有客戶資安要求或認證要求時；部署形態改變時」。
6. 一條一題問完，寫入，commit。回報：寫了哪些 ADR（含 K12）、P11 兩列的現況、品質屬性情境幾條（哪些目標還是未定）、哪些還是暫定、下一步（`/domain-new-slice`）。

## 3. 關卡或複查（第 ⑤ 步開始前）
判斷做哪一種：紀錄中判斷 S1～S5 的 ADR 有任何一項還沒有（`暫定`、`採用` 都算有）→ **關卡**；都有 → **複查**。不看有沒有 `採用`：初判搬進來的決定（例：使用者把資料庫選成 `採用`）不代表 S1、S3～S5 判斷過。沒有 `architecture/DECISIONS.md`（例：⑤ 已做過、但當時還沒有紀錄的平台）→ 先照第 2 節第 1～3 點建立並搬既有決定，再做**關卡**。
本切片的 ②③④ 要已凍結（看 tag）；沒有就停下來。

**關卡**
1. 讀本切片已凍結的 ②③④、`01_scope.md` 驗收問題、`core/`、切片地圖；已做過 ⑤ 的平台，也讀既有切片的 `05_mapping.md`「決定與理由」與 `06_evidence/signoff.md`「實作時發現的設計問題」，把已經做了的選擇寫成 ADR（補寫，背景照實寫「當時理由：…」，代價寫實作時已出現的）。
2. 依指南判斷 S1～S5，確認初判的 S2、S6、S7（S6 的模組表照 `core/entities.md` 的出處補上擁有的集合或表，S7 的附表寫每個 `[靜態替代]` 的換法）；順序照指南第二節原則 5（S7、S1 先，S1 先於 S2，S6 與 S3 一起看，S5 帶出 S4）。
3. 每條寫成 ADR：讀得到訊號而且使用者同意的標 `採用`；證據不夠的（常見是 S3～S6）標 `暫定`，「重新評估的觸發」寫等什麼訊號。
4. 第一區 P1～P12：依決定填現況（`已採用`、`不同做法：…`、`見 ADR-nnn`），P2、P3、P6 寫「見 ADR-nnn」；P13 目標值向平台負責人（使用者）問一題，不知道就留「未定」；沒有品質屬性情境的（初判早於 2026-11-04，或在這裡才建紀錄的平台），照初判第 4a 點先寫。
4b. **用情境走 ADR**（先試用，`docs/06` 第四節 4.1）：每條情境列出影響它的 ADR，每一對標 `ADR-nnn 支持` 或 `ADR-nnn 風險：<一句>`，沒有任何 ADR 走到的寫 `沒有 ADR 處理`，寫進「走過的 ADR」。同一條 ADR 對一條情境支持、對另一條是風險（取捨點）→ 寫進那條 ADR 的代價，引用兩條情境（`docs/06` 原則 6）。每個風險與「沒有 ADR 處理」各一題問架構負責人：改 ADR（照複查第 3 點）／加一條判斷 `K11` 的 ADR／接受（那條 ADR 的代價寫「接受：QS-nn，<理由>」；目標未定的，重新評估觸發加「QS-nn 的目標值決定時」）。
4a. 照初判第 5 點補：第一區沒有「P11 資料性質」一列或還是 `未定`、沒有判斷 `K12` 的 ADR（例：初判早於 2026-11-04，或 ⑤ 已做過、在這裡才建紀錄的平台）→ 各問一題補上。P11 資料性質改成 `已採用`、已凍結的 ② 還沒標的：列出要補標的切片與 `core/entities.md`，告訴人用 `/domain-change` 回頭補標（只加標記，不改設計），不在這裡改 ②。
5. 一條一題問完、寫入、commit。

**複查**
0. 先照關卡第 4a 點檢查「P11 資料性質」與 `K12` 的 ADR，缺的補問。
1. 讀本切片已凍結的 ②③④，對照每條 `採用`、`暫定` ADR 的「重新評估的觸發」與指南該節的「值得用的訊號」（例：第一次跨部署單元的下游、第一次多跳查詢、跨兩個 Aggregate 的 `擋下` 規則、規模與尖峰有了數字）。這條切片帶來新的尖峰、期限、時間觸發的工作或外部系統時，照初判第 4a 點加一條情境，只走那一條（關卡第 4b 點）。
2. 在「訊號複查紀錄」加一列：日期、切片、讀了哪些（檔案 @ tag）、結果（`無新訊號`，或 `ADR-nnn 要重新評估：<訊號>`）。
3. 要重新評估的：照關卡的寫法新增一條 ADR，舊的改 `已取代: ADR-nnn`（不刪除），一題問使用者；受影響、已有實作的切片，照 `docs/01` 0.9「平台約定修改時」在它的 `signoff.md` 加一列。
4. 寫入、commit。

**結束**：回報 ADR 狀態與 commit，告訴人接著由 `/domain-step 5` 開始 ⑤（「讀取的輸入」寫 `architecture/DECISIONS.md @ <commit>`）。⑤ 要用的 ADR 還有 `AI／待確認` 時，不開始 ⑤。

## 4. 提升（第 ⑤ 步凍結時）
1. 讀本切片 `05_mapping.md`「決定與理由」與第五區（技術欄位與平台表）。
2. 找出會被其他切片沿用的做法（版本文件的欄位、錯誤回應格式、訊息代碼、跨切片同一交易或 outbox、鎖、分批、型別慣例、[靜態替代] 的做法），以及寫了「沿用 <切片> 的 …」卻沒有對應 ADR 的。
3. 每一項問一題：提升到「三、應用架構約定」（寫成 ADR，判斷 `應用層`，背景開頭寫落實哪條約定或選型，再寫 `<切片>/05_mapping.md D-nn`，例：`落實：P2、ADR-004（S5）；hire-employee/05_mapping.md D-10`；出過錯的，代價寫 `signoff.md #n` 與這條怎麼避免，`docs/02`「架構決定紀錄」）→ 之後的切片照用；或不提升（只屬本切片）。和既有應用架構約定衝突的，寫明衝突，問要不要取代；兩條切片做法不同的，問要統一成哪一種，和選的不同的那條切片在它的 `06_evidence/signoff.md`「實作時發現的設計問題」加一列（處理寫「待處理」），不改它已凍結的 ⑤。
4. 寫入、commit；回到 `/domain-freeze` 繼續凍結。**補提升**（已凍結、當時還沒有紀錄的切片，例：`/domain-arch 提升 hire-employee`）：照第 1～3 點做，讀 `05_mapping.md` 的已凍結版本與 `signoff.md`，結束時直接 commit `architecture/DECISIONS.md`（不經 `/domain-freeze`；`signoff.md` 有加列的一起 commit）。

## 5. 補代價（實作或 ⑥ 之後）
實作時發現的設計問題（`signoff.md`）屬於某條 ADR 的代價時（例：寫入偏斜要加鎖、交易大小限制）：在那條 ADR 的「代價」補上（註明 `<切片>/06_evidence/signoff.md #n`）；代價大到要改決定的，照複查第 3 點新增 ADR 並問人。commit。
