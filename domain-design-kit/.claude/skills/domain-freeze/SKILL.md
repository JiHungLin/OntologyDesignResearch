# 凍結一個步驟

參數：`$ARGUMENTS`（步驟編號 N、切片代號；同一次修正牽涉多步時可寫多個編號，例：`3,4,5`）。沒有參數時，找出狀態為「待檢查」的交付物；只有一個就用它，有多個時，屬於同一次回頭修改的（CHANGELOG 同一個依據）建議一起凍結，其餘問人。

## 1. 確認可以凍結（任何一項不符就停下來說明，不要凍結）
- 交付物狀態是「待檢查」。第 ③ 步要同時看 `03_flows.md` 與 `03_use_cases.md`；第 ⑥ 步看 `06_evidence/signoff.md`。
- **先讀檔，不憑記憶**：讀這一步檢查紀錄「審查頁」行的最後一個審查頁（`docs/02`「審查頁」），回報時引用原文與 `檔名:行號`。
- 審查頁已由審查者作答：
  - 每一題「你的回答」都有填（A、B 或一句話）；確認列都打 ✓ 或寫了意見；抽查寫了挑哪幾條與結果；「通過後新增」的列也都答了；每一步的審查者（不是 AI）、日期已填，結論是「通過」。
  - 選了非建議選項、寫了「其他」或意見的，都已記成 X-nn（來源 `審查者`）並處理；處理時改了設計的，要先回到 `/domain-step` 的回頭修改流程，不凍結。
  - 第 ⑤ 步：最後一個審查頁的「這輪審查的步驟」是 `⑤ 第一段` 時不凍結——告訴人第一段答完了，接著是第二段（`/domain-step 5`，AI 抄回預期結果、產生 schema 與 API、做紙上推演）。第二段的審查頁答完才凍結；採用的黃金案例「紙上判定」都已填（`docs/01` ⑤「兩段審查」）。
  - 抽查發現自評不實的，審查頁的「逐條審查」要填完。
  - 舊格式（完成標準表有「審查者確認」欄，含 2026-11-04 前已送審的 ⑥）：每一列的「審查者確認」都已打勾（✓），或寫了人同意的偏離理由；「審查者」已填且不是 AI，「結論」是「通過」。2026-10-27 前送審、檔案內有「審查重點（人）」表的，照那張表確認。
  - 偏離理由：「預設」類規定可偏離，「必須」類不可，見 `docs/01` 0.2。
- 「決定與理由」的「提出／同意」欄沒有「待確認」：審查頁中寫出 D-nn 的確認列已打勾、或問題選了建議答案的，先把這些決定的「提出／同意」改成 `AI／<審查者>（<審查日期>）`，記下是依審查頁的哪一題或哪一列（寫進 CHANGELOG）；審查頁沒列出的決定不能這樣改，要人明確同意。然後執行 `python3 tools/lint.py <切片> --freeze`，有紅燈就停下來說明（含 `core/` 中沒有前綴的 Q、UC、US-D，與「被引用」缺漏）。舊格式沒有這一欄的，在回報中提醒，不擋凍結。
- 第 ⑥ 步另外確認：審查頁結論表的執行者與審查者（簽核者）都已填且不是同一人（一人團隊時執行者寫「<名字>（一人團隊）」可以同一人；舊格式看 `signoff.md`）；黃金案例的預期結果由人填寫；`lint.py --freeze` 的「執行紀錄」沒有紅燈。在改任何狀態前一起問完之後，把審查頁的執行者、簽核者、日期、結論抄回 `signoff.md`。
- 第 ④ 步另外確認：第 ③ 步已凍結。
- 「讀取的輸入」有標「（未凍結）」的其他切片檔案：那條切片的修改要先凍結（看它的 tag），還沒凍結就停下來說明（`docs/01` 0.9「其他切片要求修改」，先試用）。
- 這次凍結處理的是其他切片的要求（CHANGELOG 有「其他切片要求」、依據相同）：凍結的那一筆「依據」寫同一個 `<切片>/<檔名> D-nn`，回報時提醒提出要求的切片現在可以凍結。
- 有引用標 `[待專家確認]` 的項目可以凍結，但要在回報中列出。
- **要問人的事在這裡一次問完**（凍結只停這一次；問的時候交付物的狀態還是「待檢查」，不改檔頭、不寫 CHANGELOG）：
  - 第 ②③④ 步：版本照第 2 節第 1 點先算好，執行 `python3 tools/sync_core.py <切片> --steps <這次凍結的 ②③④> --tags <步驟>=<tag>,…`（不加 `--write`，只預覽），把差異（新增、更新、切片已沒有、衝突、未同步）給人看，問要不要照這樣寫入；工具列為「未同步」的章節（例：③ 的推導的狀態、決策流程，④ 的決策表）要不要手動放進 `core/`；規則撞號、引用了 `[已取代]`／`[已停用]` 的項目、「切片已沒有」的項目要標 `[已取代]` 還是 `[已停用]`，也在這裡問。
  - `core/` 有修改、repo 有遠端且可用 `gh`：要不要開 PR（第 3 節第 2 點）。
  - 第 ⑤ 步：執行 `/domain-arch 提升`（先試用），它的問題（哪些做法提升到架構決定紀錄）也在這裡問；它會先 commit `architecture/DECISIONS.md`。`lint.py --freeze` 的「架構決定」不能有紅燈（⑤ 要用的 ADR 不能還是「待確認」）。
  - 沒有要問的就直接往下做。

## 2. 寫入
人回答第 1 節的問題後才開始；從這裡到第 3 節打 tag **連續做完，中間不停下來問人**。凍結＝打 tag（`docs/01` 0.2）：停在一半時，檔頭寫「已凍結」卻沒有 tag，人、網頁和下一個 session 都會誤以為已經凍結（`lint.py` 會亮紅燈「凍結沒做完」）。寫入途中發現和第 1 節預覽的不一樣、要人重新決定時，先把檔頭改回「待檢查」再問。

1. **版本**：`git tag --list '<切片>/0N-v*'` 取最大版本加一，得到 `<切片>/0N-vK`。多步一起凍結時，每步各自取版本、各自打 tag。
2. 交付物開頭區：狀態改「已凍結」，版本填 tag。
3. **切片 `CHANGELOG.md`** 最上面新增一筆（類型：凍結；多步一起凍結時可合寫一筆，標題列寫出每個完整的 tag 名稱，不縮寫）：改了什麼（初版摘要或本版相對上一版的改變）、依據、反例處理統計、依審查頁登記同意的 D-nn（「D-nn 依審查頁 <檔名> 問題 n／確認第 n 列同意」）；之前回頭修改那幾筆寫「同意者：待確認」的，不回填，在這一筆寫出同意者、產出者、審查者。第一次凍結（v1）另加「審查期間的修改」：送審後沒有逐筆記的整理性修改大約幾處、主要方向、對應的反例或檢查紀錄；已逐筆記的寫筆數（可用 `git log` 比對送審後的 commit）。
4. **第 ②③④ 步：合併進 `core/`**
   - 用工具，不自己寫同步程式：照第 1 節人同意的範圍，執行同一個 `sync_core.py` 指令加 `--write` 寫入。工具照 `docs/02` 第六節格式寫入：新項目標 `[候選]`、出處 `<切片>（<步驟> @ <tag>）`、Q／UC／US-D 加切片前綴；比對解析後的內容，只有真的改變的項目才更新出處；本步引用的既有 Entity 在「被引用」加上本切片；詞彙對照表新增區併入 `core/glossary.md`。
   - 工具列為「未同步」的章節，依第 1 節人的回答，要放的照 `docs/02` 第六節手動寫。「切片已沒有」的項目不刪除，依第 1 節人的決定標 `[已取代]` 或 `[已停用]`。工具轉錯時在回報中寫明，不要繞過；工具包由研究 repo 修正。
   - 規則編號與 `core/rules.md` 撞號時，照第 1 節人決定重編的那一方。
   - 本步引用了 `core/` 中 `[已取代]` 或 `[已停用]` 的項目時，照第 1 節人的決定改引用取代它的項目。
   - 本步「變更提案」區有已核准的第 3 級變更提案：被取代或停用的舊項目不刪除，標題列與 `core/glossary.md`、`core/relations.md` 對應的列改為 `[已取代: <新 ID>，<生效日>]` 或 `[已停用: <生效日>]`，狀態要一致（`docs/02` 第六節）。
   - `core/CHANGELOG.md` 新增一筆。
   - 第 ⑤ 步：`05_mapping.md` 有「其他切片事件的連鎖」時，每個上游事件在 `core/flows.md` 事件表的「連鎖」欄加上 `<本切片>（<本切片做什麼>；<時機>）`（先試用）；事件表還沒有「連鎖」欄的，在「被引用」之後補上這一欄（其他列留空）。寫完執行 `python3 tools/lint.py <切片>`，「連鎖」不能有紅燈（「版本」的「凍結沒做完」在打 tag 前一定會出現，不算）；`core/CHANGELOG.md` 記一筆。
   - 第 ⑤ 步：`slices/PLAN.md` 中這條切片的狀態改為「設計完成（待驗證）」，在 `slices/CHANGELOG.md` 記一筆（PLAN）。已經是「設計完成（待驗證）」的切片被要求回頭修改（例：其他切片要求）時，狀態不改；重新凍結 ⑤ 時照樣是「設計完成（待驗證）」。
   - 第 ⑥ 步：提醒人把這條切片的測試加進平台的自動執行（`docs/03` P9，由平台負責人安排），在回報中列出要加的測試檔。
   - 第 ② 步：本切片正式定義的名詞，在 `slices/ENTITY_SKETCH.md` 改為「已定義」，「一句意思」改為「見 core/entities.md」，在 `slices/CHANGELOG.md` 記一筆（SKETCH）。
5. **第 ⑥ 步：升級核心項目**
   - 本切片出處的 `core/` 項目，若相關的驗收問題、規則、黃金案例都經專家確認 → `[已驗證]`；有 `[暫代]` → `[已驗證（暫代）]`；仍有 `[待專家確認]` → 維持 `[候選]`，並在回報列出原因。
   - `core/CHANGELOG.md` 記一筆（類型：升為已驗證）。
   - `slices/PLAN.md` 中這條切片的狀態改為「完成」，在 `slices/CHANGELOG.md` 記一筆（PLAN）。

## 3. git
1. 列出要提交的檔案給人看（含 `inputs/` 中還沒 commit 的檔案——本切片的，以及規劃時建的 `inputs/shared/`、`inputs/research/`、`inputs/drafts/`——、`slices/PLAN.md`、`slices/ENTITY_SKETCH.md`、`slices/CHANGELOG.md`）。
2. `core/` 有修改時：依 `docs/01` 0.3，核心的修改要由**核心負責人**核准。
   - repo 有遠端且可用 `gh`：第 1 節人同意開 PR 的，開 PR（分支 `core/<切片>-0N-vK`）。
   - 沒有遠端：在回報中提醒核心負責人審閱 `core/` 的 diff。
3. commit 訊息：`<切片> 0N 凍結：<一句話摘要>`。
4. 打 tag `<切片>/0N-vK`。
5. 不 push，除非人要求。

## 4. 回報
- tag、提交的檔案、合併進 `core/` 的項目數。
- 仍標 `[待專家確認]`、`[未核對]` 的項目。
- 下一步：`/domain-step <N+1>`。第 ⑤ 步凍結後：這條切片設計完成，可以開始下一條切片；第 ⑥ 步等有系統時再做。第 ⑥ 步凍結後：這條切片完成。
- 建議下一步在新的 session 做，附一段交接提示（切片、剛凍結的 tag、下一步要執行的指令、仍待回覆的 EQ）。

## 全自動模式
`slices/PLAN.md` 的「執行模式」是 `全自動` 時（`docs/01` 0.2「全自動模式」）：
- 審查頁還沒作答：另開子代理當審查者，只給它審查頁、審查頁指到的檔案、`docs/01` 0.2 與 `docs/02`「審查頁」，不給產出時的對話；請它照審查者的角度逐題作答（不一定選建議答案）、確認列打 ✓ 或寫意見、自選 1～2 條抽查並寫結果、結論表審查者寫 `AI（自動）`、日期、結論。⑥ 的執行者寫 `自動放行`，結論寫「通過（AI 自審）」或「不通過」。它寫了意見或選了非建議答案的，照常記 X-nn（來源 `審查者`）處理；改了設計的，先回頭修改，不凍結。
- 之後照一般流程凍結（要問人的事選建議答案：`core/` 差異照寫入、不開 PR）。
- 第 ⑥ 步：不升「已驗證」，`slices/PLAN.md` 這條切片的狀態改 `完成（AI 自審）`；回報列出要人做的事（核對 `[未核對]`、確認 `AI 獨立計算（待人確認）` 的黃金案例、正式簽核 ⑥）。
- 回報最後一行寫「全自動：繼續」；地圖上已沒有可做的切片時寫「全自動：完成（原因）」。
