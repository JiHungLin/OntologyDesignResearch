# 規劃切片地圖

參數：`$ARGUMENTS`（可以空白或很粗略，例如「我們要做請假」）。

使用者不需要事先知道切片怎麼切，那正是這一步要一起討論出來的。先用兩三句話說明：
> 「我們會把要做的事拆成一條條**切片**。一條切片是一個情境，從起點走到一個可以驗證的結果（例：急診沒去 → 事後補單 → 餘額與扣薪正確）。很多條切片累積起來，就涵蓋一個**領域**（例：人資／請假）。這一步先一起列出有哪些切片、先做哪條。」

## 1. 收集資訊
1. 讀 `docs/01` 0.3（切片大小、切片地圖、全局名詞草圖）、`docs/02` 第五節的切片地圖與全局名詞草圖格式。
2. 列出 `inputs/` 的檔案並閱讀。
3. 使用者在對話中貼上的需求、訪談或文件：新增為 `inputs/shared/` 或 `inputs/<主題>/` 下的檔案，檔頭寫「使用者於對話中提供，<日期>」。不修改已存在的檔案。
4. 已有 `slices/PLAN.md`：讀它與各切片的狀態，這次是更新，不是重做。
5. 資訊不足時，一次問完（最多 5 題），例如：
   - 這套系統給誰用？要解決什麼問題？
   - 這一階段一定要做到的是什麼？明確不做的是什麼？
   - 最常發生的情況、最常出問題的情況各是什麼？
   - 有沒有 Domain 專家或客戶端使用者可以確認？

## 2. 提出地圖
1. 從資訊中找出**情境**：每個情境要有起點（某人的動作或外部事件）和可驗證的業務結果。功能名稱（「請假管理」）不是情境，要轉成情境。
2. 依 `docs/01` 0.3 估計大小；`太大` 的提出拆法（按結果拆或按路徑拆）。
3. 標出主要領域、會碰到的領域、依賴（含哪些先用靜態替代）。
4. 建議順序：第一條選正常流程，用來建立共用核心；有依賴的排在後面。
5. 替每條切片取代號（英文小寫，以 `-` 連接）；使用者同意的是情境，不需要自己取名。
6. 沒有把握的地方寫進「待釐清」（P-nn），不要自己假設。
7. 用 `templates/PLAN.md` 的格式寫成 `slices/PLAN.md`（不存在時建立），狀態「討論中」，「決定與理由」寫下切法與順序的理由，「變更紀錄」記一筆。
8. 先完成地圖的初稿，再做下一節的名詞草圖；兩份一起拿去討論。

## 3. 提出全局名詞草圖
切片一次做一條，但名詞要先看全局，避免第一條把共用的名詞定義得太窄。
1. 從地圖上**所有**切片的情境，找出會用到的名詞。使用者手上有既有的模型或名詞清單時，先請他放進 `inputs/`，以它為起點。
2. 用 `templates/ENTITY_SKETCH.md` 的格式寫成 `slices/ENTITY_SKETCH.md`：名詞、一句意思、層（core／shared／domain）、主要關係、會用到的切片、預計由哪條切片正式定義。狀態一律「草圖」。
3. **只寫輕量內容**：不寫屬性、幾對幾、規則。沒有任何切片會用到的名詞不列；每個名詞都要指得出哪條切片會正式定義它。
4. 特別檢查被很多切片用到的名詞（例：人、僱傭關係、組織、適用的國家規則）：後面的切片會需要它具備什麼，寫進「主要關係」或「不確定的地方」，讓第一條切片定義時有依據。
5. 拿不準的寫進「不確定的地方」，並在地圖的「待釐清」開 P-nn。

## 4. 討論
- 向使用者說明地圖：有幾條切片、建議先做哪條、為什麼、哪些地方需要他決定或確認。
- 地圖與草圖一起說明。依回饋修改，每次修改在對應文件的「變更紀錄」記一筆，寫改了什麼、依據、舊 → 新、影響、同意者（範本的註解有格式）。
- 編號（D-nn、P-nn）依新增順序遞增，不重排、不重用。
- 使用者**明確表示同意**後，兩份文件的狀態都改為「已同意（<同意者>，<日期>）」。沒有明確同意就維持「討論中」。

## 5. 結束
- 告訴使用者下一步：`/domain-new-slice <切片代號>`，從建議順序第一條開始。
- 不 commit；地圖會在第一條切片的第 ① 步凍結時一起提交。

## 之後更新地圖
- 新的需求、專家意見、或某條切片做到一半發現要拆或合併時，再執行本指令；地圖改了，同時檢查草圖的「會用到的切片」是否要跟著改。
- 拆分或合併：原切片狀態改為「已拆分」或「已合併」，在「決定與理由」寫明去向；進行中的切片要拆時，先停下來請人決定已完成的步驟怎麼處理。
