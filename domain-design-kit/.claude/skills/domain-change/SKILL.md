# 處理特例或錯誤

參數：`$ARGUMENTS`。讀 `docs/01` 0.2「發現特例或錯誤時，先判斷等級」與「處理順序」。

1. **先寫成驗收問題與黃金案例情境**：把特例寫成一條新的驗收問題（Qnn）與一個黃金案例情境（預期結果留給人填），確認目前的設計答不出來或答錯。
2. **提出等級建議，由人決定**：
   | 等級 | 判斷 |
   |---|---|
   | 0 | 切片還沒通過 ⑥，或改的是本切片仍為 `[候選]` 的核心項目 |
   | 1 | 模型不用動，只多一條規則或一種分類值 |
   | 2 | 要加屬性、關係或 Entity，既有意思不變 |
   | 3 | 既有概念要拆、要合，或幾對幾要改 |
   等級由檢查會的非產出者審查者判定；你只提出建議與理由，**停下來等人決定**。
3. **依等級處理**（人決定後）：
   - **0**：照 `/domain-expert-reply` 第 5 點的方式回頭修改並記 CHANGELOG。
   - **1**：在發現它的切片 `04_rules.md` 新增規則（編號全 repo 唯一）、分類值；補黃金案例；記 CHANGELOG（類型：新增規則（第 1 級））。
   - **2、3**：用 `templates/core/changes/CR-template.md` 在 `core/changes/` 建立 `CR-nnn.md`，填寫觸發它的驗收問題或反例（必填）與影響範圍（依 `docs/01` 0.9 回歸範圍，含引用它的切片）。**不要直接改 `core/`**，等核心負責人核准。
4. **回歸**：列出受影響的切片與要重跑的 ⑥ 項目。
5. 核准後套用變更：修改 `core/`、記 `core/CHANGELOG.md` 與受影響切片的 `CHANGELOG.md`。

經常落到第 3 級，表示第 ② 步做得不夠紮實；在回報中指出。
