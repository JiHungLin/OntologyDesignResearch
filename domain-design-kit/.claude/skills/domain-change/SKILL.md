# 處理特例或錯誤

參數：`$ARGUMENTS`。讀 `docs/01` 0.2「發現特例或錯誤時，先判斷等級」與「處理順序」。

0. **新需求先判斷擴充還是開新切片**：使用者轉述的是新需求（不是設計錯誤）時，依 `docs/01` 0.9「新需求：擴充現有切片，還是開新切片」提出建議與理由，**停下來等人決定**：
   | 情況 | 建議 |
   |---|---|
   | 同一個情境多了例外或細節（起點、終點不變），切片還沒通過 ⑥ | 回該切片的 ① 補情境與驗收問題（第 0 級，用 `/domain-step 1`） |
   | 另一個情境（起點或終點不同），或切片已通過 ⑥ | 用 `/domain-plan` 在地圖新增一條切片；要改 `core/` 的部分照下面第 1～5 點判斷等級 |
   | 只是某家客戶的公司規定不同 | 通常是第 1 級：新增公司政策規則，照下面處理 |
   起點和終點用切片地圖上該切片的情境來比；判斷不出來時建議開新切片。人決定擴充或開新切片的，交給對應的指令，本指令到此結束。
1. **先寫成驗收問題與黃金案例情境**：把特例寫成一條新的驗收問題（Qnn）與一個黃金案例情境（預期結果留給人填），確認目前的設計答不出來或答錯。
2. **提出等級建議，由人決定**：
   | 等級 | 判斷 |
   |---|---|
   | 0 | 切片還沒通過 ⑥，或改的是本切片仍為 `[候選]` 的核心項目 |
   | 1 | 模型不用動，只多一條規則或一種分類值 |
   | 2 | 要加屬性、關係或 Entity，既有意思不變 |
   | 3 | 既有概念要拆、要合，或幾對幾要改 |
   等級由檢查會的非產出者審查者判定；你只提出建議與理由，**停下來等人決定**。
3. **依等級處理**（人決定後）：
   - **0**：照 `/domain-expert-reply` 第 5 點的方式回頭修改並記 CHANGELOG。
   - **1**：在發現它的切片 `04_rules.md` 新增規則（編號全 repo 唯一）、分類值；補黃金案例；記 CHANGELOG（類型：新增規則（第 1 級））。法規廢止某個分類值時，`core/rules.md` 分類值表與 `core/glossary.md` 對應的列改為 `[已停用: <生效日>]`，不刪除。
   - **2、3**：用 `templates/core/changes/CR-template.md` 在 `core/changes/` 建立 `CR-nnn.md`，填寫觸發它的驗收問題或反例（必填）與影響範圍（依 `docs/01` 0.9 回歸範圍，含引用它的切片）；第 3 級另列被取代或停用的項目（舊 ID → 新 ID、生效日）。**不要直接改 `core/`**，等核心負責人核准。
4. **回歸**：列出受影響的切片與要重跑的 ⑥ 項目。
5. 核准後套用變更：修改 `core/`、記 `core/CHANGELOG.md` 與受影響切片的 `CHANGELOG.md`。第 3 級：被拆、被合的舊項目**不刪除**，標題列改為 `[已取代: <新 ID>，<生效日>]`（沒有取代者的改 `[已停用: <生效日>]`），`core/glossary.md`、`core/relations.md` 中對應的列同時改，狀態要一致（`docs/02` 第六節）；再搜尋各切片，列出仍引用舊項目、之後要改引用新項目的地方。

經常落到第 3 級，表示第 ② 步做得不夠紮實；在回報中指出。
