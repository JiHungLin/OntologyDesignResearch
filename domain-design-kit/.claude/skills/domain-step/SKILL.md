# 執行一個步驟

參數：`$ARGUMENTS`。第一個是步驟編號 N（1～6），第二個是切片代號。
使用者用一般的話觸發（例：「繼續」「開始寫規則」）而沒有參數時：從他的話與 `domain-status` 的結果推斷 N 與切片（「繼續」＝狀態為「草稿」的那一步，或最後一個已凍結步驟的下一步），開始前用一句話確認，例：「接下來做 leave-backfill 的第 ③ 步：流程與狀態。」推斷不出來就問。

## 共同流程（每一步都照做）

### 1. 準備
1. 讀 `docs/01` 的 0.2、0.9 與第 N 步章節；讀 `docs/02` 第四節（共用格式）與第 N 步的格式。
2. **進入條件**：第 N−1 步要「已凍結」（看開頭區狀態與 `git tag --list '<切片>/0<N-1>-*'`）。
   - 未凍結 → 停下來告訴人。人同意先開始時，在本步開頭區「讀取的輸入」標註「<檔案>（未凍結）」，引用到待確認項目的地方加標記。
   - 例外：第 ④ 步可以在第 ③ 步「待檢查」時開始（`docs/01` 0.9），但 ③ 要先凍結，④ 才能凍結。
3. 讀下方「各步驟」表列的輸入。只讀列出的檔案。
4. 把預期要問專家的問題先寫進 `questions.md`（狀態「待問」）。

### 2. 產出初稿
1. 交付物檔案已存在且狀態是「草稿」：在原檔繼續。狀態是「待檢查」或「已凍結」：這是回頭修改，**每一處修改都要在 `CHANGELOG.md` 記一筆**（類型：回頭修改（第 0 級））。
2. 照範本的固定章節與欄位填寫。開頭區填「讀取的輸入」與它們的 tag。
3. 依下方「各步驟」的重點產出。

### 3. 挑錯（另開乾淨的 context）
用 Agent 工具開一個**新的子代理**，不要把本次對話內容給它。只給它：
- 交付物的檔案路徑（以及它需要對照的上游檔案路徑）；
- `docs/01` 0.5 的挑錯角度中，本步適用的角度（見下表）；
- 指示：「你是懷疑者，不是作者。針對這份交付物提出至少 5 個具體反例。每個反例寫：攻擊哪一項、用什麼真實情境、為什麼會出錯。不要修改檔案，只回報。」

### 4. 處理反例
- 逐條處理，記在「決定與理由」的「反例處理」表（X-nn）：
  - 能判斷且成立 → `接受，已修改`，修改交付物；重要的判斷另記一筆 D-nn。
  - 不成立 → `拒絕`，寫理由。
  - 需要現實資訊才能判斷 → `轉問專家`，寫進 `questions.md`（EQ-nnn），相關項目標 `[待專家確認: EQ-nnn]`。
- 修改後若產生新的疑點，可以再跑一輪挑錯；找不出新的有效反例就停。

### 5. 自評
1. 第 ②～④ 步：執行 `/domain-check`，把紅燈修掉或寫進回報。
2. 對照 `docs/02` 第七節，逐條確認本步相關的引用。
3. 在「檢查紀錄」表的「AI 自評」欄逐條填 ✓、✗ 或「部分：說明」。不填「審查者確認」。
4. 開頭區狀態改為「待檢查」。

### 6. 停下來回報
向人回報後**停止**，不要進入下一步。回報內容：
- 產出了什麼（檔案、數量摘要）。
- 需要人決定的事（列選項與你的建議）。
- 新增或仍待回覆的專家問題（EQ）。
- 自評為 ✗ 或「部分」的項目。
- 下一步：「請非產出者依檢查紀錄逐條審查，在『審查者確認』欄打勾並填寫審查者、日期、結論，然後執行 `/domain-freeze N`。」

## 各步驟

| 步驟 | 讀取 | 產出 | 挑錯角度 |
|---|---|---|---|
| ① | `slices/PLAN.md` 中這條切片的列、`inputs/<切片>/`、`inputs/shared/`、`core/` | `01_scope.md`、`questions.md` | 領域實務 |
| ② | `01_scope.md`、`core/`、`slices/ENTITY_SKETCH.md` | `02_entities.md`；必要時更新 `slices/ENTITY_SKETCH.md` | 本體懷疑者 |
| ③ | `01_scope.md`、`02_entities.md` | `03_flows.md`、`03_use_cases.md` | 時間與帳務、隱私與濫用 |
| ④ | `02_entities.md`、`03_flows.md`、`03_use_cases.md`、`inputs/` 的法規與政策原文 | `04_rules.md`；回填 `03_flows.md`、`03_use_cases.md` | 領域實務、時間與帳務 |

| ⑥ | `01_scope.md`、`03_use_cases.md`、`04_rules.md`、`02_entities.md`、`05_mapping.md`、實作 | `06_evidence/` | 領域實務 |

### ① 範圍與驗收問題
- **第 ① 步不做 entity 分析**：範圍、「範圍外但會用到」「交給第 ② 步的觀察」都用業務語言寫，不寫英文識別名稱、不判斷是不是 Entity。「範圍外但會用到」只列不由本切片負責的東西；「歸屬的切片」寫會正式設計它的切片代號（規則寫「<切片> 的第 ④ 步」）。本切片自己第 ②～④ 步會定義的名詞或規則都不列；不確定歸哪條切片時，問使用者，必要時更新切片地圖。自評時檢查每一列：歸屬的切片排在前面者，要列在地圖的「依賴」欄並直接引用；排在後面者，要用靜態替代。不符合就停下來，向使用者提出調整地圖的順序或依賴。
- 以切片地圖的情境為起點細化範圍；確認切片大小（`docs/01` 0.3）與模式（完整／輕量，判斷不出來用完整）。範圍細化後和地圖不一致（例：其實要拆成兩條），停下來請人決定，再用 `/domain-plan` 更新地圖。
- 用到 `inputs/research/` 的條目時，最後確認日期超過 6 個月的，重新打開網址比對：沒變就更新最後確認日期；有變就新增一筆、舊的標「已過時」（`docs/02`），並在回報中列出。第 ④ 步同樣適用。
- 草稿 User Story 用表格（編號、情境、例外、來源、依據），來源的值同驗收問題。你自己想出的情境寫 `AI`，即使參考了推想草稿或法規條文；直接出自訪談、現場紀錄或使用者描述的，才寫對應來源。全部都是 AI 寫的時，在回報中明確指出，並在 `questions.md` 新增一題請專家或使用者提供真實情境。
- 驗收問題至少 8 條（預設），含至少 1 條維運類。來源照實填：你想出來的寫 `AI`；從 `inputs/` 的訪談或人提供的寫對應來源；出自 `inputs/research/` 法規原文的寫 `法規`；出自 `inputs/drafts/` 推想草稿的寫 `AI`（即使草稿已接受為假設）。非 AI 來源不足 2 種、或沒有 Domain 專家／客戶端使用者時，在回報中明確指出，**不要自己補標來源**。
- P0 問題的「確認」欄，沒有專家確認過的一律 `[待專家確認: EQ-nnn]`。

### ② 名詞盤點
- 先查 `core/entities.md`：有的放「引用」，候選的加 `[引用候選]`。
- 先處理第 ① 步的「範圍外但會用到」（屬於名詞的引用 `core/` 或建卡；屬於規則資料的留到第 ④ 步）與「交給第 ② 步的觀察」（逐條處理，結果寫進「決定與理由」）。
- 對照 `slices/ENTITY_SKETCH.md`：本切片要正式定義的名詞，查草圖上「會用到的切片」，確認定義撐得起那些切片（例：僱傭關係要能表達跨國轉任）。挑錯時把這些後續切片也交給子代理當攻擊角度。
- 本切片需要修改**其他切片**已凍結的名詞、流程或規則時：停下來，向人說明要改哪條切片的哪一步、為什麼。人同意後回頭修改（對方尚未通過 ⑥ 屬第 0 級），兩邊的 `CHANGELOG.md` 各記一筆，被改的步驟狀態改回「待檢查」並重新審查。
- 和草圖不同的地方（要拆、合、改層、改由別條切片定義）：更新草圖，並在草圖與 `slices/PLAN.md` 的變更紀錄各記一筆，在回報中列出。
- 每個候選概念用三問判斷（`docs/01` ②）。不是 Entity 的放「不是 Entity」表。
- 新識別名稱取名前，搜尋 `core/glossary.md` 避免重複。
- 詞彙對照表新增區，要包含本步所有新的 Entity、屬性、關係。

### ③ 流程與狀態
- 每個會變狀態的東西：狀態機＋歷史需求（依哪條 Q）。
- 每個事件：觸發來源、層。檢查四種觸發來源是否都想過（人、其他單位個體、外部系統、時間）。
- 「建議」層事件不改變狀態。
- 寫完 UC 後填「草稿涵蓋檢查」表，每個 US-D 都要被涵蓋。

### ④ 規則與限制
- 規則編號：取 `core/rules.md` 與所有切片 `04_rules.md` 的最大號加一。
- 你給的條號與數字一律 `[未核對]`；`inputs/` 有原文的（含 `inputs/research/`），引用原文位置與網址，仍由人核對。這條切片需要、但還沒蒐集的法規，先去公開來源找並照 `docs/02` 的格式存進 `inputs/research/`（同主題加進同一份檔案，更新 `INDEX.md`）。規則表的「來源」附上證據條目編號（例：`勞保加保#01`）。規則表的「核對」是**解讀**的核對；條文原文的核對看 research 條目的「核對」欄。兩者都已核對，規則才算已核對；在回報中列出引用了哪些原文仍 `[未核對]` 的條目，方便人一次核對。規則有多個版本時，每個版本引用各自的證據條目。
- 每條規則判斷時用到的屬性，要存在於 `02_entities.md`。不存在 → 這是回頭修改（回到 ②，第 0 級）：停下來向人提出，同意後再改 ②，並記 CHANGELOG。
- 回填 `03_flows.md` 狀態轉換的「規則」欄與 `03_use_cases.md` 的「規則」，並在「回填紀錄」列出。被回填的檔案若已凍結，記 CHANGELOG。

### ⑤ 投影到實作
- 依 `docs/03` 平台約定。**先只產出 `05_mapping.md`，停下來請人確認對照表**；人確認後，再依對照表產生 `schema.sql` 與 `api.yaml`（`docs/01` ⑤ 的提示範本）。這些都是設計文件，不建立實際的資料庫或服務。
- 每張業務表、每個業務欄位、每支 API 都要在對照表；技術欄位標 `[技術]`。
- **紙上驗證（預設）**：建立 `06_evidence/golden_cases.md`，請人挑 3～5 個案例並填「預期結果、計算過程、計算者」（你不能填）。人填好後，你依 ②③④ 的設計逐步推演，填「紙上推演」（用到的名詞、狀態轉換、規則編號與推出的結果）與「紙上判定」。不一致時，先請人複核計算，再依 `docs/01` 0.9 回頭對照表提出要回到哪一步。人決定跳過時，在檢查紀錄寫明理由。

### ⑥ 跑起來驗證
- 在有系統時進行，可以逐條做，也可以累積幾條切片一起做。黃金案例沿用第 ⑤ 步的同一批。
- 你負責：合成資料、測試程式、**實際執行**並把輸出存進 `06_evidence/results/`、`answers.md`。
- 黃金案例：你可以寫情境與輸入，**預期結果、計算過程、計算者由人填**。人還沒填之前，判定一律 `[未執行]`。
- 沒有實際跑過的項目寫 `[未執行]`，不寫通過。
- `signoff.md`：只填 AI 自評與結果摘要，執行者、簽核者由人填。
