# 處理專家回覆

參數：`$ARGUMENTS`。使用者直接轉述意見而沒有給 EQ 編號時：比對 `questions.md` 中狀態為「已問」「待問」的問題，找出它回答的是哪一題，先向使用者確認；都對不上的，當作新意見，替它新增一個 EQ 編號（提出於「專家主動提出」）。

0. **這一輪已送審時**（有步驟是「待檢查」）：先問人「併入這輪／下一輪」（選擇題，`docs/01` 0.9「一輪的範圍」）。建議放下一輪、先凍結已審的部分；只有不改就會讓這輪審查的內容出錯時，才建議併入。
1. **更新 `questions.md`**：狀態改「已回覆」，填答覆、答覆日。使用者轉述的是自己查證整理的資料（不是專家答覆）：存成 `inputs/<切片>/` 的檔案（檔頭「依據等級：使用者查證」；同一題已有整理的，加在同一份檔的新日期小節），狀態改「暫依整理」，答覆欄寫那份檔與「使用者整理，非專家答覆」；相關項目仍標 `[待專家確認]`，不換成「已確認」；和設計不同的，照下面「不一致」處理。
2. **找出受影響的項目**：該列「影響」欄，加上全切片搜尋 `[待專家確認: EQ-nnn]` 的位置。必要時用 `/domain-check` 後的 `tools/impact.py <名稱>` 擴大範圍。
3. **逐項比對**答覆與目前的設計：
   - **一致**：把 `[待專家確認: EQ-nnn]` 換成「已確認」（驗收問題的「確認」欄寫「已確認」）。若該檔已凍結，記 CHANGELOG（類型：專家回覆）。
   - **不一致**：依 `docs/01` 0.9 的「回頭對照表」判斷要回到哪一步：
     | 答覆的內容 | 回到 |
     |---|---|
     | 名詞的邊界錯了 | ② |
     | 現實流程和設計不同 | ③ |
     | 規則有例外或解釋不同 | ④（需要新的判斷條件時再回 ②） |
     | 新的情境或需求 | 先依 `docs/01` 0.9「新需求：擴充現有切片，還是開新切片」判斷：擴充回 ①；開新切片用 `/domain-plan`；公司規定不同用 `/domain-change` |
     | 「這不是我要的」（看過 ⑥ 結果） | ① |
   - 切片尚未通過 ⑥ → 第 0 級；已通過 ⑥ 且影響已驗證的核心項目 → 改用 `/domain-change`。
4. **提出方案並停下來**：回到哪一步、要改什麼、依 `docs/01` 0.9「回歸範圍」哪些後續步驟要重新檢查。寫成選擇題（`docs/01` 0.2「問人的方式」）：先複述專家或使用者的說法（引用原話），A（建議）是你的方案，其他選項寫會改哪裡。**等人同意**。
5. 人同意後：
   - 修改被回到的那一步，並在 `CHANGELOG.md` 記一筆（類型：回頭修改（第 0 級）；依據：EQ-nnn；舊 → 新；影響與回歸）。
   - 被修改且原本已凍結的檔案，狀態改回「待檢查」。依回歸範圍，後續已凍結的步驟中受影響的部分也照此處理；沒受影響的步驟維持凍結。影響到其他切片已凍結的內容時，照 `/domain-step` 共同流程第 1 點「要改到其他切片已凍結的內容時」處理，不在這個 session 改對方。
   - 接著照 `/domain-step` 第 3～5 點做（範圍只有這次的差異）：**另開子代理挑錯**（每個受影響步驟用自己的挑錯角度，附既有的使用者決定）→ 照規範處理反例 → 只重新自評受影響的完成標準（加 `（<日期> 重評）`）→ 新開一份審查頁 `reviews/<日期>_<步驟>.md`，只列這次的差異、每一步只列自己的 → **另開子代理做送審前核對**。檔案內舊的審查表與舊的審查頁都不動。舊格式（完成標準表有「審查者確認」欄）的檔案，只清空受影響完成標準的審查者確認。
   - `questions.md` 的「處理」欄寫：回到哪一步、等級、對應的 D 編號或 CHANGELOG 日期。
6. 回報：改了哪些檔案、這輪挑錯與核對的結果、審查頁的路徑；同一次修正牽涉多步的，建議一起審查、一起凍結（例：`/domain-freeze 3,4,5`）。附一段交接提示，建議審查與凍結在新 session 做。
