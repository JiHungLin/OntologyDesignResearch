# Domain 設計工具包

讓 Claude Code 依團隊的 Domain 設計規範跑設計：AI 產出交付物、另開子代理挑錯、自評後停下來；人審查、決定、凍結。新的 session 不需要任何先前對話的記憶，規則由 `CLAUDE.md` 自動載入，狀態全部從檔案讀出。

## 三個名詞

| 名詞 | 比喻 | 意思 | 例子 |
|---|---|---|---|
| **共用核心**（`core/`） | 整張地圖 | 所有已定義的概念，大家共用一份——**成果** | Person、Employment、LeaveEntitlement |
| **領域** | 地圖上的一個區域 | 一個業務主題範圍，用來分類——**範圍** | 人資／請假、人資／薪資、POS／點餐 |
| **切片** | 實際走一條路線 | 一個情境從起點走到可驗證的結果——**工作單位** | 急診沒去 → 事後補單 → 餘額與扣薪正確 |

- 不先把整個領域設計完，而是一條一條切片做。每做完一條，共用核心就多一塊確認過的概念。
- 一個領域由很多條切片累積而成；一條切片也可能碰到好幾個領域。
- 概念不屬於切片，屬於共用核心。下一條切片用到同一個概念，直接引用，不重新定義。
- **你不需要事先想好切片的名稱和範圍**。先和 AI 一起討論出「切片地圖」，再一條一條做。
- **名詞先看全局**：規劃時 AI 會同時整理「全局名詞草圖」，列出所有切片會用到的名詞與預計在哪條切片正式定義，讓第一條切片就把共用的名詞定得夠完整。草圖只是參考，正式定義在共用核心。

## 開始一個新 repo

工具包資料夾**裡面的東西**要放在新 repo 的**最上層**，不是把 `domain-design-kit` 整個資料夾放進去，否則 Claude Code 讀不到 `CLAUDE.md` 和指令：

```bash
mkdir -p ~/projects/hr-domain-design
cp -r domain-design-kit/. ~/projects/hr-domain-design/   # 結尾的 /. 會連隱藏的 .claude/、.gitignore 一起複製
cd ~/projects/hr-domain-design
rm build_kit.py                                       # 只在研究資料夾使用
git init && git add . && git commit -m "Domain 設計工具包"
claude
```

手上有資料的話，可以先放進 `inputs/shared/`（需求說明、訪談紀錄、法規原文）；沒有也沒關係，可以直接在對話中說明或貼上，AI 會存成 `inputs/` 下的新檔案。開始做某條切片後，屬於那條切片的資料放在 `inputs/<切片代號>/`。

在 Claude Code 裡**直接用說的**，不需要記指令，例如：

```
我們要做連鎖飲料店的人資系統，先從請假開始
```

AI 會先和你一起整理切片地圖；同意後說「開始做第一條」就行。之後「繼續」「審查好了」「專家回覆了」這類說法，AI 都會對應到正確的流程。下面的斜線指令是給熟悉的人用的捷徑。

## 每一步的節奏

```
/domain-plan        先盤點現實資料，再和你一起整理切片地圖與全局名詞草圖（之後有新資料隨時再跑）
        │
/domain-new-slice   從地圖挑一條，建立資料夾
        │
/domain-step N      AI：讀輸入 → 產出 → 子代理挑錯 → 照規範處理反例 → 自評 → 審查頁 → 子代理送審前核對 → 停下來
        │
        ▼
人：審查者（非產出者）在審查頁（slices/<切片>/reviews/）作答：選擇題選 A、B 或寫一句，確認要看的列，自選抽查，填審查者、日期、結論
        │
        ▼
/domain-freeze N    AI：寫 CHANGELOG → ②③④ 合併進 core/（候選）→ commit → 打 tag
                    做到 ⑤ 凍結＝設計完成（待驗證），可以開始下一條；⑥ 在有系統時再做
        │
        ▼
/domain-step N+1
```

每次開新的 session，先執行 `/domain-status`。

## 指令（捷徑，也可以直接用說的）

| 指令 | 用途 |
|---|---|
| `/domain-status [切片]` | 從檔案重建狀態：各步驟、tag、待回覆的專家問題、下一步 |
| `/domain-plan [粗略的範圍]` | 一起討論切片地圖：有哪些切片、屬於哪個領域、先做哪條 |
| `/domain-new-slice [代號或描述]` | 從地圖挑一條切片，開始第 ① 步 |
| `/domain-step <1-6> [切片]` | 執行一步，產出後停下等審查 |
| `/domain-freeze <1-6> [切片]` | 審查通過後凍結 |
| `/domain-expert-reply <EQ-nnn> <答覆>` | 處理專家回覆，必要時提出回頭方案 |
| `/domain-change <描述>` | 凍結後發現特例或錯誤（含實作時），判斷等級 0～3 |
| `/domain-check [切片]` | 轉出 YAML，跑檢查工具與引用檢查 |
| `/domain-arch <初判｜關卡｜複查｜提升｜補代價> [切片]` | 平台的架構決定（`architecture/DECISIONS.md`）：地圖同意後、第 ⑤ 步開始前、⑤ 凍結時由其他指令轉來 |

## 人要做的事

| 時點 | 誰 | 做什麼 |
|---|---|---|
| 切片規劃 | 負責人、Domain 專家 | 有現實資料就提供（表單、Excel、既有系統、規章、常出問題的案例）；沒有也沒關係，AI 會先去公開來源找，找不到的寫成推想草稿。逐份看推想草稿，判斷「大致對、能先當假設用」就接受；有空時核對 research 條目的原文；和 AI 討論切片地圖與全局名詞草圖，明確表示同意 |
| 每一步產出後 | 非產出者的審查者 | 只看這一輪的審查頁並在上面作答（問題選 A、B 或寫一句話，確認列打 ✓ 或寫意見），自選 1～2 條完成標準抽查，填審查者、日期、結論（⑥ 也用審查頁：每個黃金案例一列、P0 回答、抽查時打開執行紀錄的 log） |
| 第 ①④⑥ 步（至少） | Domain 專家 | 回答 `questions.md` 的問題；確認範圍、規則、黃金案例 |
| 第 ④ 步之後、⑥ 之前 | 人 | 對照原文核對規則，核對完告訴 AI「核對好了」（哪幾筆、結果），AI 照你的話記錄；④ 不必等核對就能凍結，⑥ 中受未核對規則影響的案例不算通過 |
| 第 ⑤ 步 | 人 | 分兩段審查：第一段確認對照表、確認黃金案例並算預期結果；第二段看紙上推演的結果再通過 |
| 第 ⑥ 步 | 人 | 以獨立於系統的方式算出黃金案例的預期結果；執行者與簽核者分開（只有一個人時可以同一人，執行者寫「<名字>（一人團隊）」） |
| `core/` 有修改時 | 核心負責人 | 審閱並核准 |
| 平台決定與選型（地圖同意後、第 ⑤ 步開始前、⑤ 凍結時） | 架構負責人 | 回答 `/domain-arch` 的選擇題（一條 ADR 一題）：平台約定的現況、選型、要不要把 ⑤ 的做法提升成跨切片的約定；結果寫在 `architecture/DECISIONS.md`（試跑時由你兼任） |
| 平台的非功能目標 | 平台負責人 | 決定 P13 的目標值（回應時間、可用性、併發與尖峰、備份與還原；第一次試點前必須填），寫在 `architecture/DECISIONS.md` |
| 平台的資安範圍、第 ⑤ 步挑錯與 ADR 的資安影響 | 資安負責人 | 決定資安範圍（法規、客戶要求、ASVS 等級，判斷 `K12` 的 ADR）；同意「隱私與濫用」反例的 `拒絕` 或風險接受、ASVS 與 P9 安全檢查的例外（`docs/07`） |

## 全自動模式（先試用）

沒有人在線上也能從規劃一路做下去，人事後再看、再改（`docs/01` 0.2「全自動模式」）。

1. 新專案放在獨立的資料夾與 repo。`slices/PLAN.md` 開頭區的「執行模式」改成 `全自動`。
2. 在 repo 根目錄執行 `python3 tools/auto_run.py`。每一圈開一個新的 Claude Code session，只做一個動作，做完自己開下一圈；停下來的時候會說原因（完成、需要人、沒有進展）。
3. 指令與檔案修改不逐條核准，由 `tools/auto_hook.py` 放行並記錄在 `.domain-auto/`；`git push`、`sudo`、碰其他 repo 或家目錄、docker 掛主機路徑或 privileged 會被擋下並停止。
4. 人的關卡由 AI 代答並標記：審查者 `AI（自動）`、黃金案例的計算者 `AI 獨立計算（待人確認）`、⑥ 執行者 `自動放行`、切片狀態 `完成（AI 自審）`。
5. 事後：看 AI 作答的審查頁，要改的直接改答案或寫意見（記成來源 `審查者（事後）` 的反例，照第 0 級回頭修改）；確認黃金案例的預期結果；核對 `[未核對]` 的原文；正式簽核 ⑥ 後 `core/` 才升「已驗證」。

## 內容

| 路徑 | 內容 |
|---|---|
| `CLAUDE.md` | AI 的工作規則（自動載入） |
| `.claude/skills/` | 上面九個指令 |
| `docs/` | 規範文件（唯讀），從研究資料夾複製 |
| `templates/` | 交付物範本（唯讀） |
| `tools/` | `md2build.py`（Markdown 轉 YAML）、`check.py`（結構檢查）、`lint.py`（引用檢查）、`table.py`（讀表格）、`sync_core.py`（凍結時同步 `core/`）、`run_evidence.py`（⑥ 存執行紀錄）、`check_env.py`（檢查 ⑥ 的驗證環境）、`derive.py`、`impact.py`；`tests/`（工具的測試與範例切片） |
| `inputs/` | 原始輸入：現場資料（`shared/`、`<切片>/`）、AI 蒐集的公開來源（`research/`）、AI 推想草稿（`drafts/`，要你同意）；也可以直接在對話中貼上 |

## 維護（在 OntologyResearch 內）

規範文件的正本在 OntologyResearch 根目錄。修改正本後，在 `domain-design-kit/` 執行：

```bash
python3 build_kit.py
```

它會把七份規範複製到 `docs/`，並把《團隊開發流程_精簡版》各步驟的完成標準重新寫進範本的「檢查紀錄」。已經開始跑的設計 repo 不會自動更新；要更新時，把工具包檔案（`CLAUDE.md`、`README.md`、`.gitignore`、`docs/`、`templates/`、`tools/`、`.claude/`）一起複製過去，先確認那邊的這些檔案沒被改過，只 commit 這些檔案（訊息「更新設計工具包：…」），不動 `slices/`、`inputs/`、`core/`。
