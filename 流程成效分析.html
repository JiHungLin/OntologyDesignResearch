10/07 設計方向套用後的第一條切片：成效分析

比較：hire-employee（10/07 之前的流程）vs annual-leave-grant（套用 10/07 決議與 10/19 修改） 資料：HR design/main @ c7987b0；實作 impl/annual-leave-grant @ 405330b 更新：實作完成後補第七節 讀者：自己與團隊內部

參數表、決策表、差異審查有證據證明有用。紙上驗證抓得到問題，但涵蓋的案例太少，實作時的設計問題總數沒有減少（22 個對 21 個）。審查重點沒有讓人真的去看細節。另外，切片之間的交接開始出問題，10/07 暫緩的「整體流程圖」該拿出來重新判斷了。

一 · 結論

八個結論

1紙上驗證多抓到 2 個問題，但實作時的設計問題沒有變少紙上驗證在實作前抓到 GC04、GC06 兩個問題。實作時仍發現 22 個（第一條 21 個），換算成每條規則反而較多。差別在性質：這次幾乎都是「寫了但不夠精確」，第一條有 API 接不起來、條件沒有結果。
2決策表有用④ 寫了 6 張；挑錯 X-12、X-26 直接指出「組合漏了」，GC04 推演時也用 R93 決策表判斷。
3參數表有用18 個參數名稱全部照 ④，程式直接從參數表讀預設值，沒有自取名稱（第一條自取了 min_age、compare_basis 等）。和參數有關的問題由 7/21 降到 5/22，剩下的是格式、代碼、存放處沒寫清楚。
4差異審查省事，已改為採納已凍結後的回頭修改只審了 16 列差異；第一條切片每輪要清空再填回 28 格。
5審查重點沒有讓人的審查變得更實質74 列全部只打勾，沒有一列寫意見；人的實質意見都在對話裡提出。實作時還發現 3 個規則邏輯錯誤（R83、C01、又休又領），都一路通過了審查。
6「整體流程圖」的重新判斷條件已經出現做到一半，地圖新增了 3 條切片（D-36、D-37、D-39）；⑤ 還要在 hire-employee 的 API 掛特休的連鎖處理（D-04）。
7流程的漏洞主要是 AI 的斷言錯誤18 項流程問題中 7 項屬於這類，靠另開 context 的挑錯和使用者才抓到。
8速度快了，但不能全歸功於流程① 到 ⑤ 用了 3 天，第一條約 9 天；不過這條切片規模較小，人介入也比較少。

四 · 限制

這不是對照實驗

規模不同Entity 6 對 18、規則 35 對 64；所以另外列了「每條規則」的比值。
第一條也在建流程它的回頭修改有一部分來自流程本身在改。
實作方式不同第一條分四輪，每輪先改設計；這條一次寫完，22 個問題都還待處理。
人介入較少從 ③ 起是「8～9 成交給 Claude」的實驗，人審查的資料偏少。
沒有 HC兩條切片共 38 題專家問題，沒有一題由人資專家回答。
早期在 cloud 做第一條的 ①② 在 cloud session 完成，只能看凍結日期。

最常見的錯是 AI 憑記憶或只查一部分就下斷言，不是設計方法本身的問題。最有效的對策是另開 context 逐句核對，現在已寫進挑錯指示。另一個教訓是：工具「默默跳過」比「報錯」危險。守恆式表少了一行分隔線，舊工具不報錯也不檢查，C01、C02 就一直沒被檢查到。

六 · 建議

下一步

  1. 重新判斷「整體流程圖」。範圍先限定在切片之間的交接：每條切片的起點和終點接到哪條切片、要掛哪些上游事件。不一定要用正式的 BPMN。
  2. 判斷三個試用項目（已完成，2026-10-21 三項都照建議）：參數表、實作者角度、審查重點。
  3. 記下人的貢獻。人在對話中指出的問題也記成 X-nn，來源寫「審查者」，下一輪才量得出人審查的效果。
  4. 處理「只勾不看」。兩個方向：照 10/07 決議加「AI 出題」；或把審查重點縮小到「AI 提出、沒有依據的決定」和紙上驗證的差異，這次真正改到設計的都出自這兩處。
  5. 處理實作回報的 22 個設計問題。多數是回 ④⑤ 的第 0 級；#6 時區要先決定放在 core 還是平台設定。
  6. 讓 HC 回答一部分專家問題。至少回答 P0 的幾題；否則「設計對不對」只有 AI 和使用者檢查過。
